## 1. 背景与目标

当前代码已经具备统一请求/结果模型、MarkItDown 解析、旧版 Office 转换和基础 Markdown 切块能力，但尚未形成完整的多模型自动路由、跨模型统一输出、质量优化、独立后端和 Web 展示闭环。

本项目由三名成员基于当前代码共同扩展，形成一套可解耦运行的文档解析系统：

```text
原始文档
  → 模型能力检测与自动/手动路由
  → 解析模型调用与原生结果收集
  → 跨模型统一输入输出
  → 质量检查与安全优化
  → Web 展示、结果下载或重新解析
```

最终系统必须同时支持：

1. 完整前后端运行；
2. 只启动后端，通过 API 测试；
3. 不启动前后端，单独测试路由、某个解析算法、统一转换或质量层。

### 1.1 现有代码基线

本任务是对当前工作区代码的增量扩展，不是重新创建一个互不兼容的新项目。开发开始时的真实基线如下：

| 现有文件/模块                           | 当前职责                                                                                 | 本任务中的处理原则                                                          |
| --------------------------------------- | ---------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| `__init__.py`                         | 对外导出`DocumentParserGateway` 和稳定协议                                             | 保留现有导入方式，新增公共类型时继续从顶层按需导出                          |
| `core/contracts.py`                   | 已定义`RoutingDecision 1.0`、`ParsedDocument 2.2`、`QualityPackage 1.0` 及其子模型 | 作为公共协议唯一事实源；不另建一套含义重复的模型                            |
| `core/gateway.py`                     | 当前固定调用 MarkItDown，并编排旧 Office 转换                                            | 扩展为路由与 Adapter 编排入口；保留现有`parse`、`parse_file` 等调用能力 |
| `core/inspector.py`                   | 根据文件名和内容大小产生基础信号                                                         | 扩展文档/图片路由信号；不得把具体模型选择硬编码在预检器中                   |
| `core/converter.py`                   | 将`.doc/.ppt` 转为 `.docx/.pptx`                                                     | 继续复用；新增路由不能破坏旧 Office 转换和临时文件清理                      |
| `parsers/markitdown/markitdown.py`    | 在受控子进程中调用 Microsoft MarkItDown                                                  | 作为第一个真实 Adapter 保留，并用于多 Adapter 协议回归                      |
| `parsers/markitdown/block_builder.py` | 将 Markdown 简单切成标题和段落                                                           | 保持当前行为兼容；更丰富结构由统一归一化或质量层增量实现                    |

### 1.3 当前仓库状态

截至本版 Spec，仓库已经完成：

- 公共 Pydantic 契约 `RoutingDecision 1.0`、`ParsedDocument 2.2`、`QualityPackage 1.0`；
- `routing_decision.json`、`parsed_document.json`、`quality_package.json` 三份固定联调样例；
- 契约加载、跨阶段来源衔接、手动路由硬约束和重解析硬约束测试；
- `main` 以及三条成员功能分支；
- MarkItDown、旧 Office 转换和现有 Gateway 基线。

当前尚未完成、不得在演示或验收中声称已完成：

- Docling、MinerU、OCR 三条真实 Adapter；
- 自动/手动模型路由和 JPG/JPEG/PNG 正式测评；
- 表格字段绑定、标题树、引用绑定等质量算法；
- 独立后端、Web 前端和真实端到端闭环。

### 1.2 增量扩展原则

1. **复用优先**：能够在现有类、协议和目录边界上扩展的功能，不创建平行实现；
2. **向后兼容**：现有调用方继续可以使用 `DocumentParserGateway.from_environment()`、`parse()` 和 `parse_file()`；
3. **分层新增**：模型路由新增到 `routing/`，统一 Adapter 继续位于 `parsers/`，质量能力新增到 `quality/`，Web 分别位于 `backend/` 和 `frontend/`；
4. **单一公共协议**：`core/contracts.py` 是解析公共协议的唯一事实源，前端 API Schema 和质量层输入从这里派生或显式映射；
5. **证据不丢失**：统一输出可以增加字段或原生产物引用，但不能为了统一而删除页码、bbox、表格、图片、OCR 和模型来源；
6. **先回归后扩展**：新增模型、图片和 Web 功能前，先为现有 MarkItDown、旧 Office 转换和 block 切分建立回归测试。

## 2. 范围

### 2.1 本期范围

- 直接基于当前工作区的 Python `document_parser` 扩展，不重写现有核心，不另起一套重复的 Rust 解析工程；
- 支持系统自动选择解析模型；
- 支持用户手动指定解析模型；
- 建立模型能力注册、路由原因和失败回退机制；
- 调研并测试 JPG、JPEG、PNG 的解析能力；
- 将不同解析器的原生结果统一为稳定的 `ParsedDocument`；
- 保留质量层需要的原生 JSON、Markdown、图片、表格、页码、bbox、OCR 置信度和运行来源；
- 建立解析后质量检查、安全优化、质量分级和重新解析建议；
- 建立独立后端 API 和 Web 前端；
- 建立路由、契约、质量、图片测评和端到端测试。

### 2.2 MVP 能力下限

本项目的 MVP 不是仅证明页面和 API 能够跑通，而是第一版就必须形成具备实际结构价值的解析闭环。

#### 路由能力下限

- 自动路由和用户手动指定均至少覆盖 `Docling`、`MinerU`、`OCR` 三条真实解析路径；
- 能够根据普通文档、复杂 PDF、扫描件和 JPG/JPEG/PNG 的特征在三条路径间选择；
- 路由必须提供选择原因、实际执行模型、fallback 和失败记录；
- 现有 MarkItDown 继续保留和回归，但不替代上述三条 MVP 路由要求。

#### 质量能力下限

- **表格**：恢复可证明的物理网格、合并关系和表头结构；对证据充分的表建立稳定字段绑定，至少包含 `binding_id`、`row_key`、`column_path`、`value` 和真实 `source_locator`；
- **标题**：利用解析器层级、顺序和来源证据恢复可确认的标题层级，建立稳定 `parent_child` 和章节作用域；无法唯一判断的标题不得强行恢复；
- **引用**：对具有明确编号或可验证标识的正文引用与参考文献建立 `reference_of` 关系，并保留推导依据和状态；
- **安全降级**：复杂表格绑定不唯一、标题层级不确定或引用目标不唯一时，必须生成 issue 并进入人工复核或重新解析，不能为达到“已绑定”数量而制造错误关系；
- **四件套**：每次质量处理均输出 `optimized.md`、`canonical_document.json`、`quality_report.json` 和 `package_manifest.json`。

#### 完整串联下限

朱负责将以下链路完整串联，并保证每层仍可独立测试：

```text
Web/CLI 上传
  → 自动或手动路由
  → Docling / MinerU / OCR Adapter
  → 原生产物归档
  → ParsedDocument 统一输出
  → 质量层表格/标题/引用处理
  → QualityPackage
  → Web 展示、下载和重新解析
```

### 2.3 共享开发文件集

三个人必须使用同一批带稳定 ID 和 SHA-256 的文件进行开发、联调和验收，不能分别寻找
互不相同的样例后只汇报各自结果。共享文件集用于同时验证路由选择、Adapter 真实执行、
统一输出和质量层处理。

#### 第一批文件规模

MVP 第一批共享开发文件至少包含 24 个唯一文件：

| 类别 | 最低数量 | 必须覆盖的特征 |
|---|---:|---|
| 普通文本型 PDF | 3 | 中文、英文、可复制文本层 |
| 复杂或扫描 PDF | 4 | 多栏、公式、纯扫描、图文混排 |
| 表格重点 PDF | 5 | 简单表、合并单元格、多级表头、跨页表、结构不确定反例 |
| 标题与引用重点 PDF | 4 | 多级标题、编号引用、参考文献、引用目标不唯一反例 |
| JPG/JPEG | 3 | 拍照、旋转或模糊、表格截图 |
| PNG | 3 | 透明背景、长截图、无文字图片 |
| Office/文本回归文件 | 2 | 从 DOC/DOCX/PPT/PPTX/XLSX/MD/TXT 中选择当前必须回归的格式 |

同一文件可以同时带多个能力标签，但不得用同一个物理文件重复计数。文件应优先选择
可公开、已授权或团队自行合成的材料，禁止把客户敏感文件、个人信息或无权再分发的文档
提交到公共 GitHub 仓库。

#### 分层使用

- **Smoke 子集**：从 24 个文件中固定 6 个，覆盖普通 PDF、复杂 PDF、扫描 PDF、表格、
  JPG、PNG；用于每次提交后的快速验证；
- **Development 全集**：全部 24 个文件；三个人日常开发和固定版本对比使用；
- **Golden 子集**：从全集中至少选择 8 个，由叶维护人工确认的表格、标题、引用或 OCR
  期望结果；必须同时包含确定正例和应安全降级的反例；
- **Acceptance 子集**：在文件集扩充后预留未参与规则调试的样例，用于 Gate C/D，防止
  只针对已知样例硬编码。

#### 文件清单

每个文件必须在 `manifest.jsonl` 中有一条记录，至少包含：


```text

├─ README.md
├─ manifest.jsonl
├─ files/                  # 小型、可公开或团队合成的样例
```

#### 三人对文件集的责任

- 张负责路由标签、候选模型、图片样例覆盖和逐模型能力结果；
- 朱负责确保每个可支持文件能够通过统一入口运行，并归档原生产物和

- 三人共同评审 manifest。新增、删除或替换共享文件必须通过 PR，不得只在个人电脑上

每次批量运行至少记录 `sample_id`、输入 SHA-256、路由决策、实际解析器及版本、解析状态、

从汇总中删除失败样例。

## 3. 用户场景与独立测试

### US-001：自动选择解析模型（P1）

用户上传文档并选择“自动”，系统根据格式、内容特征、模型能力和可用性选择解析模型，同时给出选择原因和备用模型。

**独立测试**：无需前端，直接向路由模块提交文档特征，验证其返回稳定的 `RoutingDecision`。

**验收场景**：

1. 给定一个普通文本型 PDF，当用户选择自动模式时，系统返回一个可用解析模型、选择原因和备用顺序；
2. 给定一个 JPG 或 PNG，当用户选择自动模式时，系统只从声明支持图片的模型中选择；
3. 给定所有候选模型均不可用的情况，系统返回明确错误，不伪造成功结果；
4. 路由结果必须记录建议模型，实际解析结果必须记录实际执行模型，两者不得混淆。

### US-002：用户指定解析模型（P1）

用户可以绕过自动路由，明确指定某个解析模型，便于对比和复现。

**独立测试**：通过后端、CLI 或 Python 调用指定 `parser_id`，验证系统调用指定模型。

**验收场景**：

1. 指定模型可用且支持输入格式时，系统调用该模型；
2. 指定模型不可用或不支持输入格式时，系统返回明确原因；
3. 手动指定模式下，未经用户允许不得静默切换模型；
4. 同一文件、同一模型、同一参数能够复现解析来源信息。

### US-003：统一不同模型输出（P1）

无论底层模型返回 Markdown、JSON、HTML 表格、图片目录还是坐标数组，上层都读取同一种结果协议，同时质量层仍能访问原生证据。

**独立测试**：使用固定的模型原生结果 fixture，不实际运行模型，验证每个归一化器均输出合法 `ParsedDocument`。

**验收场景**：

1. 原生 Markdown 被映射到统一正文和 block；
2. 原生图片、表格和附件被映射到统一 asset；
3. 原生页码、bbox、cell/span、OCR 置信度等证据被保留；
4. 模型无法提供的能力被明确标记为缺失，不使用虚假默认值；
5. 新增解析器不要求修改前端和质量层公共调用方式。

### US-004：解析质量检查与安全优化（P1）

系统对统一解析结果执行完整性、文本、结构、表格、图片、公式和来源检查，生成质量状态、问题、修复记录和重新解析建议。

**独立测试**：直接向质量层提交固定 `ParsedDocument` fixture，不启动路由、解析模型、后端或前端。

**验收场景**：

1. 内容完整且未命中阻断规则时，结果可以进入 `pass` 或 `pass_with_warnings`；
2. 证据不足但仍可人工判断时，结果进入 `manual_review_required`；
3. 原解析产物缺失关键事实且其他模型可能补足时，结果进入 `reparse_required` 并给出建议；
4. 违反硬约束或产物损坏时，结果进入 `rejected`；
5. 质量优化不得凭空创建原解析结果中不存在的数字、公式、表头或来源。

### US-005：Web 展示与结果获取（P1）

用户通过 Web 页面上传文件，选择自动或手动模型，查看任务状态、路由原因、统一解析结果、质量问题和产物，并可下载或重新解析。

**独立测试**：前端可以使用固定 API JSON 开发；后端可以在没有前端时通过 OpenAPI/HTTP 客户端测试。

**验收场景**：

1. 前端支持上传本期声明支持的文件；
2. 前端展示建议模型、实际模型、选择原因和耗时；
3. 前端展示 Markdown、blocks、assets、原生文件列表和质量报告；
4. `reparse_required` 状态提供明确的重新解析入口；
5. 用户可以下载单项产物或完整任务包。

### US-006：图片解析能力测评（P1）

团队使用统一 JPG/JPEG/PNG 数据集比较候选模型，为图片路由和质量门提供证据。

**独立测试**：测评脚本可以脱离 Web 前端运行，并生成机器可读结果和汇总报告。

**验收场景**：

1. 测试集覆盖中文、英文、扫描、拍照、旋转、模糊、表格截图、透明 PNG、长截图和无文字图片；
2. 报告至少记录成功/失败、非空率、耗时、OCR 文本、置信度和错误原因；
3. 图片路由规则必须引用测评结论或明确的能力声明；
4. 低质量图片不得因为返回非空文本而自动视为质量合格。

```text
quality/
tests/quality/
tests/fixtures/parsed_documents/
```

**职责边界**：质量层不负责执行模型路由，不直接依赖某个第三方解析器对象，不使用无来源推断替代解析事实。

## 6. 功能需求

### 6.1 路由与模型能力

- **FR-001**：系统必须同时支持自动路由和用户指定模型；
- **FR-002**：每次路由必须产生可记录的选择原因；
- **FR-003**：系统必须区分建议模型和实际执行模型；
- **FR-004**：系统必须对解析器格式支持和运行可用性进行检查；
- **FR-005**：自动 fallback 必须遵循显式规则，并记录前一次失败原因；
- **FR-006**：手动指定模式未经用户允许不得自动切换模型；
- **FR-007**：图片路由必须覆盖 `.jpg`、`.jpeg` 和 `.png`。
- **FR-040**：MVP 自动路由和手动指定必须实际支持 Docling、MinerU、OCR，不能只返回尚未接入的模型名称；
- **FR-041**：路由必须能够接收质量层的重新解析建议，并形成新的任务或解析版本。

### 6.2 统一接入与解耦

- **FR-008**：每个解析器必须实现统一 Adapter 接口；
- **FR-009**：每个 Adapter 必须可以脱离前端独立测试；
- **FR-010**：后端必须可以脱离前端独立启动和测试；
- **FR-011**：前端不得直接导入或调用解析算法代码；
- **FR-012**：新增解析器不得要求修改前端公共调用协议；
- **FR-013**：质量层不得直接依赖第三方解析器对象；
- **FR-014**：统一输出不得丢弃质量层已声明需要的原生证据；
- **FR-015**：缺失能力必须携带原因，不得用伪造值代替；
- **FR-016**：解析器执行必须有超时、错误和临时文件清理机制。
- **FR-035**：现有 `DocumentParserGateway.from_environment()`、`parse()`、`parse_file()`、`list_parsers()` 和 `close()` 的公开调用方式必须继续可用，除非通过明确的兼容层和 Schema 版本升级处理；
- **FR-036**：当前 MarkItDown 原生支持格式的解析能力必须建立回归测试，新增路由不得降低其原有可用性；
- **FR-037**：当前 `.doc → .docx`、`.ppt → .pptx` 转换能力必须保留，并继续记录格式转换耗时和转换器来源；
- **FR-038**：`ParsedDocument.schema_version` 已由 `2.1` 提升为 `2.2`；原有核心字段语义和顶层调用方式保持兼容，新增来源证据、表格、OCR、原生产物和能力声明字段使用默认值兼容旧调用；后续不兼容变更必须再次提升版本；
- **FR-039**：顶层包现有公开导入必须保留，新增模块不得要求现有调用方直接依赖第三方解析器对象。

### 6.3 质量层

- **FR-017**：质量层必须可以对固定 `ParsedDocument` 独立运行；
- **FR-018**：质量层必须输出 `pass`、`pass_with_warnings`、`manual_review_required`、`reparse_required` 或 `rejected`；
- **FR-019**：质量层必须保留 issue 的规则、严重级别、证据和建议动作；
- **FR-020**：质量优化必须记录 repair log；
- **FR-021**：安全 no-op 必须是合法结果；
- **FR-022**：质量层必须输出四件套及其哈希绑定；
- **FR-023**：质量层必须能够建议重新解析器或参数，但不得自行伪造解析事实；
- **FR-024**：图片质量检查必须覆盖可读性、OCR 置信度、bbox 合法性、文本覆盖和无文字图片场景。
- **FR-042**：质量层必须对解析器提供的表格 HTML、cells、span、表头和来源证据进行网格恢复，并对证据充分的表生成字段绑定；
- **FR-043**：每个表格字段绑定必须包含稳定 binding ID、行键、完整列路径、原始值和真实来源定位；
- **FR-044**：质量层必须恢复具有充分证据的标题层级和章节作用域，并以稳定 block ID 建立 `parent_child` 关系；
- **FR-045**：质量层必须对具有明确标识的正文引用和参考文献建立带状态与证据的 `reference_of` 关系；
- **FR-046**：表格、标题或引用关系无法唯一确定时必须安全降级，不得输出无证据的确定关系。

### 6.4 Web 与任务结果

- **FR-025**：Web 必须支持文件上传和自动/手动模型选择；
- **FR-026**：Web 必须展示路由原因、建议模型和实际模型；
- **FR-027**：Web 必须展示统一解析结果、原生产物清单和质量结果；
- **FR-028**：Web 必须允许下载单项产物和完整任务包；
- **FR-029**：Web 必须对 `manual_review_required`、`reparse_required` 和 `rejected` 做不同展示；
- **FR-030**：重新解析必须形成新的任务或版本，不得静默覆盖历史结果。

### 6.5 测评

- **FR-031**：路由、归一化和质量层必须各自具有独立 fixture 和测试；
- **FR-032**：图片测评必须生成逐文件结果和汇总结果；
- **FR-033**：测评不得仅使用“命令成功且非空”代表质量合格；
- **FR-034**：端到端测试必须覆盖自动路由、手动指定、解析失败、低质量、重新解析和产物下载。

### 6.6 共享开发文件集

- **FR-047**：三人必须基于同一份带版本、稳定 `sample_id` 和 SHA-256 的 manifest 开发和联调；
- **FR-048**：第一批共享文件不得少于 24 个唯一文件，并覆盖 PDF、JPG/JPEG、PNG 以及必要的 Office/文本回归格式；
- **FR-049**：共享文件集必须包含表格、标题、引用、扫描/OCR 的确定正例和安全降级反例；
- **FR-050**：每次批量运行必须保留全部成功、失败、跳过和模型不可用记录，不得只汇总成功样例；
- **FR-051**：大型或受限文件可以存放在共享存储或 Git LFS，但 manifest、哈希、授权/敏感级别和稳定访问方式必须版本化；
- **FR-052**：包含敏感信息或无再分发授权的文件不得进入公共仓库，日志和固定样例不得泄露其正文；
- **FR-053**：共享文件的新增、删除、替换、标注和 split 变化必须通过 PR，并同步影响说明。

## 7. 关键实体

- **ParseRequest**：用户或调用方提交的原始解析请求；
- **DocumentSignals**：扩展名、MIME、文本层、扫描比例、图片和布局复杂度等特征；
- **ParserCapability**：解析器支持格式、运行条件、优势、限制和可用性；
- **RoutingDecision**：自动或手动路由的模型、原因、参数和 fallback；
- **ParserNativeResult**：具体解析器产生的原生结果和产物清单；
- **ParsedDocument**：供质量层和前端读取的解析器无关统一结果；
- **QualityIssue**：带严重级别、证据、规则和建议动作的质量问题；
- **QualityPackage**：质量状态、优化结果、Canonical、报告和 Manifest 的集合；
- **ParseTask**：一次解析及其路由、执行、质量和产物版本记录。
- **SharedSample**：共享开发文件集中的一个稳定样例，以 `sample_id`、SHA-256、类别、标签、来源许可和 split 标识；
- **DatasetManifest**：共享文件集的机器可读版本清单，连接原文件、路由结果、统一结果、质量标注和批量运行记录。

## 8. 非功能要求

- **NFR-001 可追溯**：任一结果必须能定位到原文件、解析器、版本、参数和原生产物；
- **NFR-002 可复现**：同一输入、解析器版本和参数应能复现执行来源；
- **NFR-003 可测试**：路由、Adapter、归一化、质量层、后端和前端均可分层测试；
- **NFR-004 隔离性**：单文件解析失败不得锁死整个后端；
- **NFR-005 安全性**：资源路径必须防止绝对路径和父目录跳转；错误日志不得泄露正文和密钥；
- **NFR-006 兼容性**：公共协议的不兼容变更必须提升 Schema 版本；
- **NFR-007 幂等性**：相同固定输入的质量包重复生成时，除允许变化的时间/任务字段外应保持一致；
- **NFR-008 可观测**：记录路由、解析、统一转换、质量检查各阶段耗时和错误；
- **NFR-009 前后端分离**：正式交付必须通过 HTTP/JSON 边界连接前端与后端。

## 9. 成功标准

- **SC-001**：自动和手动两种模型选择路径均通过契约测试；
- **SC-002**：Docling、MinerU、OCR 三条真实解析路径均能够通过统一 Adapter 接口独立运行，并可由自动或手动路由调用；
- **SC-003**：JPG、JPEG、PNG 均进入图片测评和统一解析流程；
- **SC-004**：每个 `ParsedDocument` 都记录实际解析器、版本、参数、耗时和原生产物清单；
- **SC-005**：每个质量结果都生成合法状态、问题列表以及四件套或明确失败原因；
- **SC-006**：一个模型返回非空但低质量的图片样例不能被错误自动判为 `pass`；
- **SC-007**：能够分别演示单 Adapter、纯后端和完整 Web 三种运行方式；
- **SC-008**：前端通过 API 完成上传、选择模型、查看结果、查看质量状态、下载和重新解析闭环；
- **SC-009**：新增一个测试 Adapter 时，无需修改前端和质量层公共入口；
- **SC-010**：三人负责的模块均具有独立测试，端到端测试验证三个接口能够连续衔接。
- **SC-011**：现有 MarkItDown 直通解析、旧 Office 转换、顶层导入和 `parse_file()` 调用通过回归测试；
- **SC-012**：完整 Web、纯后端和单 Adapter 三种入口最终调用的是同一套工作区核心代码，不存在复制粘贴的平行解析实现。
- **SC-013**：至少一个含合并表头或多级表头的表格样例能够生成可回溯的字段绑定；语义不唯一的反例不得错误绑定；
- **SC-014**：至少一个多级标题样例能够恢复标题父子关系和章节作用域；不确定标题被明确标记而不是强行提升；
- **SC-015**：至少一个带编号引用和参考文献的样例能够建立可回溯的 `reference_of` 关系；
- **SC-016**：从 Web/CLI 输入到路由、三类 Adapter、统一结果、质量四件套、Web 展示及重新解析形成完整端到端闭环。
- **SC-017**：共享开发文件集至少包含 24 个唯一文件，manifest 字段完整且所有 SHA-256 可校验；
- **SC-018**：张、朱、叶能够使用同一 manifest commit 分别完成路由、统一解析和质量处理，并通过 `sample_id` 对齐结果；
- **SC-019**：Golden 子集至少包含 8 个有人工期望的样例，并同时验证确定关系和应安全降级的反例；
- **SC-020**：批量报告中的输入总数等于成功、失败、跳过和不可用数量之和，不存在静默丢失样例。

## 12. 假设

- GitHub `main` 是唯一共享开发基线，个人分支必须通过 PR 合并；
- 本仓库只保存基础代码、公共协议和可复现开发材料；个人本地调研目录不属于代码交付；
- 首期 Web 用于内部展示和测试，不包含账号、权限和互联网公开部署；
- 模型运行环境可能分布在不同机器，统一接口必须允许本地进程或服务适配；
- 不同解析器允许能力不同，统一的是调用和结果协议，不是质量结论。

## 13. 已确认的 MVP 决策

1. 路由第一版必须覆盖 Docling、MinerU、OCR，并同时支持自动选择和用户指定；
2. 现有 MarkItDown 继续兼容和回归，但不能代替三条核心路由；
3. 质量层第一版必须完成有证据的表格网格与字段绑定、标题层级恢复和编号引用关系绑定；
4. 表格、标题和引用证据不足时必须安全降级，不将“尽量恢复”解释为“强制恢复”；
5. 朱负责从前端/CLI到路由、解析、统一、质量、展示、下载和重新解析的完整工程串联；
6. 三层模块仍必须支持脱离完整 Web 独立测试。
