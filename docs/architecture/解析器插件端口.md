# 解析器插件端口

## 目的

`parsers/ports.py` 是解析器插件与组合根之间的最小稳定边界。它只依赖公共文档契约，不能导入路由、Gateway、质量层、存储或任何具体解析器。

```text
插件实例 ── probe() ──> ParserCapability snapshot ──> routing
    │
    ├── execute() ──> ParserNativeResult
    ├── normalize_native() ──> ParserNormalizationBundle / ParsedDocument
    └── diagnose() ──> ParserExecutionError
```

路由层只接收由组合根收集的 `ParserCapability` 快照，绝不持有插件实例。Gateway/编排器负责把路由决策和插件实例组合起来；质量层只接收统一的 `ParsedDocument`。

## 四个端口

| 端口 | 输入 | 输出 | 禁止职责 |
|---|---|---|---|
| `probe` | 可选 `ParseRequest`、`DocumentSignals` | `ParserProbeResult` | 不启动第三方后端、不解析文件、不读取路由策略 |
| `execute` | `ParseRequest`、`DocumentSignals` | `ParserNativeResult` | 不构造质量结论、不修改质量包 |
| `normalize_native` | `ParserNativeResult`、`NormalizationContext` | `ParserNormalizationBundle` | 不选择模型、不访问 Gateway 或存储 |
| `diagnose` | 底层异常及可选请求上下文 | `ParserExecutionError` | 不向 API/审计记录泄露原始 stderr、Token、URL 或堆栈 |

`parse()`、`normalize()`、`build_native_result()` 是兼容入口；新的集成应优先使用四个端口中的明确阶段。

## 错误契约

`ParserExecutionError` 必须包含：

- `parser_id`：稳定插件 ID；
- `failure_kind`：`transient`、`policy`、`unsupported`、`unavailable`、`normalization` 或 `parser`；
- `retryable`：是否可重试；
- `safe_message`：可写入 API、任务状态和 fallback 历史的脱敏说明。

异常链仍保留原始异常，供受控日志使用；`safe_message` 不能复制第三方服务错误、CLI stderr、凭据或临时路径。Gateway fallback 和任务编排可直接消费 `failure_kind` / `retryable`，而不需要导入具体插件。

## 已接入插件

| 插件 | Probe | Execute 失败行为 | Normalize | 原生产物 |
|---|---|---|---|---|
| MarkItDown | 包安装和格式能力 | 不可用、格式不支持、转换失败均抛 typed error | Markdown → 统一证据包 | `native/full.md` |
| Docling | `docling` 安装状态 | 已实际调用后失败抛 typed error，不再回退为 placeholder | 原生 JSON/HTML/Markdown → 统一证据包 | JSON、HTML、Markdown |
| AnyDoc | 可执行文件状态 | CLI 非零退出或空输出抛 typed error | 原生目录/sidecar → 统一证据包 | sidecar 目录内容 |
| MinerU | 服务端配置和运行时能力 | 云端、CLI、magic-pdf 的实际失败抛 typed error | MinerU 原生产物 → 统一证据包 | Markdown、结构化 JSON、图片 |
| OCR | RapidOCR 安装和图片格式能力 | 不支持的 PDF/格式、缺依赖或实际 OCR 失败抛 typed error | OCR span → 统一证据包 | `ocr_result.json`、Markdown |

OCR 当前只声明并实际执行 JPG/JPEG/PNG。PDF OCR 由支持 PDF 的 Docling/MinerU 路径承担；若直接对 OCR 执行 PDF，会获得 `failure_kind="unsupported"`，不会产生空 placeholder 成功结果。

## Native sidecar 联调

原生产物 sidecar 是离线归一化入口，优先于实时后端探测。这样即使本地没有相应 SDK/可执行文件，已经采集的 Markdown、HTML、JSON、图片和其他 native files 仍可经 `normalize_native` 转换为可验证的文档证据包。

sidecar 只能由受信 worker、测试夹具或服务端存储注入；请求级高风险路径、令牌和远端地址仍由各解析器的安全边界控制。

## 新增插件清单

1. 在插件内部实现四个端口，并在 `probe()` 返回真实、可复制的能力声明。
2. `execute()` 只产生 `ParserNativeResult` 和 native sidecar，任何实际后端失败抛 `ParserExecutionError`。
3. `normalize_native()` 使用 `NormalizationContext`，生成 blocks、表格、能力声明、来源证据和渲染 Markdown。
4. 通过 `parsers.registry.build_capability_snapshot()` 暴露给组合根；不要让 routing 导入插件。
5. 提供 probe、失败分类、sidecar、normalize、Gateway fallback 的契约回归。
