# P1 实施进度与接口契约

> 状态：当前工作树实现快照（2026-08-26）
> 目的：说明已落盘的 P1 能力、可调用契约和模块边界；它不是权限、合规或生产上线声明。
> 关联但不修改：[文档解析工作台产品化实施清单](../product/文档解析工作台产品化实施清单.md)。

## 1. 结论与范围

当前 P1 已具备从“提交任务”到“质量门禁交付”的基础闭环：可恢复的异步任务、安全 retry/reparse、能力快照驱动的浏览器预检、质量层四件套预览与交付门禁、只读谱系/同源比较，以及可独立调用的重解析推荐领域能力。

以下“已实现”仅表示代码和针对性测试已存在；它**不**表示具备用户身份、租户隔离、审批或数据留存能力。尤其是业务交付的质量门禁不能替代认证和 RBAC。

## 2. 已实现能力

### 2.1 安全任务生命周期、retry 与 reparse

- `ParseJob` 保存持久化状态、attempt、event、错误分类、`retryable`、不可变 source 身份、`parent_parse_id` 和 CAS 控制版本号。
- 应用 lifespan 会恢复仍处于 queued 的任务；若质量包已完整发布则恢复其终态，否则把中途中断任务标为可安全 retry 的失败。关闭时停止进程内队列，避免把未知的半途执行当作可直接重放。
- 异步任务控制面已使用显式 `PublicParseJob` 白名单 DTO，而不是直接序列化 durable `ParseJob`：只暴露安全 ID、`source_extension`、受限 parser/options 形状、状态/attempt/质量/失败摘要和时间戳；不暴露文件名、source digest、内部路径、任意 option、原始 event message 或参数映射。
- `POST /api/jobs` 以 `Idempotency-Key` 创建异步任务；同一 key 与相同请求返回既有任务，不同请求返回冲突。
- `POST /api/jobs/{parse_id}/retry` 仅允许可重试的失败任务创建 child job。`policy`、`unsupported`、`integrity` 等禁止重试；重放同一个幂等 key 不会重复入队。
- `POST /api/parses/{parse_id}/reparse` 从已验证的 durable source 创建新的 child job，可指定新的 parser/options；父任务和已发布结果保持不变。
- retry child 继承父任务的 source、请求 parser 和 options；reparse child 继承 source，但使用此次 reparse 的显式 parser/options。
- 创建 child job 时会保留 source SHA-256、文件类型和大小的同源身份，并记录 `parent_parse_id`。这不是就地覆盖，也不是业务文档 revision 的替换。

### 2.2 能力快照与浏览器预检

- `GET /api/parsers` 返回当前注入的 `ParserCapability` 快照，包括 `parser_id`、支持格式、可用性、不可用原因和是否需要网络。
- 前端在选择文件后按扩展名、解析器可用性与格式支持禁用不可手动选择的选项；空文件直接阻止提交；无扩展名和超过 50 MB 仅提示，最终仍由服务端校验。
- 前端不展示或允许用户伪造服务器事实（例如 `libreoffice_available`）。
- 创建、reparse、retry 都生成稳定 `Idempotency-Key`；网络重试复用同一 key。
- reparse 前端只从**当前浏览器会话中由本页创建的任务**保存的白名单快照继承 `route_profile`、`allow_cloud`；URL 恢复、历史任务或缺失快照时以安全空值重新提交，不读取服务端 job 的任意原始 option。这两个字段仍只是请求偏好，不能提升服务端云端授权。

当前没有单独的 `/api/preflight` HTTP 端点；“预检”由 capability snapshot + 浏览器轻量检查组成，服务端在任务创建和路由阶段再次作最终校验。

### 2.3 默认质量预览与 delivery gate

- 质量层发布四件套：`optimized.md`、`canonical_document.json`、`quality_report.json`、`package_manifest.json`；manifest 绑定前三项哈希。
- 前端默认请求并渲染已发布的 `optimized.md`，不以原始 `ParsedDocument.markdown` 作为静默回退预览。
- `GET /api/parses/{parse_id}/delivery` 在下载前校验四件套与 manifest，并且 ZIP 仅包含四件套，不含 source、native、`parsed_document.json` 或诊断日志。
- 质量状态为 `pass`、`pass_with_warnings` 时可下载业务交付包；`manual_review_required`、`reparse_required` 返回 409；`rejected` 返回 403；完整性校验失败返回 409。
- `GET /api/parses/{parse_id}/download` 是诊断包下载，和业务交付 ZIP 是两个不同入口，前端也分别标注用途。

`/delivery` 只解决“质量状态是否可交付”和四件套完整性，**不**执行身份、租户、审批或授权判断。

### 2.4 只读谱系与同源比较

- `GET /api/jobs/{parse_id}/lineage` 沿 `parent_parse_id` 逐级读取父任务并返回 root-to-target 控制面投影；不枚举整库。
- 谱系遍历上限为 64；缺父任务、循环、深度上限或 source identity 不一致会以 `lineage_complete=false` 和 `lineage_integrity` 安全标识返回，不把异常父节点混入结果。
- `GET /api/jobs/compare?left=<parse_id>&right=<parse_id>` 只允许比较同一不可变 source identity（SHA-256、文件大小、文件类型均相同）的任务；不同来源返回 409。
- 响应仅含安全 parser/options 形状、attempt/quality/失败状态、耗时、可安全读取的结构计数和差异；不返回 source 内容、文件名、source SHA-256、`package_path`、option 值或秘密类 option key。
- `cas_revision` 是持久化 CAS 计数，明确不是面向用户的业务文档版本号。

### 2.5 纯重解析推荐与编排 adapter

已提供 `GET /api/jobs/{parse_id}/reparse-recommendations` 只读 HTTP API，以及前端的安全展示与“采用建议”选择 CTA。成功结果、失败任务和终态但结果暂不可读取的任务都会进入同一个独立 reparse action 区；不会伪造结果或产物。CTA 只预填重新解析方式，自动创建 reparse child 与受身份授权集成仍未实现。纯领域能力仍可独立集成。

- `routing.recommendations.recommend_reparse(...)` 输入轻量 `ReparseContext`、`ParserCapability` snapshot、质量/失败 `ReparseSignal` 与有效策略，输出稳定排序候选和可选自动方案。
- 每个候选包含 `parser_id`、`reason`、`executable`、`replaces_current_parser`、`requires_cloud`、`auto_options`、`blockers`；自动方案只能来自 `executable=true` 候选。
- 不支持格式、当前不可用、有效策略未允许、已尝试且策略禁止重复、或云端未被有效策略允许的候选不会成为可执行或自动推荐。
- 规则没有 MinerU 专用分支；parser 偏好和 parser options 由 `ReparseRecommendationPolicy` 显式注入。
- `composition.reparse_recommendations.recommend_reparse_for_job(...)` 将 `ParseJob` 的文件名、请求/实际尝试 parser、`quality_state`、`failure_kind`、`retryable` 适配为领域输入；不会读取原始错误详情，也不会把 `job.options.allow_cloud` 当作授权。
- 仅当质量状态为 `reparse_required` 或出现可行动的 parser 失败时才产生推荐；无信号返回 `None`。默认 policy 为云端拒绝。
- HTTP API 对无可行动信号返回 `{"parse_id": "...", "recommendations": null}`；对已评估结果仅投影 signal `source`/`code`/`retryable`、候选 `parser_id`/执行事实与自动方案 parser，不返回 `reason`、`auto_options`、原始错误、路径、source digest 或正文。
- 因当前没有 `Principal` 或 `CloudExecutionGrant`，HTTP endpoint 强制使用云端拒绝策略；不会读取历史 `job.options.allow_cloud` 或部署开关来放宽推荐。
- 前端在成功结果、失败任务和终态结果读取失败时请求该只读 API，并以 `AbortController` 和任务上下文防止旧任务响应串入；仅以本地映射展示 signal/candidate 的安全字段。失败/不可读结果使用独立 action 容器，结果区与产物区仍保持隐藏。
- “采用建议”仅在可执行、非云端的自动方案存在时预填重新解析下拉框；不会自动选择、不会提交请求，用户仍须显式点击“重新解析”创建 child job。

## 3. 公开接口契约

### 3.1 HTTP 接口

| 接口 | 用途 | 核心语义 / 返回 |
| --- | --- | --- |
| `GET /api/parsers` | 获取能力快照 | 返回 `ParserCapability[]`；供 UI 预检，不能当作服务端最终授权。 |
| `POST /api/jobs` | 创建异步任务 | multipart 上传；支持 `parser_id`、`options_json`、`Idempotency-Key`；返回 202、`status_url` 和安全任务 DTO。 |
| `GET /api/jobs/{parse_id}` | 查询任务状态 | 返回 `PublicParseJob` 白名单投影：安全 ID、`source_extension`、受限偏好、状态/attempt/质量/失败摘要与时间戳。 |
| `GET /api/jobs/{parse_id}/events` | 查询任务事件 | 返回白名单 attempt/event 时间线与通用失败摘要；不返回原始 message、参数或 metrics。 |
| `GET /api/jobs/{parse_id}/reparse-recommendations` | 读取只读重解析建议 | 无信号时 `recommendations=null`；仅返回内容无关的候选执行事实；当前强制云端拒绝，不创建任务。 |
| `DELETE /api/jobs/{parse_id}` | 取消可取消任务 | 仅 queued/preflight 阶段可取消；不是数据删除。 |
| `POST /api/jobs/{parse_id}/retry` | 创建 retry child | 只允许 retryable failure；支持 `Idempotency-Key`，不修改父任务。 |
| `POST /api/parses/{parse_id}/reparse` | 创建 reparse child | 从 durable source 创建新任务；请求体为 `parser_id` + `options`，支持 `Idempotency-Key`。 |
| `GET /api/parses/{parse_id}` | 读取统一解析结果 | 返回 `ParsedDocument`；用于技术/诊断视图。 |
| `GET /api/parses/{parse_id}/quality-package` | 读取质量包 | 返回 `QualityPackage`；用于质量展示与诊断。 |
| `GET /api/parses/{parse_id}/artifacts` | 列出已验证产物 | 清单校验失败时阻断。 |
| `GET /api/parses/{parse_id}/download` | 下载诊断包 | manifest 白名单 ZIP；不等同业务交付。 |
| `GET /api/parses/{parse_id}/delivery` | 下载业务交付包 | 仅质量可交付状态；仅四件套；失败状态按 409/403 阻断。 |
| `GET /api/jobs/{parse_id}/lineage` | 读取谱系 | 内容无关、只读、受深度和同源一致性保护。 |
| `GET /api/jobs/compare?left=&right=` | 同源任务比较 | 不同不可变 source identity 返回 409；不返回正文或 source digest。 |

`POST /api/parses` 为兼容同步入口；新页面应使用 `POST /api/jobs` + 状态查询。

`PublicParseJob` 的 `source_extension` 是规范化后的后缀，仅用于浏览器能力预检；它不等同于文件名或 source identity。任务 DTO 中的 `options` 只允许 `route_profile`、`allow_cloud` 两项公开偏好；错误文本由 `failure_kind` 映射为通用摘要，`error_reference` 仅允许安全枚举或派生的 `failure-*` 码。

### 3.2 Python 领域接口

```python
from document_parser.routing import (
    ReparseContext,
    ReparseRecommendationPolicy,
    ReparseSignal,
    recommend_reparse,
)

recommendations = recommend_reparse(
    context,
    capability_snapshot,
    signals,
    ReparseRecommendationPolicy(allow_cloud=False),
)
```

```python
from document_parser.composition import recommend_reparse_for_job

recommendations_or_none = recommend_reparse_for_job(
    job,
    capability_snapshot,
    policy=effective_policy,
)
```

调用方必须把 `effective_policy` 解析为服务器/租户/同意规则已收紧后的结果；不得把 HTTP 请求、`job.options` 或浏览器勾选直接视为云端授权。当前 adapter 未执行任何 HTTP、存储或质量包读取。

谱系与比较的纯投影入口位于 `backend.lineage`：`resolve_lineage`、`build_lineage_snapshot`、`build_same_source_comparison`、`same_source_identity`。它们只接收已加载的 `ParseJob`（以及可选结构计数），不直接访问存储。

重解析建议的安全 HTTP 投影入口位于 `backend.reparse_recommendations`：`cloud_denied_reparse_policy`、`public_reparse_recommendations`。它只做领域结果的内容无关投影，不提供执行授权，也不读取请求 option 作为云端同意。

## 4. 模块依赖与解耦边界

```text
Parser plugins ──> ParserCapability snapshot ──> routing
       │                                           │
       └──> ParsedDocument ──> quality ──> 四件套 ─┴──> orchestration
                                                        │
ParseJob + capability snapshot ─> composition.reparse_recommendations ─> routing.recommendations
                                                        │
backend (HTTP / storage / delivery / lineage endpoints) ──> frontend (HTTP only)
```

| 模块 | 可以依赖 | 不应依赖 / 不做 |
| --- | --- | --- |
| `parsers` | 公共 contracts、各自原生运行时 | 不调用质量、前端、存储或 FastAPI。 |
| `routing` | `ParserCapability` 快照、路由设置 | 不构造 parser 实现；`routing.recommendations` 不依赖 parser/quality/backend。 |
| `quality` | 固定 `ParsedDocument` | 可独立运行；不选择 parser、不发起 reparse、不使用 Agent/LLM 作为确定性门禁裁判。 |
| `orchestration` | parsing gateway、repository、quality runner 的端口 | 负责任务状态和发布，不依赖 routing 的建议模型。 |
| `composition` | routing、parser registry、ParseJob 适配器 | 负责把具体实现接到稳定 contracts/ports；不承载 HTTP。 |\n| `backend` | composition root、storage、公开 contracts | 负责 HTTP、持久化边界、DTO 脱敏和交付门禁；不把内部 package path、source identity 或原始任务诊断暴露给 public job。 |
| `frontend` | 后端 HTTP 契约 | 不直连 parser、quality、云服务或文件系统。 |
| `backend.lineage` | 已加载任务、可选安全结构计数 | 只读投影；不读取正文、不遍历整库、不执行任务。 |

## 5. 安全与状态语义

- 云端默认关闭；`RoutingSettings.allow_cloud` 与解析器执行边界共同约束执行。客户端的 `allow_cloud` 最多是请求偏好，不能打开服务端已关闭的云端路径。
- 若未来接入“等待云端同意”，应由独立的 `CloudExecutionGrant` 领域对象和服务端策略判定；不得复用当前 boolean option 充当同意记录。
- `needs_review` 仍是任务控制状态；必须同时查看 `quality_state` 才能知道是人工复核、建议重解析还是拒绝。
- `reparse`、`retry`、谱系和比较都使用 child job 保留历史；CAS `revision` 不是面向下游交付的 revision。
- 任务状态、取消和事件接口使用白名单 DTO；这降低路径、文件名、原始 option 和原始诊断泄露面，但它**不是**认证、租户隔离或访问授权。
- 业务交付与诊断下载分离，但目前接口还没有身份授权边界，不能据此宣称已完成数据隔离。

## 6. 明确未实现（不得标记为完成）

下列对象和流程当前**没有**完整领域模型、持久化、HTTP 授权流程或 UI 工作台，因此不得在验收、产品页面或对外说明中称为“已完成”。

| 未实现项 | 当前缺口 |
| --- | --- |
| `Principal` / 身份认证 | 没有认证提供商接入、会话/服务账号 principal、身份上下文或接口鉴权。 |
| 租户模型与 RBAC | 没有 `tenant_id`/角色授权边界；知道 `parse_id` 的请求目前不能依赖租户隔离。 |
| `CloudExecutionGrant` | 没有按 job/revision/provider/region/文案版本记录的同意凭据；`allow_cloud` 不是 grant。 |
| `ReviewCase` / `ReviewDecision` | 没有复核队列、领取/转派、批准/拒绝/例外放行、双人复核或审批审计。`needs_review` 仅表示需要进一步处理。 |
| Retention / 删除 / legal hold | 没有 source/native/quality/delivery 的分级保留期、真实删除工作流、冻结或合规审计。取消任务不等于删除数据。 |
| 下游交付账号 / webhook | 没有面向 LLMwiki 的受限服务账号、revision 令牌、撤销或推送审计。 |
| 推荐自动执行 / 受身份授权集成 | 前端已在成功、失败和结果不可读终态安全展示并手动采用推荐；不会自动创建 reparse child，且仍没有基于 `Principal` / `CloudExecutionGrant` 的执行授权。 |

1. 先确认身份提供商、Principal、租户和角色模型，再把现有读取/下载/谱系端点置于授权边界之后。
2. 定义并持久化 `CloudExecutionGrant`，将 provider/region/数据范围/同意文案与具体 job/revision 绑定。
