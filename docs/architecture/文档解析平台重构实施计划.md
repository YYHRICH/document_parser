# 文档解析平台重构实施计划

> 状态：已完成（2026-08-26；代码、回归、打包及真实解析器端到端均已验证）  
> 范围：解析平台整体架构；保留已完成的质量层 P0～P5 成果。  
> 原则：质量层继续只消费 `ParsedDocument`，不引入 Agent/LLM 参与解析或质量修复。

## 1. 目标与边界

### 1.1 目标

将当前“同步 API 调用解析器并立即运行质量层”的 MVP 链路，演进为可控、可恢复、可审计的文档处理平台：

```text
                         contracts / ports / pure utilities
                                        ↑
       ┌───────────────┬────────────────┼────────────────┬───────────────┐
       │               │                │                │               │
   路由层          统一归一化层      质量层          解析器执行器       存储适配器
 RoutingDecision   ParsedDocument   QualityPackage   NativeResult       ArtifactStore
       │               │                │                │               │
       └───────────────┴────────────────┴────────────────┴───────────────┘
                                        ↑
                 编排器 / Gateway（唯一的组合根，可选）
                                        ↑
                 API / CLI / Worker（交付与展示层）
```

完成后，路由层、统一归一化层和质量层都可在没有其他两个模块的情况下独立运行、测试和发布；解析器可以独立扩展，质量层无需感知解析器私有格式；失败任务可以追踪、重试和复现；重新解析不会覆盖历史结果。统一输出不再只是一个通用 Markdown 文件，而是同时承载语义结构、来源证据、能力声明和可渲染文本的版本化交换包。

### 1.2 明确不做

- 不重写 `ParsedDocument 2.2 → QualityPackage 1.0` 的质量层主边界。
- 不在质量修复、路由或解析流程中接入 Agent、LLM 或不确定性自动决策。
- 不让前端直接调用解析器、云服务或质量层。
- 不在不同解析器输出之间静默混合内容；一次文档版本只对应一次明确的解析尝试。

## 2. 目标领域模型

| 对象 | 含义 | 不可变性 |
|---|---|---|
| `SourceDocument` | 原始文件、来源元数据和 SHA-256 | 是 |
| `ParseJob` | 用户请求的处理任务及状态机 | 状态可变，历史保留 |
| `ParseAttempt` | 某个解析器的一次真实执行 | 是 |
| `DocumentRevision` | 一次成功归一化后的 `ParsedDocument` | 是 |
| `QualityRun` | 某个 `DocumentRevision` 的质量运行结果 | 是 |
| `ArtifactManifest` | 每个产物的路径、类型、大小、哈希和来源 | 是 |

关系如下：

```text
SourceDocument
  └─ ParseJob
       ├─ ParseAttempt #1（主解析器，失败）
       ├─ ParseAttempt #2（fallback，成功）
       │    └─ DocumentRevision #1
       │         └─ QualityRun #1
       └─ ParseAttempt #3（用户重解析）
            └─ DocumentRevision #2
                 └─ QualityRun #2
```

`reparse` 必须创建新的 `ParseJob` 或新的尝试链，不能写回覆盖旧的 `DocumentRevision`、质量包或原生产物。

## 3. 统一输出协议与质量层联合设计

### 3.1 定位：统一“文档证据包”，不是统一一份 Markdown

不同解析模型的最终交付应当是同一种**逻辑文档证据包**。`ParsedDocument` 是包的主协议和质量层唯一业务输入；Markdown 只是由同一语义结构渲染出来的可读视图，不能成为唯一事实来源。

```text
解析器原始结果
  → Normalize
  → Document Evidence Package
       ├─ semantic document：blocks、tables、relations、assets
       ├─ source evidence：page、bbox、原文片段、原生对象、置信度
       ├─ capability matrix：哪些证据真实存在、精度和缺失原因
       ├─ rendered Markdown：从 semantic document 导出的阅读视图
       └─ artifact manifest：所有文件的哈希、来源和版本
  → Quality Layer
       ├─ 按规则声明需要的证据能力
       ├─ 产生 issue / repair proposal / gate
       └─ 输出派生的 QualityPackage，不改写输入包
```

物理落盘可采用一个标准 document package，至少包含：

```text
document-package/
  parsed_document.json     # 主输入：结构化语义 + 稳定 ID + provenance
  document.md              # 可读投影；必须能由主输入再生成
  assets/                  # 被文档引用的受控资源
  native/                  # 解析器原生产物，仅供追溯和人工复核
  manifest.json            # 文件哈希、大小、媒体类型、来源 attempt/revision
```

质量层的 `canonical_document`、`optimized_markdown`、质量报告和修复审计应作为同一 revision 的**派生产物**交付，不能反向成为解析器或归一化器的输入。

### 3.2 语义核心、证据层与渲染层

统一协议需分为三个清晰层次，并定义单一事实来源：

| 层次 | 必须内容 | 谁写入 | 质量层如何使用 |
|---|---|---|---|
| 语义核心 | `document_id`、版本、block tree、表格 cells、资源、关系、稳定 ID | Normalize | 规则定位与修复目标的唯一依据 |
| 证据层 | source anchors、页码/bbox、原文片段、confidence、native artifact 引用、冲突记录 | Normalize | 判断规则是否可执行、结论置信度与人工复核 |
| 渲染层 | Markdown、HTML 等阅读表示 | Renderer | 展示和受证据约束的精确修复，不单独推断事实 |

具体约束：

- 每个 `block`、`table`、`asset`、`relation` 都要有稳定 ID；修复目标使用 ID、字段路径和执行前哈希，不能依赖全篇文本搜索。
- 表格保留结构化 cells、行列/span、来源 HTML/原生表示与渲染 Markdown；存在冲突时并存记录，由确定性 resolver 决策或交人工复核。
- 任一渲染片段都必须能回溯到 block/table ID；同一 revision 中，`document.md` 与语义核心不一致时以语义核心为准并产生契约错误。
- 缺页码、坐标、置信度或表格单元格时，显式在 capability matrix 中说明范围和原因；质量规则只能降级或跳过，不得从 Markdown 猜造证据。
- 质量层产生的修复只生成新的工作文档和审计记录；输入 `ParsedDocument` 始终只读。

### 3.3 质量层参与协议设计的方式

质量层不为某个 parser 定制字段，但必须拥有协议需求的共同决策权。新增或修改统一字段时，按以下流程执行：

1. 质量层维护 `QualityEvidenceRequirements`：每条规则/修复声明所需的语义字段、证据字段、最小精度和缺失时的降级行为。
2. 归一化层维护 `CapabilityDeclaration`：每个 parser/revision 声明已提供、部分提供或不可提供的证据及原因。
3. 执行前建立 capability matrix；规则根据矩阵得到 `pass`、`fail`、`warning`、`not_applicable` 或 `needs_review`，不能将“未知”误判为“通过”。
4. 协议字段、枚举、ID 规则或语义变更必须先提交 schema migration、parser fixtures 与 quality fixtures，并同时通过契约测试。
5. `ParsedDocument 2.2` 保持当前兼容入口；需要破坏性语义调整时发布新 schema version 和显式 migration，禁止静默复用字段含义。

### 3.4 联合验收基线

每个 parser 的固定样本都必须同时验证：

- 能通过 `ParsedDocument` schema 和 manifest 完整性校验；
- block/table/asset/relation 引用不悬空，稳定 ID 可重复生成；
- Markdown 从语义核心重渲染后语义等价；
- capability matrix 与真实产物一致，缺失证据不会被伪装为默认值；
- 质量层在该 capability matrix 下得到预期的 rule status、repair proposal 和 gate；
- 质量修复后的目标能通过 precondition、replay、rollback 与 no-op verifier 复检。

## 4. 路由、统一归一化与质量层的解耦设计

### 4.1 三个模块的独立职责

| 模块 | 唯一职责 | 最小输入 | 唯一输出 | 禁止依赖 |
|---|---|---|---|---|
| 路由层 `routing` | 根据文件信号、能力和策略生成执行计划 | `DocumentSignals`、`ParserCapability`、`RoutePolicy` | `RoutingDecision` | 解析器实现、Normalizer、质量层、Gateway、Backend、存储 |
| 统一归一化层 `normalization` | 原生产物转换为可验证的文档证据包 | `NativeParseResult`、`NormalizationContext` | `ParsedDocument` + manifest/capability | 路由策略、质量规则、Gateway、Backend |
| 质量层 `quality` | 运行确定性检查、修复、门禁与质量报告 | `ParsedDocument`、质量配置 | `QualityPackage` | 路由、Parser、Normalizer、Gateway、Backend、文件系统目录 |

因此，下列调用必须始终合法：

```python
# 不需要解析器、归一化器或质量层。
decision = router.route(signals, registry, policy)

# 不需要路由、解析器、Gateway 或文件包；可直接用于 fixture / CLI / 其他系统。
quality_package = run_quality(parsed_document)

# 不需要路由或质量层；用于离线原生产物导入或 adapter contract test。
parsed_document = normalizer.normalize(native_result, context)
```

### 4.2 依赖方向与组合根

三个模块只能依赖稳定的下层抽象，绝不能相互横向导入。`Gateway` 不再被视为核心业务模块，而是唯一允许装配路由、执行器、归一化、质量层和存储实现的**组合根**。

```text
contracts/                 # Pydantic 协议、枚举、schema version；不得导入业务模块
ports/                     # 小而稳定的协议：ParserRegistry、ParserExecutor、ArtifactStore、JobRepository
common/                    # 无业务状态的纯函数：哈希、稳定 ID、路径校验、原子写入、时间/错误基础类型

routing/     → contracts, ports, common
normalization/ → contracts, ports, common
quality/     → contracts, common, quality 自己的 rules/repairs
composition/（Gateway） → routing, normalization, quality, ports
backend/cli/worker → orchestration, ports
```

允许的是“上层通过依赖注入调用下层接口”；不允许的是下层为了方便导入上层实现。举例：质量层只接收 `ParsedDocument` 对象，绝不读取 `ApiStorage` 路径；路由层只读取 capability snapshot，绝不实例化 MinerU、Docling 或 OCR parser。

### 4.3 公共代码的抽取规则

公共代码应按稳定职责抽取，而不是建立无限增长的 `utils.py`：

- `contracts`：跨模块数据模型、schema 迁移、稳定错误码；这里不放业务流程。
- `common.ids`、`common.hashing`、`common.paths`、`common.atomic_io`：无领域策略、可纯函数测试的基础能力。
- `ports`：仅定义跨边界所需的小接口；接口由调用方的真实需求驱动，不能提前做“大而全服务层”。
- 每个模块内部的规则、渲染、证据解析、策略和错误映射仍留在该模块，不能因为被两个文件复用就过早下沉。

抽取前必须满足至少一个条件：多个模块需要同一语义、实现不依赖模块内部状态、并且能够独立测试。否则保留在所属模块，避免“公共层”反向成为新的耦合中心。

### 4.4 强制验收

- 三个模块各自拥有独立入口、独立 fixture 和独立 CLI/smoke test。
- 删除或替换任一个模块的具体实现后，其余两个的 import、单元测试和核心调用仍可运行。
- 架构测试禁止 `routing`、`normalization`、`quality` 相互导入，也禁止它们导入 `composition.gateway`、`backend`、具体 parser 或存储实现。
- 所有跨模块调用只能使用 `contracts` 数据对象或 `ports` 接口；不得传递 framework request、数据库 session、文件系统路径或解析器私有对象。
- `Gateway`/编排器的集成测试验证模块协作；三个模块的单元与契约测试不启动 Gateway。

## 5. 核心设计原则

1. **策略与执行分离**：路由只生成受策略约束的执行计划；编排器负责实际尝试、fallback、重试和审计。
2. **统一证据协议优先**：解析器交付的不是孤立 Markdown，而是以 `ParsedDocument` 为核心的版本化文档包；质量层仅消费其语义、证据与 capability，缺失证据必须声明，不能补造。
3. **不可信输入最小化**：请求只能表达用户偏好，云端地址、Token、输出目录、超时和资源上限只能由服务端配置。
4. **产物不可变且可校验**：源文件、原生产物、归一化文档和质量包均有哈希、来源和版本关联。
5. **失败是可管理状态**：解析失败需要错误分类、是否可重试、下一候选解析器和完整 attempt 历史。
6. **本地与云端隔离**：本地执行器和云端执行器分别限流；云端只允许可信服务域名并禁止向客户端暴露凭据。
7. **三模块独立运行**：路由、统一归一化和质量层只依赖公共协议/小接口；Gateway 负责装配，不得成为任何一个模块的前置依赖。

## P0：安全、配置与发布基线

### 目标

先消除可越权调用、配置泄漏和不可重复发布的风险；不改变用户可见的核心功能。

### 工作项

- 新增服务端 `ExecutionPolicy` / `ParserExecutionOptions`，替代将 `ParseRequest.options` 原样传入解析器。
- 删除 API 表单和普通请求对 `native_output_dir` 的支持；仅保留受限的本地开发 CLI 入口，且路径必须在配置的工作根目录内。
- 将 `mineru_api_base_url`、Token、可信域名、重定向策略、上传/下载超时移到服务端配置；拒绝请求覆盖。
- 无论自动还是手动选择解析器，都必须经 `ModelRouter` 校验 `allow_cloud`、能力、格式和租户策略。
- 建立模块依赖基线：冻结 `contracts`/`ports` 的最小公共面，为 routing、normalization、quality 增加禁止反向依赖的 import architecture test。
- 增加上传大小、MIME/扩展名一致性、解压大小、单任务时长、并发数和磁盘配额限制。
- 收紧质量包写接口：优先移除外部直接覆盖；若必须保留，则必须验证输入 revision、manifest 和所有核心文件 SHA-256。
- 修正 `pyproject.toml` 的包发现/显式包清单，验证安装后的 API、routing、backend、全部 parser 与 quality 子包均可导入。

### 涉及模块

`core/contracts.py`、`composition/gateway.py`、`routing/`、`backend/app.py`、`backend/storage.py`、`parsers/mineru/`、`pyproject.toml`。

### 验收条件

- `allow_cloud=false` 时，任何入口均不可能提交云端任务。
- 外部请求无法指定本机目录、云端地址或 Token。
- 云端回调/下载 URL 不在可信域名集合时被拒绝。
- 手动选择不可用或不支持的 parser 返回结构化 4xx 错误。
- `pip install .` 后在干净环境中完成 API 启动和核心导入 smoke test。

## P0.5：统一输出协议与质量层联合基线

### 目标

把当前 `ParsedDocument 2.2` 从“多个字段的公共 JSON”明确为“质量层可验证的文档证据包”，冻结共同语义与演进规则，再进入异步编排和插件拆分。

### 工作项

- 梳理现有 `ParsedDocument`、`QualityPackage`、canonical document、repair audit 与 manifest 字段，形成字段所有者、来源、稳定性和消费者矩阵。
- 定义 `QualityEvidenceRequirements`、`CapabilityDeclaration` 与 rule status 降级语义；将质量规则实际所需的证据写成可测试的声明。
- 规定 semantic core、evidence 与 rendering 的单一事实来源，补齐 block/table/asset/relation 的稳定 ID、source anchor 和冲突表达。
- 定义结构化表格、来源 HTML、Markdown 表格之间的 resolver 输入/输出和保守跳过条件，复用既有质量层的表格修复审计模型。
- 制定 `ParsedDocument` schema 版本策略、兼容窗口、migration 格式和弃用流程；任何 parser 不得私自改变字段含义。
- 为每个已接入 parser 建立“parser fixture + capability matrix + quality expectation”的联合契约基线。

### 验收条件

- 质量层不读取 parser 私有对象，也不以 parser ID 作为规则分支条件。
- 每条质量规则都能说明其最小输入证据与证据不足时的确定性行为。
- 每个 parser fixture 的统一输出都可由质量层稳定消费，并得到可预期、可审计的结果。
- `parsed_document.json`、`document.md`、assets 与 manifest 的一致性可自动验证。
- 后续新增 parser 只需实现协议、capability 和 fixture，不修改质量层业务规则。

## P0.6：三模块独立运行与公共内核收敛

### 目标

落实第 4 节的依赖方向，使路由层、统一归一化层和质量层在代码、测试和运行入口上真正独立；Gateway 仅作为可替换的集成装配器。

### 工作项

- 将公共 Pydantic 协议、schema migration、稳定错误码迁入无业务依赖的 `contracts` 边界；清理 feature 模块之间的模型反向导入。
- 定义最小 `ports`：parser capability snapshot、parser execution、artifact storage、job persistence 等；由编排器注入实现，不让 routing/quality 直接构造具体服务。
- 将稳定 ID、哈希、路径校验、manifest 校验和原子写入等多模块通用能力拆为命名明确、无业务状态的 pure utilities。
- 为 `routing`、`normalization`、`quality` 提供独立 Python API 与 CLI fixture 入口；它们不得要求 FastAPI、worker、Gateway、存储目录或真实 parser 环境存在。
- 将现有 `composition/gateway.py` 的跨模块编排职责收敛到 `orchestration`/composition root；保持兼容入口，逐步消除 feature 模块对其反向导入。
- 引入 import architecture test 和循环依赖检查；CI 中单独安装/导入三个模块的最小依赖集。

### 验收条件

- 在不注册任何 parser executor 的情况下，路由层仍可使用伪 capability registry 生成完整 `RoutingDecision`。
- 在不初始化路由、Gateway、API 或文件系统的情况下，质量层可对内存中的 `ParsedDocument` 运行全部确定性规则。
- 在不启动路由或质量层的情况下，归一化层可对原生产物 fixture 生成并验证 `ParsedDocument`。
- 三个模块不存在相互导入、对 `backend` 的导入，或对具体 parser/storage 实现的直接依赖。
- 端到端功能仍只通过 composition root 串联，既有 API 行为与公共契约保持兼容。

## P1：任务编排与真实 fallback

### 目标

将解析从同步 HTTP 请求中迁出，使路由计划能被真实执行、记录和恢复。

### 工作项

- 定义 `ParseJobState`：`queued`、`preflight`、`parsing`、`normalizing`、`quality_checking`、`succeeded`、`failed`、`cancelled`、`needs_review`。
- 定义 `JobRepository` 和 `TaskQueue` 抽象。开发环境可使用 SQLite + 本地 worker；部署环境实现 PostgreSQL + 队列服务。
- 将 `POST /api/parses` 改为创建任务并返回 `202 Accepted + parse_id`；新增状态、attempt 历史、取消和事件查询接口。
- 编排器作为 composition root 读取 `RoutingDecision`，通过注入的执行器和归一化器依序执行主解析器及允许的 fallback；每次尝试都写入 parser、版本、参数指纹、开始/结束时间、错误分类和资源统计。
- 区分可重试错误（网络超时、服务暂不可用）和不可重试错误（格式不支持、策略禁止、契约不合法）。
- 将质量层作为成功归一化后的独立步骤；质量失败不篡改解析尝试记录。
- 增加幂等键，避免网络重试创建重复任务；重启后能恢复未完成任务或明确标记中断原因。

### 验收条件

- 长耗时任务不阻塞 API worker。
- 已定义 fallback 的自动路由任务会依序尝试并完整记录历史。
- 手动指定解析器绝不静默 fallback。
- 任一阶段失败后，查询接口能返回准确状态、失败分类和安全的用户提示。
- 同一幂等键不会生成重复 `SourceDocument`/任务。

## P2：版本化存储与产物治理

### 目标

使每个结果可复现、可对比、可安全下载，并为多模型评测和重新解析提供数据基础。

### 工作项

- 以 P2 的领域模型替代“一个 parse_id 对应一个可覆盖目录”的隐式状态。
- 源文件、大型资产和原生产物使用内容寻址或对象存储抽象；数据库只保存索引、版本关系和 manifest。
- `ArtifactManifest` 统一登记路径、媒体类型、大小、SHA-256、生成步骤、来源 attempt/revision。
- 所有写入采用临时目录 + 原子提交；只允许已提交版本对外下载。
- 为来源文件、原生产物、规范化文档、质量包定义保留期限、清理任务和审计记录。
- 下载接口只暴露已授权的 manifest 条目；后续可替换为短期签名 URL，不改变 API 语义。

### 验收条件

- 同一来源的两次解析结果可并存、可比较、不会互相覆盖。
- 任意下载产物可以回溯到 source、attempt、revision 和 SHA-256。
- 篡改文件会在读取或下载前被发现。
- 清理策略不会删除仍被有效 revision 引用的产物。

## P3：解析器插件化与执行隔离

### 目标

降低 `parsers/base.py` 和单一适配器的复杂度，让新增解析器不扩散影响到 Gateway、质量层或 API。

### 工作项

- 将每个解析器分解为四个稳定接口：`Probe`、`Execute`、`Normalize`、`Diagnose`。
- `Normalize` 必须输出第 3 节定义的文档证据包：语义核心、证据层、capability matrix、渲染视图和 manifest 保持可追溯关联。
- 解析器不得直接拼装质量结论或优化 Markdown；质量层只在统一协议之后运行。
- `Probe` 只负责格式/环境能力；`Execute` 仅产出原生产物；`Normalize` 仅生成 `ParsedDocument`；`Diagnose` 将底层异常归为平台错误码。
- 为每个 parser 定义显式 Pydantic 配置模型，禁止散落的字典参数。
- 将本地二进制、OCR、Office 转换与云端调用分别放入受限执行器，配置独立的并发、超时、临时目录和资源上限。
- Parser registry 只暴露稳定 capability snapshot、版本和 schema 兼容性；routing 依赖该 snapshot，质量层不依赖 parser ID 的分支逻辑。
- 按解析器建立固定 fixture、原生产物 fixture 和 `ParsedDocument` 契约回归。

### 验收条件

- 新增 parser 时，不修改质量层、API 路由或既有 parser 实现。
- 每个 parser 都可独立执行 probe、native run、normalize 和 contract test。
- 解析器异常统一映射为平台错误码，日志仍保留底层诊断信息。

## P4：质量反馈、评测与可观测性

### 目标

让“哪个解析器更适合什么文档”由稳定指标和确定性证据支撑，而不是经验判断。

### 工作项

- 建立分层语料：格式、语言、扫描比例、表格复杂度、公式、图片、Office 版本和失败样本。
- 为每次 attempt 记录耗时、资源、成本、失败率、能力缺失和质量门禁结果。
- 建立解析器 × 文档类型的评测矩阵，输出结构完整度、表格保真度、OCR 覆盖、质量 gate 通过率和人工复核率。
- 将质量层的 `reparse_required` 转成明确的路由输入；它只提出确定性建议，不直接执行或选择模型。
- 提供任务 trace：`job_id → attempt_id → revision_id → quality_run_id`，并输出结构化日志、指标和告警。
- 前端展示任务阶段、实际解析器、fallback 历史、质量摘要和版本比较，不直接展示敏感配置或原始错误栈。

### 验收条件

- 可以回答每类文档的首选 parser、fallback 成功率、平均耗时及质量收益。
- 任一线上失败可以通过 trace 定位到具体尝试、配置版本和原生产物。
- 路由策略调整必须有固定语料回归数据支撑。

## 7. 测试与发布护栏

每个阶段合并前均应具备以下护栏：

- 模块架构测试：禁止 routing、normalization、quality 相互导入或反向导入 Gateway/backend/具体 parser；三个模块以 fake ports 和 fixture 独立 smoke。
- 单元测试：策略、状态机、路径安全、错误分类、manifest 校验。
- 联合契约测试：所有 parser 输出均能通过 `ParsedDocument`、capability matrix、语义/渲染一致性与 manifest 校验；质量层对每个 fixture 的预期状态、修复和 gate 均可复现。
- 协议迁移测试：旧 schema fixture 经过显式 migration 后仍可被质量层消费；不允许字段语义静默漂移。
- 集成测试：上传 → job → fallback → normalize → quality → download 的完整链路。
- 安全测试：路径穿越、请求参数越权、SSRF、超大文件、恶意 ZIP、哈希篡改。
- 回归语料：每次路由/解析器/规范化改动都运行固定样本；质量层维持独立回归。
- 发布检查：安装包 smoke test、数据库迁移演练、worker 重启恢复、指标和告警可用。

## 8. 推荐执行顺序与依赖

```text
P0 安全、配置与依赖基线
  → P0.5 统一输出协议与质量层联合基线
    → P0.6 三模块独立运行与公共内核收敛
      → P1 任务编排与 fallback
        → P2 版本化存储
          → P3 插件化与隔离
            → P4 评测与观测闭环
```

P0 是上线前阻塞项；P0.5 冻结统一证据协议；P0.6 是 P1、P3 和质量层长期稳定演进的共同前提；P1 是产品稳定性的前提。P2～P4 可逐步推进，但 P2 的版本标识和 manifest 需要先于大规模评测落地。
