# P0 身份、权限、云端同意与人工复核领域契约（设计稿）

> 状态：待产品确认的 P0 设计；本文不实现认证体系，不选择 JWT、SSO 或任何身份供应商，也不改动解析、路由或质量算法。

## 1. 目的与边界

本契约为文档解析工作台的 P0 消除四类歧义：谁能访问哪一份文档、何时允许把原件送往云端、谁能对待复核结果作决定，以及何时可以正式交付结果。

它只定义领域对象、端口和服务端强制规则。认证方式由部署环境通过可注入的 `PrincipalResolver` 提供；解析器、路由器、归一化层和质量层不认识用户、租户、Cookie、JWT 或 SSO。

以下内容不属于本次 P0 设计：成员管理 UI、完整组织目录、下游下载令牌、双人复核、全量留存引擎和通用版本库。这些可以在不破坏本契约的前提下后续增加。

## 2. 现状审查结论

- 当前 FastAPI 的 job、parse、artifact、download、delivery、reparse 和 metrics 接口均不接收 `Principal`，仅凭 `parse_id` 读取全局文件系统记录；这不是授权边界。
- `ParseJob.revision` 是 `ApiStorage.save_job()` 的乐观并发 CAS 计数，不是用户可见的文档版本，绝不能拿来绑定审批或交付。
- 当前已发布结果的稳定 P0 引用应为 `revision_ref = parse_id`：每次重新解析都会创建新的 child job/新的 `parse_id`；再以 `document_id + quality_run_id + artifact_manifest_digest` 固定其内容快照。后续可新增正式 `Revision` 实体，但不能改变这个不变量。
- `needs_review` 是技术任务终态，且当前同时承载 `manual_review_required`、`reparse_required` 与 `rejected`。审批不能通过把 Job 从 `needs_review` 改回 `succeeded` 实现；真实质量状态必须从 `QualityPackage.quality_report.state` 读取。
- `allow_cloud` 目前只是路由选项：当服务器 `DOCUMENT_PARSER_ALLOW_CLOUD=true` 时，缺省请求会被视为可使用云端。它不是用户同意，也没有服务商、区域或数据范围记录。
- `backend.delivery.delivery_eligibility()` 正确地只做质量门判断、没有掺入 RBAC；但匿名 `/api/parses/{id}/delivery` 直接调用它，尚未组合资源授权、人工审批和交付撤销。
- `/download` 会打包 source、native 与诊断产物，应被定义为“诊断包”，不能与正式业务交付混为一谈。`POST /quality-package` 即使只在配置开关开启时可用，也不能作为普通公开 API 的信任边界。

## 3. 名词与不可变规则

| 名词 | P0 定义 | 不能做什么 |
|---|---|---|
| `Principal` | 本次请求或后台系统动作的已验证主体：`principal_id`、`tenant_id`、主体类型、角色/权限集合。它是运行时上下文。 | 不进入 `ParsedDocument`、`QualityPackage`、路由决策或质量规则。 |
| `JobScope` | Job 控制面上的不可变归属：`tenant_id`、`owner_principal_id`、`created_by_principal_id`。P0 创建时 owner 与创建人相同。 | 不能由客户端传入或通过 reparse 改写。 |
| `revision_ref` | P0 中已发布 Job 的 `parse_id`；与内容快照指纹一起指向一份不可变输出。 | 不能使用 Job 的 CAS `revision` 字段替代。 |
| 质量状态 | `QualityPackage` 的确定性结论。 | 人工复核不得篡改它、不得修改修复审计。 |
| 复核决定 | 对一个固定内容快照的业务处置。 | 不得自动继承到 child job、新质量运行或内容已变更的包。 |
| 正式交付 | 面向提交人或下游的受控业务包读取。 | 不能因页面隐藏按钮、知道 URL 或拿到 artifact 路径而绕过。 |

任何用户可见的资源操作都先在当前租户作用域内定位资源，再判断权限。未认证返回 `401`；跨租户或不可见资源一律使用不泄露存在性的 `404`；同租户但角色不够可返回 `403`。

## 4. 最小领域实体

### 4.1 身份、归属与策略

| 实体 | 最小字段 | 生命周期与用途 |
|---|---|---|
| `Principal`（运行时） | `principal_id`、`tenant_id`、`kind`（human/service/system）、`roles`、`scopes`、`active` | 由可注入身份适配器解析；不要求本项目知道其认证载体。 |
| `TenantPolicy` | `tenant_id`、`status`、`policy_version`、允许的云服务、敏感级别规则、保留策略引用 | 由管理面维护；是平台总开关之下的租户约束。P0 不要求先实现成员目录。 |
| `JobScope` | `tenant_id`、`owner_principal_id`、`created_by_principal_id`、`created_at` | 与 `ParseJob` 控制记录同存或由其一对一元数据保存；不可变。 |
| `ProcessingPolicySnapshot` | `job_id`、`tenant_id`、分类、`policy_version`、`cloud_mode`、允许服务集合、创建时间 | Job 创建/预检时由服务端生成，保存当时的处理约束；客户端只可表达偏好或拒绝。 |

P0 采用固定动作而不是先建设复杂权限语言：`job.create`、`job.read`、`job.cancel`、`job.reparse`、`artifact.read_diagnostic`、`artifact.read_source`、`delivery.download`、`review.claim`、`review.decide`、`tenant.audit.read`、`platform.metrics.read` 与 `system.quality.override`。角色只是这些动作的可配置集合；所有动作仍必须满足同租户和资源范围条件。

### 4.2 云端执行授权

P0 用一个不可变的 `CloudExecutionGrant` 同时记录显式同意和服务端评估结果，避免把 checkbox 当作证据。

| 字段 | 说明 |
|---|---|
| `grant_id`、`tenant_id`、`revision_ref/job_id` | 归属与精确目标。P0 中 job 与未来发布 revision 共用 `parse_id`。 |
| `source_sha256`、`source_size_bytes` | 绑定实际将被处理的原件，而非仅绑定文件名。 |
| `accepted_by_principal_id`、`accepted_at` | 谁在何时作出确认。 |
| `service_id`、`provider`、`region`、`data_scope` | 明确哪家服务、哪个区域、会发送哪些数据类别（至少原件字节；按实际情况补充页图/转换产物）。 |
| `notice_version`、`policy_version`、`plan_fingerprint` | 证明展示的文案和被批准的执行计划。 |
| `state`、`revoked_at`、`used_attempt_ids` | `accepted`、`declined`、`revoked` 或 `consumed`；撤销只能阻止尚未开始的调用。 |

该对象必须由服务端根据一个 `CloudServiceCatalog` 创建。Catalog 将 `parser_id` 映射为 `service_id`、服务商、区域、数据范围和文案版本；它属于后端组合层，不进入纯路由器。仅有 `ParserCapability.requires_network=true` 不足以证明同意覆盖了具体目的地。

### 4.3 人工复核与交付

| 实体 | 最小字段 | 关键规则 |
|---|---|---|
| `ReviewCase` | `case_id`、`tenant_id`、`revision_ref`、`document_id`、`quality_run_id`、`artifact_manifest_digest`、`quality_state`、`state`、`assigned_to`、CAS `version` | 质量包发布后按需创建。状态为 `open`、`claimed`、`resolved`、`superseded`。它是可领取的工作项，不是质量包的一部分。 |
| `ReviewDecision` | `decision_id`、`case_id`、同一份快照指纹、`action`、`reviewer_principal_id`、`reason`、`evidence_refs`、`decided_at` | 追加式记录。P0 动作为 `approve_delivery`、`reject_delivery`、`request_reparse`。决定不得改写 `QualityPackage`。 |
| `DeliveryRecord` | `delivery_id`、`tenant_id`、`revision_ref`、`package_kind`、`recipient_principal_id/service_id`、`artifact_manifest_digest`、`basis`、`status`、时间 | P0 可在每次正式交付/下载时创建记录；`issued`、`revoked`、`expired` 不等同于 Job 状态。 |
| `AuditEvent` | `event_id`、`tenant_id`、actor、动作、对象类型/ID、结果、时间、关联 ID、允许字段的脱敏上下文 | 追加式。不得写入原始内容、绝对路径、Token、Authorization 或原始异常栈。 |

`manual_review_required` 只有在存在同一 `revision_ref + quality_run_id + artifact_manifest_digest` 的有效 `approve_delivery` 决定时才可正式交付。`reparse_required` 与 `rejected` 在 P0 中一律不能被审批放行；前者只能创建 child job，后者只能拒绝或重新提交。每个 child job 都有自己的 ReviewCase，绝不继承 parent 的同意或审批。

## 5. 四条状态轴与交付门

技术任务、质量、复核和交付必须独立。建议的 P0 映射如下：

| 质量状态 | ReviewCase | 正式业务交付 |
|---|---|---|
| `pass` | 不需要 | 可由有权限主体下载，仍需 manifest 校验与审计。 |
| `pass_with_warnings` | P0 不需要（可在 P1 开启可选复核） | 可交付，并携带质量元数据。 |
| `manual_review_required` | 自动创建 `open` case | 默认阻断；仅相同快照的有效批准可解除。 |
| `reparse_required` | 可创建处置 case | 阻断；仅允许受权人请求/创建 reparse。 |
| `rejected` | 可创建只读处置 case | 永久阻断本 revision。 |

云端同意是另一条执行授权状态，不能复用 `needs_review`。若预检或候选 fallback 需要云端而没有有效 Grant，产品状态显示“等待云端同意”；技术实现可在 Job 上新增非终态 `awaiting_cloud_consent`，其恢复动作只能重新进入排队/预检。任何字节离开本地前都必须再次检查有效 Grant。

正式交付的服务端判定顺序固定为：

1. 当前 Principal 对该 revision/包类型具有 `delivery.download`；
2. revision 在当前 tenant 内且 package manifest、document identity、质量包四件套均完整；
3. 质量门允许，或 `manual_review_required` 有同一快照的有效批准；
4. 没有 revoked/expired 的 DeliveryRecord 或保留策略阻断；
5. 写入审计/交付记录后，再生成 ZIP 或响应字节。

`/download` 的全量包不走这条“正式交付”含义。它应改名为诊断包，分别检查 `artifact.read_diagnostic`、`artifact.read_source` 和复核/支持范围；不能因为质量失败就自动开放给普通提交人。

## 6. 依赖边界与可独立运行的模块

```text
FastAPI HTTP 适配器
  -> PrincipalResolver / AuthorizationPolicy
  -> 提交、复核、交付等应用服务
  -> TenantScopedJobRepository + ReviewRepository + AuditSink
  -> 编排器 -> Gateway -> Routing -> Parser adapters
                     \-> Quality runner
```

| 模块 | 可以独立运行的边界 | 不应依赖的内容 |
|---|---|---|
| `core`、normalizers、`quality` | 输入 `ParsedDocument`，输出 `QualityPackage`。 | Principal、tenant、ReviewCase、HTTP、存储路径。 |
| `routing` | 输入 capability snapshot、signals 和纯执行约束，输出 RoutingDecision。 | 用户身份、同意记录、数据库/文件系统。 |
| `orchestration` | 依赖 JobRepository、Gateway、QualityRunner 和可选的执行授权端口；可作为命令行/worker 库运行。 | FastAPI Request、Cookie、特定认证供应商、Review 状态迁移。 |
| `ApiStorage` | 持久化 Job/原件/包，并按明确 `tenant_id` 物理或逻辑分区。 | 角色推断、HTTP 认证、质量/人工审批策略。 |
| FastAPI 与应用服务 | 解析 Principal、授权、调用 use case、返回脱敏 DTO、审计。 | 直接拼接存储路径或把用户输入当执行策略。 |
| Review/Delivery policy | 对固定 revision 快照给出业务准入结论。 | 具体 parser、质量修复实现、认证载体。 |

建议新增但不绑定供应商的端口：

```python
class PrincipalResolver(Protocol):
    def resolve_current(self, request) -> Principal: ...

class AuthorizationPolicy(Protocol):
    def require(self, principal: Principal, action: str, resource: object | None = None) -> None: ...

class CloudExecutionPolicy(Protocol):
    def authorize(self, job_scope: JobScope, plan: object) -> CloudExecutionGrant | object: ...

class ReviewRepository(Protocol):
    def claim_case(self, tenant_id: str, case_id: str, actor_id: str, expected_version: int) -> ReviewCase: ...
    def append_decision(self, decision: ReviewDecision) -> ReviewDecision: ...

class AuditSink(Protocol):
    def append(self, event: AuditEvent) -> None: ...
```

`PrincipalResolver` 可以由任何部署实现；测试可注入静态 fake resolver，生产环境若未注入则必须拒绝受保护请求，不能回退为匿名管理员。

## 7. API 草案与调用顺序

每个受保护接口都遵循“解析 Principal → 租户作用域定位资源 → 动作授权 → 业务门禁 → 审计 → 响应”的次序。不得先无作用域 `load_job(parse_id)` 再把存在性告诉客户端。

| API 草案 | 所需动作 | P0 规则 |
|---|---|---|
| `POST /api/jobs` | `job.create` | 服务端从 Principal 写入 JobScope；幂等键按 `tenant_id + principal_id + endpoint` 作用域；客户端 `allow_cloud` 只能表达拒绝，不能提升权限。 |
| `POST /api/jobs/{id}/cloud-consent` | owner 的 `job.update` 或产品指定委托权限 | 只能接受服务端生成的 plan/challenge ID 与文案版本；生成或拒绝 CloudExecutionGrant，不接收任意 provider/region。 |
| `GET /api/jobs`、`GET /api/jobs/{id}`、`/events` | `job.read` | 查询天然带 tenant filter；DTO 不返回 `package_path`、本机路径或敏感异常。 |
| `POST /api/jobs/{id}/cancel` | `job.cancel` | 当前 `DELETE /api/jobs/{id}` 实际是取消，P0 应改为显式 cancel 路由；保留 `DELETE /api/jobs/{id}` 给未来删除申请，避免语义冲突。 |
| `POST /api/parses/{id}/reparse` | `job.reparse` + source read 范围 | parent 必须在同 tenant 且有权访问；child 继承 JobScope，不继承审批/云端 Grant；重新做云端政策判断。 |
| `GET /api/parses/{id}`、quality package、artifact | `job.read` 加产物类别动作 | 原件/native/诊断/优化产物分别鉴权；兼容 `/api/parses` 同步入口也必须经过同一 use case。 |
| `GET /api/parses/{id}/diagnostic-download` | 诊断和原件范围动作 | 取代语义含混的全量 `/download`；每次下载审计。 |
| `GET /api/parses/{id}/delivery` | `delivery.download` | 通过第 5 节的完整判定；不能仅调用质量函数后直接返回 FileResponse。 |
| `POST /api/review-cases/{id}/claim`、`/decisions` | `review.claim`、`review.decide` | CAS 领取；决策服务再次验证快照、质量状态和 reviewer 范围。 |
| `GET /api/metrics` | `platform.metrics.read` 或受限 tenant 指标动作 | 不能直接对所有 `storage.iter_jobs()` 匿名聚合。 |
| quality override | `system.quality.override` | 从公开 HTTP 客户端面移出或只允许显式 maintenance/system 主体；必须审计并使旧 ReviewCase superseded。 |

## 8. 云端与路由的精确责任划分

现有 `RoutingSettings.allow_cloud` 应解释为“部署是否具备云端执行能力上限”，而非“本次用户已同意”。有效云端许可为：

```text
平台总开关允许
AND 租户策略允许该服务/区域
AND 分类策略允许该数据范围
AND 本 Job 对该执行计划存在未撤销的 CloudExecutionGrant
```

路由器仍只根据能力与约束选择/排序解析器。它不读取数据库中的同意，也不判断角色。应用服务或执行授权端口将有效约束传给路由/网关，并在每一次网络候选调用之前复核 Grant；无 Grant 时只能过滤云端候选或进入等待同意，绝不能把本地 fallback 静默升级为云端调用。

这也意味着 `ReparseRequest.options` 不能携带新的云端目的地、Token、服务商 URL 或授权判断。服务端在创建 child job 时重新生成计划和 Grant，而不是复制 parent 的 options。

## 9. 对当前 delivery、review 与同意接口的处理建议

- 保留 `backend.delivery.delivery_eligibility()` 的“质量预门”定位，不把 Principal、角色或 HTTP 状态塞入它；必要时改名为 `quality_delivery_eligibility()` 更清晰。
- 新建应用层 `DeliveryPolicy`，组合质量预门、ReviewDecision 快照和 DeliveryRecord；最外层再由 AuthorizationPolicy 判断谁可以取件。三者不能相互替代。
- 不应在质量层或 `ParseJob` 上增加 reviewer 字段。ReviewCase/Decision 只引用 immutable artifact manifest 快照，因此质量包重写、重新解析或 manifest 改变会自动让旧决定失效。
- `POST /api/parses/{id}/quality-package` 的布尔配置开关不是授权。P0 默认不对外暴露；若保留维护入口，必须有 system principal、固定输入来源、审计和 ReviewCase 失效处理。
- `/api/parsers` 可返回经 tenant policy 过滤后的公开能力；不能把 server token、内部 URL、不可用原因的敏感细节带给普通用户。

## 10. 迁移次序与安全默认值

1. **先加纯契约与测试替身。** 定义 Principal、JobScope、ReviewCase、CloudExecutionGrant 和上述端口；为 `create_app()` 注入 resolver/policy。生产未配置 resolver 时，所有业务 API fail closed；开发/现有测试仅显式注入开发主体。
2. **给控制面加租户作用域。** 新建 Job 时强制写 JobScope；Repository API 改为接收 `tenant_id`，原件、job 与 package 使用租户命名空间，例如 `tenants/{tenant_id}/.jobs/{parse_id}` 与 `tenants/{tenant_id}/packages/{parse_id}`。`ParsedDocument`、`QualityPackage` 与质量四件套不写入身份字段，保持可搬运。
3. **隔离历史数据。** 既有 `job.json` 没有 tenant/owner，不能自动分给默认租户。将其标记为 legacy quarantine，只允许经受控管理员迁移：人工选择 tenant/owner、验证 source 与 manifest、原子搬迁、写 migration AuditEvent。未迁移包不对普通 API 可见。
4. **收敛所有 HTTP 入口。** jobs、旧 `/api/parses` 同步兼容入口、artifact、全量下载、delivery、reparse、metrics 和 quality override 全部经过同一授权/审计链；幂等查询不再全局扫描其他租户。
5. **引入云端计划和同意门。** 平台默认关闭云端；接入 CloudServiceCatalog、challenge/Grant 和等待同意状态；用本地、云端、fallback、拒绝、撤销等 API/E2E 测试证明任何网络调用都被门控。
6. **最后接入复核与正式交付。** 包发布后创建 case，审批以 manifest digest 绑定；delivery 在每次取件时重新校验。旧的匿名 `/delivery` 和全量 `/download` 先 fail closed，再以受权 API 替换。

物理存储迁移前应先验证每个旧包的 manifest、`revision.json`、source digest 与 quality 四件套；迁移失败的包保留隔离记录，不做“修好再发布”的隐式写入。`parent_parse_id`、幂等键和所有索引均必须纳入 tenant scope。

## 11. 必须由产品确认的四项决策

1. **租户与默认可见范围：** P0 是“提交人仅看自己的任务”，还是“同租户成员默认可看团队任务”？推荐默认 owner-only，团队查看通过明确 `job.read.team` 动作开启。
2. **云端同意颗粒度：** 每份 source/每次 reparse 都单独确认，还是在明确服务商、区域、数据范围和有效期后允许租户级预授权？推荐 P0 按 Job/source 单独确认，并在本地失败转云端时进入等待确认。
3. **人工复核权限：** `manual_review_required` 是否允许一名复核人批准交付？`reparse_required`、`rejected` 是否存在任何例外放行？推荐 P0 仅允许前者单人批准，后两者永不放行；双人和例外放行留到 P2。
4. **历史与删除责任：** 无法确定 owner 的旧任务是删除、隔离还是由管理员逐条认领？同时确认 source、native、质量包、交付记录和审计各自的保留期。推荐未知归属一律隔离，不自动归属给系统或第一个登录用户。

## 12. P0 完成验收

- 未认证、跨租户、被撤权和过期/撤销交付均不能读取 job、事件、原件、artifact、ZIP、quality package 或 metrics；不得泄露资源是否存在。
- 任何 `manual_review_required`、`reparse_required`、`rejected` 结果均无法通过直接 URL、旧兼容 API、artifact 下载或下游路径绕过正式交付门。
- 云端关闭、无同意、同意与服务/区域不匹配、同意撤销和本地失败转云端均不会产生网络请求。
- 复核决定与 exact `revision_ref + quality_run_id + artifact_manifest_digest` 绑定；重新解析、重写质量包或包完整性变化后旧决定不能交付新内容。
- 解析、路由、归一化和质量层仍可在没有 HTTP、认证、tenant、ReviewCase 或文件系统实现的情况下独立测试和运行。
