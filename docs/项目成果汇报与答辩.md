# 项目成果汇报与答辩

## 一、项目背景与核心痛点

本项目面向复杂文档解析与质量治理场景。原始问题不是“缺一个解析器”，而是缺少一套稳定、可追踪、可审计、可扩展的文档解析工程链路。

主要痛点包括：

- 多解析工具输出不一致：Docling、MinerU、OCR、AnyDoc、MarkItDown 的 Markdown、JSON、HTML、图片、坐标和 OCR 结果形态不同。
- 前端与算法容易耦合：如果前端直接调用解析器，后续模型切换、fallback、质量层接入都会变得不可维护。
- 缺失证据容易被误填：bbox、table cell、OCR confidence 等字段如果伪造，会导致质量判断失真。
- 路由、解析和质量层割裂：无法形成从上传、模型选择、解析、质量审查到重新解析的闭环。
- 原生产物不可追踪：出了问题后难以回溯到底是解析器能力缺失、归一化错误还是质量规则判断问题。

## 二、解决方案总览

我设计并落地了一套统一文档解析与质量处理系统：

```text
Web / API / CLI
  -> ParseRequest
  -> ModelRouter / RoutingDecision
  -> Parser Adapter
  -> ParsedDocument 2.2
  -> Quality Pipeline
  -> QualityPackage 1.0
  -> Web 展示 / 产物下载 / Reparse
```

系统核心设计是以公共契约作为中心：

- `RoutingDecision 1.0`：统一模型路由结果。
- `ParsedDocument 2.2`：统一解析结果。
- `QualityPackage 1.0`：统一质量层交付结果。

通过这一设计，前端、后端、解析器、路由层、质量层都围绕稳定契约协作，而不是互相依赖私有对象。

## 三、关键落地成果

### 1. 统一 Parser Adapter 体系

已接入和注册 5 类解析器：

- MarkItDown：轻量基线与回归路径。
- Docling：结构化文档解析。
- MinerU：PDF 高质量解析，支持云端 task API、本地兼容和 sidecar。
- OCR：RapidOCR 图片识别路径。
- AnyDoc：Office 与旧 Office fallback。

收益：

- 解析器从“散乱脚本调用”收敛为统一 Gateway。
- 新增解析器只需要实现 Adapter，不影响前端和质量层。
- 缺失输出统一通过 `capabilities` 声明，不伪造证据。

### 2. 自动路由与 fallback

实现 `ModelRouter`，支持：

- `local_first`
- `quality_first`
- `allow_cloud`
- LibreOffice 可用性
- parser capability registry
- fallback history

收益：

- PDF、图片、Office、文本等不同输入可自动选择解析路径。
- 手动 parser 模式仍可用于调试和复现。
- 云端调用受 `allow_cloud` 约束，避免误上传。

### 3. 统一文档包与 NativeArtifact

每次解析生成可追踪 package：

```text
parsed_document.json
quality_package.json
source/original.*
native/*
assets/*
```

每个原生产物包含：

- 安全相对路径
- 类型
- 文件大小
- SHA-256
- 是否为质量层必需证据

收益：

- 支持人工复核。
- 支持质量层证据追踪。
- 支持 artifact 下载。
- 支持 reparse 保留历史任务，不覆盖旧结果。

### 4. 后端 API 与 MVP Web

实现独立 FastAPI 后端：

- parser 列表
- 上传解析
- 读取解析任务
- artifact 下载
- 质量包读写
- 重新解析
- 静态前端挂载

MVP Web 支持：

- 上传文件
- Auto route / 手动 parser
- route profile
- allow cloud
- routing reason
- markdown
- capabilities
- warnings
- artifacts
- quality package
- reparse

收益：

- 前端完全不直接调用算法。
- 后端成为唯一编排入口。
- 演示和联调成本显著降低。

### 5. 质量层闭环

实现 `quality.run_quality(parsed_document)`：

- EvidenceContext
- 规则检查
- 标题、引用、表格、跨页表格处理
- capability matrix
- gate evaluator
- whitelist repairs
- canonical document
- quality report
- package manifest

后端在 parse/reparse 成功后自动生成 `quality_package.json`。

收益：

- 从“解析完成”升级为“解析 + 审计 + 质量状态”。
- 质量层不依赖解析器私有对象。
- Web 可直接展示最终质量包。

## 五、行业先进性与创新点

### 1. 契约优先，而不是工具优先

传统做法通常围绕某一个解析器的返回结构开发，后续替换成本高。本项目以 `ParsedDocument` 为中心，把工具差异封装在 Adapter/Normalizer 内部，从架构上支持多模型演进。

### 2. 证据真实性优先

系统不为了字段完整而伪造信息。缺失 bbox、cell、OCR confidence 时，统一通过 `capabilities` 声明。这让质量层可以基于真实证据降级，而不是产生虚假通过。

### 3. 原生产物可审计

所有 native sidecar 被归档为 `NativeArtifact`，并提供 SHA-256 和安全下载路径。这使得质量问题可以回溯到解析器原始输出。

### 4. 路由、解析、质量三层解耦

路由只负责选择，Adapter 只负责解析和归一化，质量层只负责审计与修复。职责清晰后，系统可以独立替换模型、扩展规则或升级前端。

### 5. MVP 不是 Demo，而是可测试工程链路

Web 页面背后复用正式 API 和 Gateway，不存在“演示代码另写一套”的问题。测试基线覆盖了从契约到后端闭环的主要路径。

## 七、结项结论

本项目已经从单点解析能力升级为完整的文档解析与质量治理平台雏形。系统具备自动路由、多解析器接入、统一契约、证据归档、质量评估、Web 展示和重新解析能力。

后续可以继续演进的方向：

- 引入异步任务队列，提高大文件处理体验。
- 扩展 LLM repair agent。
- 丰富真实业务 golden 数据。
- 增加浏览器 e2e 测试。
- 持续完善 MinerU、Docling、AnyDoc 在不同机器上的部署体验。
