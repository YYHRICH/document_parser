## 三、实施步骤与技术细节

### 3.1 目标架构与依赖铁律

```text
trigger（入口）        api（契约）         frontend（契约消费者）
 HTTP / CLI / MQ       DTO / OpenAPI       页面 + api-types.ts
      │                    │                    ▲
      ▼                    ▼                    │
   app（用例 + 编排 + 组合根）◄────── api DTO 复用
      │
      ▼
   domain（模型 / 路由 / 质量 / 端口 / 归一化）
      ▲                    ▲
      │ 实现端口            │ 实现端口
   infra（解析器 / 转换 / 存储 / 打包 / 质量产物 / LLM 占位）
```

依赖铁律（由 `scripts/check_dependencies.py` 用 AST 解析 import 强制校验，组合根豁免）：

```text
trigger → app → domain ← infra
    └──────→ api → domain
```

### 3.2 各层落地明细

- **trigger（触发层，只接客不写业务）**
  - `trigger/http/app.py`：FastAPI 应用工厂；`routes.py`：薄路由（health / parsers / parses / quality-package / artifacts / download / reparse）；`main.py`：uvicorn 入口。
  - `trigger/cli/main.py`：argparse 参数解析，与 HTTP 共用 `ParseDocumentUseCase`。
  - `trigger/mq/__init__.py`：MQ 触发占位，依赖 `domain.ports.EventPublisherPort`。
- **api（契约层）**
  - `api/dto.py`：后端唯一 DTO（由 `backend/schemas.py` 迁入）：`ParseJobResponse / ParseRecordResponse / QualityPackageResponse / ReparseRequest / ParserListResponse`。
  - `scripts/gen_frontend_types.py`：OpenAPI → `frontend/api-types.ts`（404 行）；`scripts/validate_contract_baseline.py`：契约基线校验。
- **app（应用层，总指挥）**
  - `use_cases.py`：`ParseDocumentUseCase`（解析→落盘→质量）、`ReparseDocumentUseCase`（换解析器重解析）、`RunQualityUseCase`（质量流水线入口）。
  - `orchestration.py`：`DocumentParsePipeline`（由原 `core/gateway.py` 门面拆解）：`SimpleSourceInspector` 提取 `DocumentSignals` → `ModelRouter` 路由（或显式 parser_id）→ 候选解析器逐个尝试（fallback 链）→ `ConverterPort` 格式转换 → 返回 `ParsedDocument` + native 旁路字节，全程记录 `FallbackAttempt / duration_ms / provenance`。
  - `bootstrap.py`：组合根 `ApplicationContainer` / `build_default_pipeline` / `build_router` / `build_application` / `build_use_cases`，仓库内唯一允许 import infra 具体实现的位置。
- **domain（领域层，大脑）**
  - `model/contracts.py`：领域模型族 `ParsedDocument / ParseRequest / DocumentSignals / ParserCapability / RoutingDecision / FallbackAttempt / ParserProvenance / QualityState / SourceAnchor / CanonicalBlock…`。
  - `routing/`：`ModelRouter`（按信号决策）、`policy.py`（降级策略）、`registry.py`、`ids.py`。
  - `quality/`：15+ 条规则（`QL_CONT/QL_HDG/QL_PROV/QL_REF/QL_TBL`）、`evidence/` 证据上下文、`gates/evaluator.py` 门禁状态机（优先级 `rejected > reparse_required > manual_review_required > pass_with_warnings > pass`）、`repairs/whitelist.py` 白名单修复（`QL_RPR_001/002`）、`pipeline.py` 流水线编排。
  - `normalization/bundle.py`、`service/source_inspector.py`：文件信号检查。
  - `ports.py`：`ParserPort / ConverterPort / StoragePort / EventPublisherPort` 四个 Protocol —— 依赖倒置的落点。
- **infra（基础设施层，干活的工具）**
  - `parsers/`：5 个解析器适配器（markitdown / docling / mineru / ocr / anydoc），统一实现 `ParserPort`；`registry.py` 登记表模式。
  - `converter.py`（`ConverterPort`）、`storage/api_storage.py`（`ApiStorage` 实现 `StoragePort`，含路径校验与包结构落盘）、`packaging/document_package.py`、`quality_packaging/`（质量报告产物）、`llm/`（占位，规划中）。

### 3.3 契约收敛闭环

后端改字段 → `scripts/gen_frontend_types.py` 重新生成 → 前端 `tsc` 编译即报错；配合 `scripts/validate_contract_baseline.py` 守住已冻结契约（`docs/朱-parse-integration-契约基线.md`），把"运行期才发现不一致"提前到"编辑器/CI 就报错"。

### 3.4 依赖强校验

`scripts/check_dependencies.py` 基于 AST 解析每个文件的 import，按铁律校验层间方向，组合根豁免；当前执行结果 `DDD dependency check: ok`，可作为 CI 门禁。

## 四、关键设计与权衡（思考与权衡）

1. **编排放 app 而不是 trigger**：HTTP handler 写编排会让 Web / CLI / MQ 各复制一遍；上移后用例层成为唯一入口，三个入口只做"协议适配"。
2. **端口优先于直接依赖**：解析器、存储、LLM 都是会变的依赖；接口化后"新增解析器 = 新增适配器 + 登记表登记"，零改动业务代码。
3. **组合根集中组装**：所有 `new` 收敛到 `app/bootstrap.py`，业务代码只认抽象，换实现只动组合根。
4. **domain 零框架依赖（除冻结的 schema 模型）**：路由、质量规则、门禁、归一化可独立单测，领域层甚至可独立成库/独立部署 —— 这是"可拆分"的根基。
5. **渐进式迁移，不推翻重来**：先冻结契约（`ParsedDocument 2.2 / QualityPackage 1.0`），再移动目录、批量修正 import、跑全量回归；靠依赖脚本兜底防回潮。
6. **诚实边界**：MQ consumer 与 LLM 质量顾问当前为占位/规划（MVP-B M6），文档中明确标注【已实现】/【规划中】，不把规划当已上线。
