# 文档解析服务周报

汇报人：朱恩铄
汇报日期：2026 年 9 月 4 日
负责范围：解析服务 DDD 架构与工程集成、文档生命周期、下游数据交付、多模态协议对齐、前后端联调。

## 一、当前任务目标

本周重点将文档解析能力从单次文件处理，完善为可管理、可交付、可追溯的服务：

1. 完成指定文件夹的文档变更识别，贯通新增、修改、删除与解析处理。
2. 对齐下游 Wiki 的输入目录和数据格式，完成发布、更新、撤回的适配与验证。
3. 对齐杨欣川提供的多模态产物协议，统一图片、OCR、视觉描述和来源定位字段。
4. 整理已有比赛数据集解析结果，形成可供下游验证的标准数据包。
5. 补齐前后端演示入口，展示从文件进入、质量检查到下游交付的过程。

分工边界：路由策略结论由张云雅负责，质量诊断与修复策略由叶耀华负责；本人重点负责上述能力的服务化集成、生命周期管理、协议对齐与交付链路，不将路由和质量算法成果重复计入个人产出。

## 二、本周进展与产出

### 1. 文档生命周期：从单次解析扩展到增量管理

**完成内容与结果**

- 基于文件路径、SHA-256 内容摘要和上一次 Manifest 实现扫描对账。
- 支持新增、修改、未变化、移动或重命名、删除、失败重试六类处理。
- 新增时分配稳定的 `source_id`；内容修改后保留文档身份，生成新的 `parse_id`。
- 未变化的文件跳过解析；内容不变的移动或重命名更新路径，避免重复计算。
- 解析或发布失败记录错误，下次扫描继续重试；删除时调用下游撤回接口。
- 将当前状态写入 `manifest.json`，将事件及发生时间追加至 `events.jsonl`，解析产物单独保存。
- 提供 HTTP 和 CLI 入口；页面支持放入文件、同名更新、扫描和删除。

**技术效果**

相比单次上传解析，新增了文档身份管理和变更对账，能够判断“同一份文档是否需要重新解析”，并将删除动作传递至交付端。当前选择内容摘要对账方案，便于验证、重跑和人工排查。实时文件监听是后续可选方案，但需要进一步处理短时间多次写入、事件合并、写入未完成等情况。

当前未开展与成熟文档管理平台的量化对标，因此不宣称行业领先。现阶段完成的是基础增量生命周期闭环，而非完整的生产级版本管理系统。

**工程实现**

- 领域层定义状态、事件和端口，应用层编排解析及交付，基础设施层负责文件扫描和记录持久化，继续保留 DDD 分层。
- 每次扫描需要读取文件并计算摘要，成本与受管文件总大小有关；未变化的文件不再调用解析器，可减少重复模型处理。
- 当前采用按钮或 CLI 主动扫描，不是常驻后台实时监听，也没有定时扫描任务。
- 当前演示环境使用本地文件存储，不增加数据库和消息队列部署成本；文件夹演示固定使用本地 MarkItDown，避免依赖云端调用。
- 后续可以增加防重入锁、任务队列、扫描进度及文件稳定性检测；尚未验证并发扫描、进程中断恢复和大目录性能。

**产品价值**

用户无需对未修改文件重复操作，可以查看文档当前状态、解析身份和错误信息。删除后的撤回记录有助于发现过期资料。现阶段适合单机演示和小规模受管目录，响应时间及吞吐量仍需通过真实负载测试确认。

### 2. 下游串联：以适配器隔离双方内部实现

**完成内容与结果**

- 实现 `MobileworkDeliveryAdapter`，将质量层结果转为下游 Wiki 约定的目录结构。
- 仅发布 `pass`、`pass_with_warnings` 状态且正文非空的结果；质量不合格的新版本不覆盖已有合格正文。
- 将优化后的正文写入稳定的 `raw/sources/{source_id}.md`。
- 复制资源到 `raw/assets/{source_id}/`，改写正文中的对应资源路径，保存资源清单与质量元数据。
- 文档更新时使用同一源文件名；撤回时移除下游监听的 Markdown，并保留相关元数据用于追溯。
- 页面增加下游交付面板，展示发布数量、撤回数量、质量状态、监听目录和交付记录。

交付结构：

```text
raw/
├── sources/{source_id}.md
├── assets/{source_id}/...
├── metadata/{source_id}/
│   ├── quality_package.json
│   ├── assets.json
│   └── delivery.json
└── .llmwiki/.document_parser/delivery-manifest.json
```

**技术效果**

相比让下游直接读取各模型私有输出，统一适配器隔离了解析器差异。下游通过稳定文件名及内容变化识别新增、修改、删除，不需要接入上游内部 Manifest。选择目录契约，是因为当前下游已经提供 `raw/sources` 扫描入口，可复用已有能力。

API、对象存储或消息队列也可以作为后续交付方式，但当前没有必要为了本地集成引入额外服务。尚未对不同交付方式做吞吐量、故障恢复或跨机器部署对比。

**工程实现与验证**

- 接入现有生命周期发布、撤回端口，不复制路由与质量处理逻辑。
- 单个交付文件采用临时文件加替换方式写入；这不等于整个多文件包具有事务性，跨文件一致性仍需进一步加固。
- 跨仓库集成测试实际调用下游 Wiki 的扫描代码，验证首次发布被识别为 `new`、内容更新为 `modified`、撤回为 `deleted`。
- 最近一次相关回归中，API、生命周期、交付适配器及生命周期架构测试合计 **16 项通过**。此结果为此前联调记录，不代表生产环境验收。
- 当前 Web 面板写入本地沙箱 `outputs/api/_downstream-mobilework/`，并非直接向姚丞韬的正式运行环境发布。

**产品价值**

页面可以直观看到“解析完成”和“已交付下游”的区别，减少只看到文件生成、却无法确认交付状态的问题。已验证的是交付和扫描事件识别，尚不能据此认定 Wiki 页面构建、索引及最终问答效果已经通过验收。

### 3. 多模态对齐：统一资源、视觉内容和来源证据

**完成内容与结果**

- 编制多模态数据契约 v1.0 评审稿及杨侧产物字段映射说明。
- 对齐杨侧 `mmwiki-0.1` 与解析侧 `ParsedDocument 2.2`，保留原生产物和模型来源信息。
- 统一文档块、资源、检索片段和视觉证据之间的 ID 关联，保留阅读顺序、页码、坐标系、页面尺寸及单位。
- 为图片保留独立的 Caption 与 OCR 槽位，避免视觉描述覆盖原始图注或 OCR 原文。
- 按图片类型约定 Caption/OCR 的执行或跳过规则；非就绪结果不可检索，并需记录原因或错误。
- 对资源路径、文件、哈希、外键及状态语义设置接入约束；缺失定位证据不通过默认值伪造。

**技术效果**

相比只交付 Markdown 图片链接，新的协议能够表达图片来源、关联正文、OCR 内容和视觉描述的证据属性。图像推断与原文提取分开记录，降低下游把推断当作原文事实的风险。

当前采用显式字段映射与校验，而不是要求各模块直接消费彼此的私有格式。协议已形成，但未完成与其他多模态平台的量化比较，也未验证整体检索收益。

**工程实现**

- 交付原图，不额外要求缩略图；根据图片类型决定是否执行 Caption/OCR，减少无必要的处理。
- 当前主要完成协议和接入约束对齐，不等于多模态推理模型已经全量运行或通过效果验收。
- 历史 Markdown 中缺失的页码、bbox、OCR 和表格单元格证据不能靠字段映射补齐，需要读取原生产物或重新解析。
- 模型推理耗时、显存、云端费用和资源存储量尚未完成统一测量；下一步需要在当前机器上用代表样本验证。

**产品价值**

下游能够区分原文、OCR 和视觉推断，并获得资源及来源定位信息。失败或缺失字段显式展示，比输出看似完整但无法验证的数据更可靠。实际价值仍需由 Wiki 消费、图片展示和检索测试进一步确认。

### 4. 比赛数据产物整理与前后端联调

**完成内容与实验结果**

- 对 allin6 已保存的解析结果进行选优候选导入、统一模型重建、质量流水线处理和资源物化。
- 本批形成 **224 个 Source、224 份正式数据包、8,471 个已物化图片资源**；完成报告记录悬空本地图片引用为 0，拒绝或要求重解析的选中包为 0。
- 每包包含统一解析结果、优化正文、质量包、图片及包记录，可用于下游验收。
- 完成上传解析、质量展示、生命周期和交付面板的集成；修复前端脚本语法问题、输出路径问题及 MinerU 新版 Python 包识别问题，并处理当时检测到的依赖冲突。

**结果口径与结论**

本批使用已有模型结果，**不是重新对 224 份原始文件全量调用解析模型**。224 份是选优后的文档包，不等同于质量层四模型回放的 777 个输出单元。通过质量门也不意味着内容完全无误，缺失证据仍按能力声明保留。

工程上复用已有解析结果可减少重复处理成本；产品上形成统一正文、资源和质量说明，便于下游验收。根据当前完成报告，这批正式包尚未写入生命周期 Manifest，也尚未完成向姚侧正式运行环境的批量发布，不能将其与页面中小样本生命周期演示混为一谈。

## 四、本周总结

本周完成了文档生命周期、目录契约交付适配器、多模态协议对齐和前后端演示链路，形成“文件变化识别—解析与质量处理—标准产物—下游发布或撤回”的基础闭环。当前主要成果是单机工程集成和本地联调验证；下一阶段重点从功能打通转向下游实际消费验收、多模态契约定版以及并发、性能和故障恢复验证。
