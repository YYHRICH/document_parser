# Document Parser 三人开发分工

本文是三人实际领任务、提 PR 和联调验收的执行清单。产品范围和验收标准以
`specs/archive/001-document-parser-collaboration/spec.md` 为准，公共字段以
`core/contracts.py` 为唯一事实源。

## 1. 共同目标

在当前 Python `document_parser` 基线之上完成以下 MVP：

```text
Web/CLI
  -> 自动或手动路由
  -> Docling / MinerU / OCR
  -> ParsedDocument
  -> 表格、标题、引用质量处理
  -> QualityPackage
  -> Web 展示、下载或重新解析
```

MarkItDown 作为现有基线继续保留并做回归测试，但不能替代 Docling、MinerU、OCR
三条 MVP 解析路径。

## 3. 张：模型选型与路由

### 3.1 开发任务

- `ZY-01`：建立 Docling、MinerU、OCR 的 `ParserCapability` 注册表，记录格式、版本、
  GPU/网络要求、可用状态和不可用原因；
- `ZY-02`：实现自动路由，根据扩展名、文本层、扫描比例、页数和语言等
  `DocumentSignals` 返回 `RoutingDecision`；
- `ZY-03`：实现用户指定模型校验。手动模式不得未经允许静默切换模型；
- `ZY-04`：定义自动 fallback 顺序和触发条件，保留每次失败原因；
- `ZY-05`：调研并实测 JPG、JPEG、PNG，覆盖普通图片、扫描、拍照、旋转、模糊、
  表格截图、透明 PNG、长图和无文字图片；
- `ZY-06`：接收质量层的 `ReparseRecommendation`，形成新的路由决策或明确拒绝原因。

### 3.2 交付物

```text
routing/
benchmarks/model_selection/
tests/routing/
tests/fixtures/images/
```

必须提交可执行代码、路由单元测试、图片逐文件结果、汇总报告和路由规则说明。

### 3.3 完成标准

- 自动模式和手动模式均能真实调用 Docling、MinerU、OCR，而不只是返回模型名称；
- `routing_decision.json` 固定样例通过契约测试；
- 不支持格式、模型不可用和所有 fallback 失败均返回明确原因；
- 图片路由规则有测评或能力声明作为依据。

## 4. 朱（parse-integration）：统一接入、解耦与完整串联

### 4.1 开发任务

- `ZH-01`：为 Docling、MinerU、OCR 实现统一 Adapter；现有 MarkItDown Adapter 保留；
- `ZH-02`：把各模型原生 Markdown、JSON、HTML、图片、表格和坐标归一为
  `ParsedDocument`；
- `ZH-03`：保存模型原生产物，并通过 `NativeArtifact` 提供安全相对路径、类型、大小和
  SHA-256；
- `ZH-04`：把张的 `RoutingDecision` 接到 Gateway 和 Adapter，记录建议模型、
  实际模型及 fallback 历史；
- `ZH-05`：按质量层输入矩阵提供 page、bbox、table cells/span、OCR spans、block ID、
  阅读顺序和能力缺失声明；
- `ZH-06`：实现独立后端 API，保证前端不直接调用解析算法；
- `ZH-07`：实现 MVP Web，展示上传、模型选择、路由原因、解析结果、质量状态、产物下载
  和重新解析；
- `ZH-08`：提供单 Adapter、纯后端和完整 Web 三种测试入口；
- `ZH-09`：维护三个公共契约的工程兼容性和端到端契约测试。

### 4.2 交付物

```text
core/
parsers/
normalizers/
backend/
frontend/
tests/contracts/
tests/api/
tests/e2e/
```

### 4.3 完成标准

- 每个 Adapter 可脱离 Web 独立运行；
- 三种模型结果均能生成合法 `ParsedDocument 2.2`；
- 缺失证据必须在 `capabilities` 中说明原因，不能填假 bbox 或假置信度；
- Web、CLI 和纯后端复用同一 Gateway，不复制算法实现；
- 完整链路能够生成并展示 `QualityPackage`，并能根据重解析建议生成新任务。

## 5. 叶：质量优化与准入

### 5.1 开发任务

- `QL-01`：维护质量输入需求矩阵，明确每条规则需要朱提供的字段或原生文件；
- `QL-02`：恢复有证据的表格网格、合并单元格和多级表头，输出
  `TableFieldBinding`；
- `QL-03`：恢复有证据的标题层级，输出稳定的 `parent_child` 关系和章节作用域；
- `QL-04`：绑定有明确编号或标识的正文引用与参考文献，输出 `reference_of`；
- `QL-05`：实现质量 issue、白名单 repair log、能力矩阵和准入状态；
- `QL-06`：输出 `optimized.md`、`canonical_document.json`、
  `quality_report.json`、`package_manifest.json` 四件套；
- `QL-07`：证据不足时进入人工复核或重新解析，不制造表头、数字、标题或引用关系；
- `QL-08`：维护质量正反例和最终验收集，并负责跨模块 PR 的接口验收。

### 5.2 交付物

```text
quality/
tests/quality/
tests/fixtures/parsed_documents/
```

### 5.3 完成标准

- 至少一个复杂/多级表头样例生成可回溯字段绑定，并有一个不确定反例安全降级；
- 至少一个多级标题样例生成 `parent_child`，不确定标题不强行升级；
- 至少一个编号引用样例生成 `reference_of`；
- 每个输出关系都带状态和证据，每个字段绑定都能回到真实来源；
- 五种质量状态均有测试，`reparse_required` 必须携带解析器建议。

## 6. 三次联调

### 联调一：接口样例评审

三人共同运行 `tests/test_contract_examples.py`。张确认 `RoutingDecision` 足够表达
路由，朱确认三类模型可映射到 `ParsedDocument`，叶确认字段足够完成表格、
标题和引用处理。通过后接口进入冻结状态。

### 联调二：固定样例串联

不启动真实模型和 Web：张输出固定 `RoutingDecision`，朱读取 fixture 生成
`ParsedDocument`，叶生成 `QualityPackage`。这一阶段用于发现字段问题，不等待完整
算法。

### 联调三：真实端到端

至少选择普通 PDF、复杂表格 PDF、扫描件、JPG、PNG 各一份，从 Web/CLI 走完路由、
解析、统一、质量、下载和重新解析流程。

## 7. 依赖与并行规则

- 张不必等待 Adapter 完成，可先对固定 `DocumentSignals` 开发路由；
- 朱不必等待路由规则完成，可用 `routing_decision.json` 开发编排；
- 不必等待真实模型完成，可用 `parsed_document.json` 开发质量层；
- 朱使用 `quality_package.json` 开发 Web/API 展示；
- 任何人需要新增公共字段，必须同时提交模型、固定样例、测试和接口说明；
- 禁止下游直接读取 Docling、MinerU 或 OCR 的私有对象。

## 8. Git 协作建议

建议从 `main` 创建以下功能分支：

```text
feature/router-model-selection
feature/parser-integration-web
feature/quality-layer
```

公共契约修改单独提交，避免和大规模算法修改混在一起。PR 至少需要一名下游接口使用者
评审；涉及 `core/contracts.py` 的 PR 需要三人确认后合并。

## 9. 统一 Definition of Done

每项任务只有同时满足以下条件才算完成：

1. 代码可运行，不以调研报告或伪实现代替；
2. 有正常、失败或不确定场景测试；
3. 输入输出符合公共契约；
4. 缺失能力和失败原因可观察；
5. README 或模块说明给出独立运行方式；
6. 不破坏 MarkItDown 和旧 Office 转换基线；
7. PR 已通过对应负责人和接口消费方验收。
