## 1. 背景与结论

前端目前支持五条解析路径：

- microsoft.markitdown
- docling
- mineru
- ocr
- anydoc

前端会传递模型选择、route_profile、allow_cloud 和 libreoffice_available；路由层再依文件类型、运行环境及用户偏好选择解析器。所有解析器最终应归一化为 ParsedDocument 2.2，主要字段包括 markdown、blocks、tables、assets、ocr_spans、capabilities、provenance 和 routing_decision。

因此，质量层不能按 parser_id 分支修复。它必须依据当前文档实际携带的结构和证据工作：某份文档是否有表格 HTML、表格 Markdown、单元格网格、页坐标或 OCR 置信度，才是可否检查、可否修复的依据。

当前质量层已经通过 quality/contracts.py 形成独立入口，并具备完整性、来源、标题、引用、表格、跨页表格、能力矩阵和 Gate 能力；M6 Agent/LLM 路径已移除。

## 2. 当前问题

### 2.1 修复机制与规则机制割裂

当前 QualityRule 负责输出 issue、能力观测和关系候选；修复由 WHITELIST_REPAIRS 另行全局执行。规则不能表达“该问题有哪些安全修复方式”，修复也没有足够的目标定位、结构证据和策略上下文。

### 2.2 修复目标不够精确

当前流水线先修改整篇 ParsedDocument.markdown，再将同一规则分别投影到每个 block。这会带来以下风险：

- 顶层 Markdown 和 block/canonical 内容可能产生不一致；
- 修复记录难以精确描述实际改动目标；
- 表格 HTML 转换没有优先使用 ParsedTable 已有的 Markdown、cells 与 span 证据；
- 全局字符串扫描容易误触不属于实际表格对象的内容。

### 2.3 现有低风险修复仍有语义风险

QL-RPR-001 当前会删除所有行尾空白，而 Markdown 的两个及以上行尾空格表示硬换行。这可能改变正文语义，应先修正。

QL-RPR-003 目前只自动转换结构完整且不含 rowspan / colspan 的 HTML table。含 span 的表格会保留原始 HTML 和 cells，解析器只产生有损 Markdown 候选并进入人工复核。

### 2.4 解析器运行能力不等于文档证据能力

ParserCapability 描述格式支持、依赖是否安装、网络/GPU 前提等运行时信息；质量层需要的是某一次解析产物实际带来的证据。

| 解析路径 | 典型可用证据 | 质量层限制 |
| --- | --- | --- |
| MarkItDown | Markdown、基础 blocks | 通常缺表格网格、页坐标、OCR 置信度 |
| Docling | Markdown、原生 JSON、可选 HTML | 表格和坐标证据取决于本次归一化结果 |
| MinerU | Markdown、表格 HTML/Markdown/cells、页坐标、图片 | 合并单元格 Markdown 投影可能有损 |
| OCR | 行级文本、bbox、OCR 置信度 | 不应推断表格结构或修正文字符 |
| AnyDoc | 原生产物中的 Markdown/JSON 等 | 证据完整度取决于实际 sidecar |

## 3. 目标架构

    ParsedDocument（原始结果，只读）
      → RepresentationInventory（表示与证据清单）
      → RepresentationResolver（文本 / 表格 / OCR 表示选择）
      → QualityRule（Finding + 可选 RepairProposal）
      → RepairPolicy（自动 / 人工复核 / 禁止）
      → RepairExecutor（精确补丁）
      → Verifier（重跑受影响规则）
      → GateEvaluator → QualityPackage

### 3.1 不变原则

- 原始 ParsedDocument 永远不被质量层覆盖或改写。
- 解析器名称只进入审计信息；规则、修复策略和执行器不按解析器名称分支。
- 自动修复只能做可证明等价的格式/结构标准化，不能猜测事实。
- 每个修复必须有目标、前置哈希、来源证据、参数、回放记录和复检结果。
- 表格 HTML、原生 JSON、cells 等原始证据必须保留，不能因生成 Markdown 而丢失。
- Gate 只消费复检后的 finding 与能力状态。
- 质量层只给出重新解析建议，不自动选择或调用其他模型。

### 3.2 RepresentationDescriptor

质量层内部新增类型化表示描述，第一阶段不强制修改 ParsedDocument 2.2：

- kind：document_markdown、block_markdown、table_html、table_markdown、table_cells、ocr_spans、native_artifact；
- target：文档、block UUID、table ID 或原生产物路径；
- content_sha256：执行前置条件，防止过期补丁；
- availability / granularity / fidelity：可用性、粒度、无损/有损/未知；
- evidence_refs：来源字段和原生产物引用；
- derived_from：某一展示表示由哪些结构事实投影而来。

RepresentationInventory 由 QualityInputAdapter 从当前 ParsedDocument 构建；旧版本产物只能得到“推断表示”，其自动修复权限应更保守。

### 3.3 表格表示选择策略

TableRepresentationResolver 的优先级如下：

1. 完整 table_cells（含行列与 span）是结构事实；
2. 结构校验通过的 table.markdown 是优先展示形式；
3. 缺 Markdown 且完整 HTML 无合并单元格时，可自动转换；
4. HTML 带 rowspan / colspan 时：
   - 始终保留 HTML 和 cells；
   - 若已有与结构一致的表格 Markdown，可采用它；
   - 否则只生成有损展示候选，默认 review_required，不得把投影结果冒充无损事实。

## 4. 分阶段实施

### P0：跨解析器基线与回归护栏

任务：

- 整理现有 MinerU、Docling、fallback fixture。
- 补充 MarkItDown、OCR、AnyDoc 的真实或脱敏原生产物 fixture。
- 为每份 fixture 记录 Markdown、blocks、tables、HTML、cells、anchors、OCR spans、assets、capabilities。
- 建立“规则 × 证据状态”的矩阵，而不是“解析器专属规则”的矩阵。
- 固化当前质量状态、issue、repair、canonical 和 package manifest 的回归快照。

验收：

- 每种解析器输出都能独立进入质量层。
- 不存在崩溃、未声明证据缺失或无理由的 Gate 放行。
- 无表格文档中的表格规则必须标记 not_applicable，不得阻塞。
- 基线测试可区分既有 xfail 和新增回归。

### P1：修正现有修复的语义风险

任务：

- 修复 QL-RPR-001：保留 Markdown 硬换行、代码块边界、CRLF/LF 和反斜杠硬换行语义。
- 为 QL-RPR-001 增加正文、表格、围栏代码、空白行和混合换行测试。
- 保留 QL-RPR-002 与 QL-RPR-003 的现有功能和 golden 测试，不在本阶段扩大修复范围。
- 记录现有 QL-RPR-003 对合并单元格的展示性、有损投影行为。

验收：

- 修复幂等。
- 原 Markdown 语义不变。
- 相同输入重复运行不会产生第二次 repair。
- 已有正常 fixture 的质量结论不发生意外变化。

### P2：引入表示清单和精确修复目标（已完成）

任务：

- 新增 quality/representations/，实现 RepresentationDescriptor、RepresentationInventory、QualityInputAdapter。
- 从 ParsedDocument 精确枚举 document、block、table、OCR 和原生产物表示。
- 引入唯一权威载体约束：一次修复只改一个明确字段；其他输出从该字段派生。
- 为旧协议创建兼容适配：缺少 locator 时可检查，但禁止依赖精确结构的自动修复。
- 逐步让 normalizer 输出更显式的表示引用；此项在验证后再决定是否升级核心契约版本。

验收：

- 任一 repair 都能定位到具体 document/block/table/artifact 目标。
- AppliedRepair 中含目标 ID、前置哈希及证据引用。
- 不再通过“全篇字符串扫描后再猜 affected block”的方式记录修复范围。

### P3：实现通用表格表示解析器（已完成）

任务：

- 新增 TableRepresentationResolver。
- 实现表格 HTML、table Markdown、cells 三类表示的结构校验和一致性比较。
- HTML 表格转换决策已迁移到已注册执行器，并将 table_html 源目标、哈希与文档/block Markdown 写入目标一并记录。
- 对无 span 的 HTML 表格允许 auto_safe 转换。
- 对有 span 的表格保留结构事实，并将有损 Markdown 投影显式标为 lossy_projection。
- 输出表格解析决策和差异证据，供报告和人工复核使用。

验收：

- HTML 表格转换不依赖 MinerU。
- MinerU、Docling、AnyDoc 只要输出相同类型的证据，就走同一逻辑。
- 表格 HTML、Markdown、cells 不一致时不得静默覆盖。
- 含 rowspan/colspan 的表不会因 Markdown 展示而丢失原始结构证据。

### P4：引入 RepairProposal、Policy、Executor、Verifier（已完成）

任务：

- 扩展 RuleResult，允许规则输出 RepairProposal。
- 新增 RepairPolicy，决策为 auto_safe、review_required、forbidden。
- 新增 RepairExecutor，校验目标哈希、前置条件和参数后执行精确补丁。
- 新增 Verifier，重跑受影响规则并记录验证结论。
- 将 WHITELIST_REPAIRS 从“全局直接修改”迁移为“已注册执行器 + 策略准入”。
- 重构 pipeline，使 canonical、optimized markdown、repair report 都来自同一份优化工作文档。

验收：

- 每条 applied repair 都可以回放、回滚和复检。
- 前置哈希不匹配时，repair 被拒绝且可审计。
- 修复后仍存在的问题不能被标为已修复。
- Gate 只读取复检后的 issue 和 capability verdict。

### P5：迁移既有修复、兼容发布与文档（已完成）

迁移顺序：

1. QL-RPR-001：安全的行尾格式规范化；
2. QL-RPR-002：定位后的 Markdown 表格分隔行修复；
3. QL-RPR-003：重命名为解析器无关的 table_html_to_markdown，接入表格解析器和策略。

任务：

- 更新 ../../quality/README.md、修复工作清单和契约文档。
- 更新 CLI 输出，使 repair proposal、策略决策和复检结果可查看。
- 保持现有 QualityPackage 1.0 可读；新增字段通过兼容版本或可选字段提供。
- 运行完整单元、集成、契约和 golden 测试。

验收：

- 所有既有修复在新模型下行为可追踪。
- 原始产物、优化产物和 canonical 之间的来源关系清晰。
- 同一输入的稳定 ID、repair ID、输出哈希一致。
- 质量层可继续独立执行：python -m quality --input ...

## 6. 明确不纳入本次质量层重构

以下能力禁止自动修复：

- OCR 猜字、错字纠正、断词通用拼接；
- 补写表头、单元格、数值、标题、公式；
- 跨页表盲目合并；
- 修改引用目标、来源定位、页码或 bbox；
- 用外部知识覆盖文档原文。

以下问题虽已观察到，但属于路由/解析编排职责，不混入质量层实现：

- 路由层会生成 fallback 计划，但 Gateway 尚未实际按顺序执行 fallback；
- 手动指定解析器时，Gateway 当前会绕开部分路由校验；
- OCR 解析器的实际执行能力与其注册能力声明需要单独对齐。

质量层只读取 routing_decision 和 provenance 进行审计；它可以输出重新解析建议，但不负责自动选择、调用或比较其他解析模型。

## 7. 开始实施的顺序

推荐按以下批次提交，保证每个批次可独立回归：

1. P0 + P1：补基线并先修硬换行语义风险；
2. P2：表示清单、目标定位和兼容适配；
3. P3：通用表格表示解析器；
4. P4：提案式修复与复检编排；
5. P5：迁移、文档、完整回归和发布准备。

开始 P2 前需要确认一项产品决策：对于带 rowspan / colspan 且没有可靠 table Markdown 的 HTML 表格，是否允许默认输出有损的展示 Markdown。建议默认不自动覆盖，只提供候选并保留人工复核状态。
