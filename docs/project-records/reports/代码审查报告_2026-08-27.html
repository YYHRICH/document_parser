0. 一句话结论

这套代码的工程质量明显高于一般内部项目、防御纵深到位。复查更正(2026-08-27):原 P0-2(任意目录读取)经攻击链逐环核验,HTTP 入口存在黑名单拦截(`native_output_dir` 被拒),当前不可直接利用,降级为"深层防御缺口";真正可直接利用的是 P0-3(存储型 XSS,全链实锤)——在无鉴权(用户确认 P0-1 暂缓)的当前阶段,任何能触达服务的人都能上传夹带恶意 HTML 的产物并诱导运营者触发,脚本在 API 同源执行后可读取全部文档。另有 5 个 P1(质量层 2 个崩溃 + 1 个静默改错、.doc 请求必失败、rowspan DoS)建议一个月内修复。其余问题按路线图排期即可,不需要返工式重构。

1. P0 高危(发布前必须处理)

P0-1 全 API 匿名访问 + parse_id/task_id 即访问凭据(IDOR)

维度内容
位置backend/app.py 全部路由(310-762)、backend/task_endpoints.py(68-350)、backend/tasks.py:151(scope 恒为 None)
问题无任何鉴权中间件;知道 parse_id 即可读完整解析文档、原文 PDF、质量报告、事件、谱系,可驱动 reparse 消耗资源;三组独立佐证(backend 静态、前端 401 语义缺失、覆写钩子无鉴权)
修复发布前置加反向代理层 BasicAuth/mTLS;P0 落地 ProcessingTask.scope 并写入索引,load_job/load_task 按 scope 过滤;/api/metrics 限内部网段

P0-2 请求 options 可任意目录读取(跨组证据链已闭合)

维度内容
位置parsers/base.py:426,621-626(任意 native_output_dir 被 rglob+read_bytes) + anydoc.py / docling.py:122 / ocr.py:171(未拒绝该键) + composition/gateway.py:318-334({**request.options} 原样透传)
问题⚠️ 2026-08-27 复查更正:当前经 HTTP 不可直接利用。入口 _validate_public_options(backend/app.py:84-96,855-871)的黑名单已含 native_output_dir,5 个建任务/重解析端点全部拦截(命中 400)。但下游链路全部实锤:MinerU 有防护、anydoc/docling/ocr 适配器无拒绝、base.py 对 native_output_dir 执行 rglob+read_bytes、gateway 透传 options——一旦黑名单被裁剪、或有人绕过 HTTP 直接调 storage/gateway,任意目录读取立即复活。属纵深防御缺口,建议保留黑名单并补回归测试
修复reject_sensitive_request_options 上提到 base 层统一执行;_native_path 拒绝 .. 段;落盘前 resolve().is_relative_to(safe_root);gateway options 按 parser_id 分组下发

P0-3 解析产物同源内联渲染 → 存储型 XSS

维度内容
位置backend/app.py:716-726(get_artifact FileResponse 无 Content-Disposition) + storage.py:1094-1107
问题native/*.html、assets/*.svg 被浏览器内联执行(上传内容攻击者可控);受害者打开 URL 即在 API 同源执行脚本,可 fetch 任意 parse 文档;即便无 html 工件,revision.json 等元数据也可内联读取
修复一律 Content-Disposition: attachment 或仅 text/plain 内联;全局 X-Content-Type-Options: nosniff + 严格 CSP;前端页面同步补 CSP meta

严重度问题
