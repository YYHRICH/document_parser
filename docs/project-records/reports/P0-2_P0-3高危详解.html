P0-2 / P0-3 高危问题详解

通俗解释 + 逐环攻击链(基于真实代码核验,2026-08-27)。当前阶段:P0-1(鉴权)用户确认暂缓,产品设计期。

先给结论

问题一句话当前状态
P0-2 任意目录读取请求参数理论上能被用来当"文件路径",让服务器去读它磁盘上任意目录的文件已复查降级 HTTP 入口有拦截,当前不可直接利用;深层防御缺口,建议保留拦截+补测试

P0-2 是什么意思

背景:上传文件时,客户端可以附带一组"解析选项"(options)。其中一个选项叫 native_output_dir,本意是给受信工具用的"原生解析结果输出目录"。

问题:解析器代码拿到这个选项后,会把它当目录,然后 递归读取该目录下所有文件并打包进解析结果。如果攻击者能控制这个值,理论上可以传 C:\Windows\system32 之类,把服务器上的文件读回来。

请求 options: { "native_output_dir": "C:\Users\secret" } → anydoc/docling/ocr 适配器直接采信(无任何拒绝,mineru 有拒绝) → base.py: rglob("*") 递归枚举 + read_bytes() 逐个读文件 → 全部内容塞进 native_files → 落盘进文档包 → 通过产物列表/下载暴露给请求方
复查更正(重要):原审查没看到入口处还有一道拦截——后端在 HTTP 入口就把 native_output_dir 列入黑名单拒绝(命中返回 400),5 个建任务/重解析端点全部走这道校验。所以当前通过正常 HTTP 请求无法利用。风险降级为:防御只有这一道,下游每条链路(适配器无拒绝、递归读文件)都是实锤;将来任何人改动黑名单、或新增不走这道校验的入口、或被脚本直接调用底层接口,漏洞立即复活。
建议:保留入口黑名单别删,加一条回归测试锁住;把适配器层也补上同样的拒绝(纵深),成本半小时。

P0-3 是什么意思

背景:系统支持"离线 sidecar"——调用方可以预先提供解析结果(native 文件),方便没有安装解析器时也能把已有结果入库。调用方式是在 options 里传 native_html / native_files / native_markdown / native_payload 这四个键。

问题:这四个键不在任何入口黑名单里,适配器拿到就直接采信、无条件按成功处理;上传者给什么内容就原样落盘成 native/document.html 等文件。而产物查看接口用"浏览器内联打开"的方式服务这些文件(不是强制下载)——恶意 HTML/JS 就在你们网站自己的域名下执行。由于当前没有登录(P0-1 暂缓),脚本可以偷偷读取服务器上所有解析过的文档。

攻击者:上传任意文件(哪怕 1KB 的 txt)+ options 里塞 native_html="<script>fetch('/api/parses/…')</script>" + parser_id=docling(不要求本机真的装了 docling) → sidecar 非空 → "解析成功",恶意 HTML 落盘 native/document.html → 产物清单把该文件显示为"HTML 文档预览"链接 → 运营者/任何人在浏览器打开 /api/parses/{id}/artifacts/native/document.html → JS 在 API 同源执行 → 可读取所有任务的文档、原件、下载包
为什么现在值得处理:① 门槛极低——一个 HTTP 请求,不需要任何解析器真实可用;② 前端还主动把这类文件渲染成"预览"链接,等于帮攻击者递链接;③ 没有登录意味着脚本能读到全部文档,而不是只有自己的。
修复成本极低(建议现在就做):
① 入口黑名单补 4 个键:native_html / native_files / native_payload / native_markdown(与 native_output_dir 同款,已有现成机制,加几行);
② 产物下载接口强制 Content-Disposition: attachment(或只允许纯文本内联),加 X-Content-Type-Options: nosniff;
③ 可选:前端不再把 html/svg 类产物展示为可点击预览。
①②合计约半小时改动,产品设计期做掉,后续鉴权上线前的空窗就安全了。

修复优先级建议(产品设计期视角)
