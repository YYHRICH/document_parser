# 质量层工作报告
## 结论

> 我们已经完成了一套可以独立运行的文档质量检查层。它能够检查文档结构、标题、表格、引用和原文来源，发现问题后给出明确结论，并输出一套可以供 LLMwiki 判断和使用的质量结果。

它解决的核心问题不是“把文字提取出来”，而是：

> 防止不可靠的解析结果直接进入 LLMwiki。

## 1. 质量层做了什么

质量层的输入是一份统一格式的 ParsedDocument，里面已经包含正文、标题、表格、引用、页码和来源位置等信息。

质量层主要完成五件事：

| 工作 | 通俗解释 |
| --- | --- |
| 完整性检查 | 看文档块是否存在、顺序是否混乱、内容类型是否匹配 |
| 来源检查 | 看每段内容能不能回到原文页码和位置 |
| 标题检查 | 看标题层级是否合理，能不能还原章节关系 |
| 表格和引用检查 | 看表格结构、跨页关系、列顺序和正文引用是否可靠 |
| 结果判定 | 判断通过、带提醒、需要人工复核或不能使用 |

另外，质量层只允许做少量明确的整理，例如清除行尾空格、修正明显的 Markdown 表格分隔行。它不会擅自改写原文内容，也不会凭空补标题、数字或表格字段。

## 2. 调用链路

    上游解析结果 ParsedDocument
                    ↓
    建立文档索引和证据索引 EvidenceContext
                    ↓
    执行 15 条质量规则
    （完整性、来源、标题、引用、表格）
                    ↓
    建立能力判断
    （哪些结果有证据，哪些只是推断）
                    ↓
    质量门统一判定
    （通过 / 带提醒 / 人工复核 / 重新解析 / 拒绝）
                    ↓
    输出 QualityPackage
    （优化内容、结构数据、质量报告、完整性清单）
                    ↓
    交给 LLMwiki 决定是否入库

质量门只有一个最终裁判。具体规则只负责发现问题，不能各自决定“放行”还是“拦截”。

## 3. 质量效果

### 已经能够检查的内容

- 文档块是否缺失、重复或顺序冲突；
- 标题字段是否完整，标题层级是否异常；
- 每个文档块能否回到原始页码和来源位置；
- bbox 坐标是否有效；
- 表格列路径、行列关系和合并单元格信息；
- 跨页表格是否可能是同一张表；
- 跨页表格是否发生列顺序变化；
- 正文中的数字引用能否找到对应参考文献；
- 原始产物和文件包哈希是否一致。

## 4. 支持的文档情况

质量层不按照 PDF、Word 这样的文件后缀来判断，而是按照文档结构来检查。

| 文档情况 | 质量层重点 |
| --- | --- |
| 普通正文和章节 | 内容完整性、阅读顺序、标题层级、来源位置 |
| 包含表格的文档 | 表头、合并单元格、字段绑定、跨页关系、列顺序 |
| 含参考文献的文档 | 参考文献编号、正文引用、引用来源 |
| 扫描或 OCR 文档 | 识别证据、置信度、来源定位、是否需要人工复核 |
| 证据不完整的兜底结果 | 明确标记证据不足，不伪造 verified 结果 

## 5. 表格处理详解

表格是最容易影响 LLMwiki 使用效果的部分。质量层的处理原则是：

> 不把表格简单压成一段文字，而是尽量保留行、列、合并关系、表头层级和原文位置；证据不足时宁可标记复核，也不生成看起来准确但实际错误的绑定。

### 5.1 先把表格还原成网格

上游需要提供每个单元格的：

- 起始行和起始列；
- 占用行数和列数；
- 单元格文字；
- 是否为表头；
- 是否为行标题；
- 单元格或表格的原文位置。

质量层先检查这些信息能不能组成一个合法网格：

1. 检查行列坐标是否为负数；
2. 检查单元格是否超出表格声明的行列范围；
3. 把每个单元格按照行跨度和列跨度展开到实际占用位置；
4. 检查两个单元格是否占用了同一个位置；
5. 检查数据区域是否出现没有任何单元格覆盖的空洞。

如果出现重叠、越界或数据区空洞，质量层会标记表格结构问题，后续不会继续生成可靠的字段绑定。

### 5.2 合并单元格怎么处理

合并单元格不会被拆成多个虚假的普通单元格。

例如：

|   | 一季度 | 一季度 | 二季度 |
| --- | --- | --- | --- |
| 地区 | 数量 | 金额 | 数量 |

质量层会保留“一季度”这个单元格跨两列的关系，而不是复制成两个独立的“一季度”。

处理步骤是：

1. 用 row_span 和 col_span 记录合并范围；
2. 检查合并单元格占用的所有网格位置；
3. 根据单元格覆盖的列，恢复每一列对应的多级表头；
4. 生成 column_path，例如“ 一季度 / 数量 ”、“ 一季度 / 金额 ”；
5. 将数据单元格与 column_path 绑定，而不是只按第几列绑定。

这样下游拿到的不是“第三列等于 100”，而是：

> 地区 = 华东，字段 = 一季度 / 数量，值 = 100。

### 5.3 多级表头怎么判断

如果上游明确标记了表头区域，质量层会检查表头是否从第一行开始、是否连续。

如果表头没有明确标记，质量层采用保守策略，通常先把第一行作为表头。对于存在跨列合并的表格，会继续检查下一行是否仍然像表头，例如内容是否连续、是否还没有进入数据行。

判断不确定时，质量层不会强行确认，而是把字段绑定降为 inferred 或 manual_review_required。

### 5.4 每个表格字段如何绑定

对每一个数据单元格，质量层会生成一条结构化绑定，主要包括：

- row_key：这一行对应的对象；
- column_path：这一列的完整表头路径；
- value：单元格的实际内容；
- source_locator：原文页码、表格位置和单元格位置；
- evidence：生成 row_key 和 column_path 所依据的单元格。

row_key 优先使用上游明确标记的行标题。如果没有行标题，才使用该行第一个非空单元格作为推断值，并标记为 inferred。

如果发现两行的 row_key 重复，质量层不会假设它们是同一行，而是将相关绑定降为人工复核。

### 5.5 单元格来源不完整时怎么处理

如果单元格有真实 bbox，绑定会使用单元格级位置。

如果上游没有提供单元格 bbox，但提供了表格级 bbox，质量层只能使用表格级位置，并把来源粒度标记为 table，而不是伪装成 cell。

如果连表格级来源也没有，质量层不会生成 verified 绑定。

### 5.6 跨页表格怎么判断

跨页表格不会简单按照“上一页最后一张表”和“下一页第一张表”直接合并。质量层会先判断两张表是否真的可能属于同一张表。

目前要求至少满足以下一种条件：

- 两页表头完全一致；
- 两页表头有足够的重合；
- 表名、正文或元数据中出现“续表”“续行”等提示。

同时，两张表还需要：

- 页码连续；
- 在文档阅读顺序中相邻；
- 列数基本一致；
- 能找到表格来源和必要的位置信息。

如果只是相邻页面，但表头和内容完全无关，质量层不会把它们当作续表比较。这样可以避免把“供应商表”和下一页的“项目表”误认为同一张表。

### 5.7 跨页续表如何输出

质量层目前不会把两页表格物理拼成一张新表，而是：

1. 保留每一页原来的表格和页码；
2. 生成一条 table_continuation 关系；
3. 在关系中记录两张表的编号、页码、表头和位置证据；
4. 页内字段绑定继续单独保留；
5. 由下游根据 continuation 关系决定是否展示成连续表格。

这样做可以避免合并后丢失页码，也方便回到原文核对。

### .8 跨页列漂移怎么处理

质量层会比较两页表格的：

- 列数；
- 表头顺序；
- 多级表头路径；
- 有条件时的列位置和宽度。

如果发现下一页列顺序改变，例如上一页是“项目、期初、期末”，下一页变成“项目、期末、期初”，质量层会输出列结构漂移问题。

此时不会按列号继续绑定，因为那会把“期初”的数值错绑定到“期末”。

如果表头略有变化、续表标记较弱或位置信息不完整，跨页关系会保留，但状态会降为人工复核。

### 5.9 典型场景的处理结果

| 场景 | 质量层处理 |
| --- | --- |
| 合并表头，行列跨度清楚 | 保留合并关系，生成多级 column_path |
| 合并单元格发生网格重叠 | 标记表格结构问题，不生成可靠绑定 |
| 两页表头完全一致，页码连续 | 生成已确认的续表关系 |
| 两页有“续表”提示，但表头不完全一致 | 保留关系，建议人工复核 |
| 两页列顺序发生变化 | 标记列漂移，禁止按列号静默绑定 |
| 两张表只是相邻页面但内容无关 | 不建立续表关系 |
| 只有表格级 bbox，没有单元格 bbox | 允许使用表级来源，但不标记为单元格级确认 |
| 没有足够来源证据 | 不生成 verified 结果，进入人工复核 |

# 质量层如何服务 LLMwiki

## 1. 质量层和 LLMwiki 的关系

质量层不是 LLMwiki 本身，也不是知识库页面。

它位于 LLMwiki 入库之前，作用类似“入库前检查站”：

    原始文档
        ↓
    上游解析
        ↓
    统一文档结果
        ↓
    质量层检查和判定
        ↓
    LLMwiki 入库
        ↓
    检索、问答和引用

如果没有质量层，LLMwiki 可能把标题错乱、表格错位、引用丢失的内容直接建成知识。后续即使问答出现错误，也很难判断问题来自原文、解析还是入库。质量层提供的价值是：在内容进入知识库之前，先把风险标出来。

## 2. 交给 LLMwiki 的四类结果

质量层最终输出 QualityPackage，核心内容可以这样被下游使用：

| 结果 | LLMwiki 的用法 |
| --- | --- |
| optimized.md | 作为主要的知识文本，供切片和索引 |
| canonical_document.json | 保存标题、段落、表格、引用和原文位置，供结构化处理 |
| quality_report.json | 判断是否直接入库，或者标记为人工复核 |
| package_manifest.json | 检查文件是否齐全、内容是否被替换 |

建议 LLMwiki 不要只读取 optimized.md。至少要把文档编号、版本、章节路径、页码、原文块编号和质量状态一起保存。

## 3. 让 LLMwiki 做得更好的几个方向

### 方向一：按照章节和结构切片

不要只按固定字数切文本。应优先参考：

- 标题层级；
- 章节路径；
- 表格边界；
- 引用关系；
- 页码和原文块编号。

这样问答时能更容易返回完整上下文，也能把答案定位到原文。

### 方向二：把质量状态带入检索

检索时应区分：

- 已通过内容；
- 带提醒内容；
- 待人工复核内容；
- 已拒绝内容。

默认只检索已通过内容；在没有足够结果时，再由业务人员决定是否扩大到带提醒内容。

### 方向三：保留引用和原文位置

LLMwiki 的回答最好能同时带出：

- 文档名称；
- 版本；
- 章节；
- 页码；
- 原文块编号；
- 原始文件链接或归档位置。

这样用户可以判断答案来自哪里，也方便发现问题后修订。

### 方向四：建立反馈闭环

下游用户如果发现答案不准确，应能记录：

- 哪个文档；
- 哪个章节或表格；
- 哪个质量问题；
- 是否需要重新解析；
- 修复后是否重新入库。

这些反馈可以反过来完善质量规则、人工标注集和后续 LLM 辅助判断。

## 最后结论

> 质量层的主要作用不是把所有文档都判成“合格”，而是把可靠内容放行，把不确定内容标出来，把问题留在进入 LLMwiki 之前解决。

> 对 LLMwiki 来说，最重要的不是多拿到一段文本，而是拿到一份知道来源、知道质量、知道能不能信的标准文档结果。
