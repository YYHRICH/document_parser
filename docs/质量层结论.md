# 四模型真实数据集自动修复报告



## 摘要

核心结果如下：

- 当前四模型解析结果对应 224 条源文件记录；四种模型共保存 777 个可回放的 Markdown 输出单元。原始全量目录另有 210 条属于其他数据类别，当前结果集没有对应输出。
- 756 个输出单元非空，21 个为空；质量回放没有发生脚本错误。
- 172 个输出单元被质量层改写，产生 1,450 次白名单修复操作。
- 1,309 个 MinerU HTML 表格被转换为 Markdown；另外 2 个表格因无法安全定位正文表格块而拒绝替换。
- 自动修复只改变可证明的格式表示和空白，不补写 OCR 内容、不猜测缺失正文、不臆造表格单元格。
- 质量层的正式下游交付只有 optimized.md 和 quality_package.json。

本轮结果支持以下判断：MinerU 是当前数据中复杂 PDF、扫描件和表格证据最丰富的来源，但必须经过 HTML 表格转换、资产完整性和标题结构检查；Docling 的版面与来源证据较强，但本次配置下表格网格和空结果仍需关注；AnyDoc 和 MarkItDown 能提供可用正文，但统一证据不足时只能降级交付。

## 2. DDD 分层中的实际执行位置

本次审查没有把数据集读取、修复规则和文件写入混在一起，执行边界保持 DDD 和 Ports and Adapters 结构：

| 层 | 本次承担的职责 | 对应位置 |
|---|---|---|
| 领域层 | 统一模型、质量规则、修复注册表、canonical 构建、能力矩阵和质量门 | domain/model、domain/quality |
| 应用层 | 接收 ParsedDocument，调用质量流水线，返回 QualityPackage | app/use_cases.py、domain/quality/pipeline.py |
| 基础设施层 | 解析器 Adapter、统一文档包读取、双文件质量包写入 | infra/parsers、infra/packaging、infra/quality_packaging |
| 触发层 | HTTP、CLI 和脚本入口 | trigger、tools/replay_quality_on_dataset.py |
| 下游 Wiki | 只消费最终双文件，不参与质量判断 | 仓库外系统 |

质量规则不直接读取 MinerU 或 Docling 私有对象。解析器先通过 Adapter 归一到 ParsedDocument，质量层再基于统一字段和真实 evidence 执行规则。HTML 表格修复规则虽然主要命中 MinerU，是因为 MinerU 的统一输入保留了 HTML 表格证据，而不是因为质量层硬编码了某个模型分支。

## 3. 质量层实际修复了什么

质量层当前只自动执行三类可验证、可重放且不改变事实内容的白名单修复。规则编号用于程序追踪，报告中同时给出它真正修改的内容：

| 修复规则 | 支持修复的具体问题 | 实际修改动作 | 明确不做的事 |
|---|---|---|---|
| 行尾空白清理（QL-RPR-001） | Markdown 每行末尾残留的多余空格或制表符 | 逐行删除行尾空格和制表符，保留原换行结构 | 不改正文文字、段落顺序、标题、链接或表格数据 |
| Markdown 表格分隔行对齐（QL-RPR-002） | 管道表格的表头列数与其下一行分隔线列数不一致，导致表格不能被稳定识别 | 以表头列数为准，补齐或截断分隔线单元，并规范分隔符和空白 | 不新增表头、不补表格数据、不推断缺失单元格 |
| HTML 表格转 Markdown（QL-RPR-003） | 正文中保留完整 HTML 表格，不利于 Wiki 切块、展示和文本召回 | 解析 HTML 表格并生成 Markdown 管道表格，同时更新统一表格对象、对应表格块和文档全文 | 无法唯一定位时不替换；不猜测跨页续表、缺失值或合并单元格语义 |

### 3.1 行尾空白清理（QL-RPR-001）

该规则逐行去除 Markdown 行尾多余空格，保留正文字符、段落顺序、标题文本、图片链接和表格内容不变。

本轮执行情况：

| 模型 | 发生改写的文档/单元 | 修复记录 |
|---|---:|---:|
| AnyDoc | 0 | 0 |
| Docling | 30 | 30 |
| MarkItDown | 0 | 0 |
| MinerU | 102 | 102 |
| 合计 | 132 | 132 |

它解决的是 Markdown 表示噪声，不是 OCR 或语义错误。实际修复记录会写入质量报告，并保留受影响内容块的稳定编号，便于追踪具体改动位置。

### 3.2 Markdown 表格分隔行对齐（QL-RPR-002）

该规则处理已经是管道表格、但分隔行不符合 Markdown 解析要求的情况。它只规范分隔线中的列数量、分隔符和空白，不生成新的表头或数据。

本轮执行情况：

| 模型 | 修复记录 |
|---|---:|
| AnyDoc | 3 |
| Docling | 0 |
| MarkItDown | 6 |
| MinerU | 0 |
| 合计 | 9 |

这类修复有助于 Wiki 识别和切分表格，但不等于恢复了原文档的物理网格，也不会生成可信的单元格级页码或坐标定位。

### 3.3 HTML 表格转换为 Markdown（QL-RPR-003）

这是本轮新增并真正命中的核心修复。MinerU 的 Markdown 中保留了完整 HTML 表格，虽然内容存在，但 Wiki 直接消费时不利于 Markdown 切分、展示和文本召回。

规则在满足以下条件时才执行：

1. 输入中存在完整、可解析的 HTML 表格片段；
2. 质量层能够把该片段唯一对应到一个统一表格对象和一个表格内容块；
3. 转换器能生成合法 Markdown 表格；
4. 原 HTML 表格内容确实出现在全文 Markdown 中；
5. 替换前后能同步检查表格块和全文内容。

修复动作不是简单的字符串替换，而是同步更新三个位置：

- 统一表格对象中的 Markdown 表示；
- 对应表格内容块中的 Markdown 内容；
- 文档全文中的 HTML 表格片段。

同时保留原始单元格、跨行/跨列合并结构以及转换证据。普通 Markdown 无法完整表达跨行和跨列合并，转换后可能出现布局表示损失；质量报告会如实记录，不把转换结果标成与原表格完全等价。

本轮 MinerU 共检测到 1,311 个 HTML 表格候选：

- 1,309 个成功转换；
- 2 个拒绝转换；
- 成功转换分布在 133 个输出单元中。

两个拒绝案例的共同原因是：表格内容块没有出现在文档全文中，质量层无法确定应替换哪一处。系统因此保留原内容，并记录“自动修复被安全规则拒绝”，而不是猜测替换位置。

### 4.1 总体统计

| 模型 | 改写单元 | 修复总数 | 实际修复内容 | 修复后仍有问题 | 修复后已解决问题 | 拒绝修复 | 最终状态 |
|---|---:|---:|---|---:|---:|---:|---|
| AnyDoc | 3 | 3 | Markdown 表格分隔行对齐 3 次 | 1,370 | 0 | 0 | 189 个带警告通过，2 个拒绝交付 |
| Docling | 30 | 30 | 行尾空白清理 30 次 | 1,389 | 0 | 0 | 169 个带警告通过，6 个拒绝交付 |

| 合计 | 172 | 1,450 | 行尾空白 132 次；表格分隔行 9 次；HTML 表格 1,309 次 | 6,180 | 2,611 | 2 | 726 个带警告通过，51 个拒绝交付 |

“修复后仍有问题”是指完成自动修复并重新执行全部质量规则后，质量报告中仍保留的问题实例数，不是问题文档数，也不是修复前问题数。同一份文档可以同时存在多类问题，同一类问题也可能分别指向多个内容块。它包括无法靠安全格式变换解决的正文缺失或乱码，也包括本次仅使用 Markdown 回放、缺少页码和坐标等结构化证据所产生的告警。

“修复后已解决问题”只统计修复前出现、复检后消失且能够按稳定特征完成前后对账的问题。它与修复操作数不是一一对应关系：一个表格转换可以同时解决多个问题，而行尾空白和表格分隔行改写目前没有对应的质量问题特征，因此虽有实际改写，已解决问题数仍记为 0。

## 5. 不同模型分别修复了什么

### 5.1 AnyDoc

AnyDoc 有 191 个非空输出单元，质量层实际改写 3 个单元，全部是“Markdown 表格分隔行对齐”修复（规则编号 QL-RPR-002）。

质量层没有对 AnyDoc 做以下操作：

- 没有补充页码、页面坐标或来源内容块；
- 没有从纯 Markdown 猜造物理表格单元格；
- 没有修复 OCR 或扫描 PDF 内容；
- 没有把缺失图片当作存在。

AnyDoc 修复后仍有 1,370 个问题实例：规则所需证据不足 955 个、标题层级或章节结构不可靠 220 个、来源追溯信息不足 191 个，另有图片或附件引用不完整 2 个、正文乱码或不可打印字符 2 个。189 个输出带警告通过，2 个被拒绝交付。这里的证据问题主要源于本轮只读取 Markdown、无法取得原生页码和坐标，不应理解成正文中有 1,370 处文字错误。

结论：AnyDoc 的本轮质量修复以 Markdown 可消费性为主，未改变事实内容；如果 Wiki 需要页级证据、图片资产或复杂表格字段检索，统一层必须补齐这些结构，不能让质量层事后猜测。

### 5.2 Docling

Docling 有 175 个输出单元，其中 174 个非空，质量层改写 30 个单元，全部是“行尾空白清理”（规则编号 QL-RPR-001）。1 个空 Markdown 没有被质量层填充，最终作为拒绝条件的一部分保留。

Docling 本轮没有命中 HTML 表格转换，也没有命中 Markdown 表格分隔行对齐。修复后仍有 1,389 个问题实例：规则所需证据不足 875 个、标题层级或章节结构不可靠 224 个、来源追溯信息不足 174 个、图片或附件引用不完整 110 个、正文乱码或不可打印字符 5 个、正文完整性不足 1 个。169 个输出带警告通过，6 个被拒绝交付。

结论：Docling 的主要价值在于版面、页面和块级来源证据；质量层本轮只清理表示噪声，未对标题层级、表格网格或空结果进行内容猜测。要改善表格能力，应调整 Docling 解析配置或由路由层改用 MinerU，而不是在质量层伪造单元格。

### 5.3 MarkItDown

MarkItDown 有 187 个输出单元，其中 167 个非空，20 个为空。质量层实际改写 6 个单元，全部是“Markdown 表格分隔行对齐”修复（规则编号 QL-RPR-002）。

质量层没有把 20 个空输出补成正文，也没有把内嵌的 Base64 图片数据推断成可用资源。修复后仍有 1,205 个问题实例：规则所需证据不足 935 个、来源追溯信息不足 167 个、标题层级或章节结构不可靠 65 个、正文完整性不足 20 个、正文乱码或不可打印字符 12 个、图片或附件引用不完整 6 个。149 个输出带警告通过，38 个被拒绝交付。

结论：MarkItDown 可以作为轻量格式转换器，但空结果和内嵌的 Base64 图片数据会直接影响 Wiki 入库。质量层能拦截空内容、报告资源风险，但不能从空 Markdown 恢复原文；需要路由层重新选择解析器或先完成资源外置。

### 5.4 MinerU

MinerU 有 224 个非空输出单元，是四种模型中唯一全部产出非空 Markdown 的模型。质量层改写 133 个单元，共执行 1,411 次修复：

- 行尾空白清理 102 次（规则编号 QL-RPR-001）；
- HTML 表格转换为 Markdown 1,309 次（规则编号 QL-RPR-003）。

MinerU 修复后仍有 2,216 个问题实例：规则所需证据不足 1,580 个、标题层级或章节结构不可靠 290 个、来源追溯信息不足 224 个、图片或附件引用不完整 106 个、表格结构不满足要求 9 个、正文乱码或不可打印字符 3 个、表格仍为 HTML 或缺少 Markdown 表示 2 个，以及自动修复被安全规则拒绝 2 个。219 个输出带警告通过，5 个被拒绝交付。

MinerU 的 1,309 个 HTML 表格修复是本轮最重要的质量收益。转换后，优化 Markdown 中不再残留这批 HTML 表格，表格块和全文内容保持同步，Wiki 可以按 Markdown 表格进行后续切块和索引。质量层没有尝试修复标题语义、跨页续表、OCR 识别错误或缺失图片，因为本轮回放缺乏足够证据。

结论：MinerU 适合当前数据中的扫描 PDF、图文报告和复杂表格，但交付 Wiki 前必须经过表格表示转换、资产完整性检查、标题树检查和分片完整性检查。

### 5.5 基于全量结果的后处理策略调整

本轮结果支持将后处理策略明确为“证据驱动的最小修复”，而不是对所有 Markdown 做统一重写：

1. 固定执行顺序为：修复前诊断 → 白名单修复 → 结构同步 → 修复后复检 → 质量门判定。这样可以区分“实际改写”“问题消失”和“仍需处理”，避免用修复次数冒充质量提升。
2. 行尾空白清理和 Markdown 表格分隔行对齐只处理格式噪声，不借助语言模型改写句子、数字、公式、标题或缺失值。
3. HTML 表格转换只在 HTML 表格、统一表格对象和表格内容块具有唯一证据链时执行；替换定位失败就拒绝修复并保留原文，不猜测位置。
4. 质量层不补救空 Markdown、OCR 乱码、缺失图片、跨页续表和阅读顺序错误。这些问题需要路由层重新解析，或由统一层补齐页码、坐标、资源清单和来源映射后再处理。
5. 模型差异用于路由和评测，不写入质量规则分支。当前数据只说明不同模型触发的修复类型不同，不意味着质量层应该为某个模型复制一套私有逻辑。
6. 全量回放继续采用只读 Markdown 模式；正式 Wiki 交付仍由真实统一文档对象生成，且只输出 `optimized.md` 和 `quality_package.json`。

## 6. JSON 绑定和 Wiki 交付

### 6.1 JSON 的设计与两个交付文件的分工

质量层只向 Wiki 交付两个文件，但二者职责不同：

| 文件 | 保存内容 | Wiki 的主要用途 |
|---|---|---|
| `optimized.md` | 完成安全修复后的连续正文、标题、图片引用和 Markdown 表格 | 全文索引、分段切块、向量化、关键词检索和提供给大模型阅读 |
| `quality_package.json` | 内容块、表格字段绑定、文档内关系、来源位置、质量问题、修复记录和准入结果 | 结构化检索、表格问答、答案溯源、过滤不可靠内容和解释质量状态 |

JSON 不重复保存完整的优化正文，避免同一份正文同时存在于 Markdown 和 JSON 中而产生不一致。JSON 保存的是 Markdown 难以表达、但 Wiki 检索和回答必须使用的结构、关系、证据与质量状态。

`quality_package.json` 的顶层设计如下：

| JSON 对象 | 作用 | 主要内容 |
|---|---|---|
| `document_id` | 绑定同一份文档的 Markdown、统一文档和质量报告 | 三处文档编号必须一致，防止正文与 JSON 串包 |
| `canonical_document` | Wiki 可直接消费的统一文档结构 | 内容块 `blocks`、表格字段绑定 `table_bindings`、章节或引用关系 `relations`、文档元数据 `metadata` |
| `quality_report` | 说明该文档经过了哪些检查、修复后还存在哪些风险 | 最终状态、修复后仍有问题、已解决问题、实际修复、拒绝修复、能力判断和质量门依据 |

其中，统一内容块负责把一段内容固定为稳定节点。每个内容块至少带有内容块编号、类型、文档顺序、修复后内容和来源位置。表格绑定和章节关系都通过内容块编号回到这个节点，避免 Wiki 分别维护互不关联的正文、表格和来源信息。

### 6.2 表格字段绑定如何设计

HTML 表格转成 Markdown 只是解决“能显示、能切块”的问题。为了让 Wiki 能回答“某一行、某一列的值是什么”，质量层还会把每个可识别的数据单元格转换为一条结构化绑定：

~~~text
一条表格字段绑定
  = 所属表格
  + 对应内容块
  + 行键
  + 完整列路径
  + 单元格值
  + 原始来源位置
  + 证据强度
~~~

各字段的含义如下：

| 字段 | 中文含义 | Wiki 如何使用 |
|---|---|---|
| `binding_id` | 该字段绑定的稳定唯一编号 | 去重、更新和引用同一条绑定，即使不同单元格的文字相同也不会混淆 |
| `table_id` | 所属表格编号 | 将同一张表的所有字段放回同一查询范围 |
| `block_id` | 对应的表格内容块编号 | 回到 `blocks` 中取得完整 Markdown 表格和上下文 |
| `row_key` | 行键，即这一行由什么值标识 | 定位“排行 1”“某个品类”“某个年份”等目标行 |
| `column_path` | 从上到下的完整列标题路径 | 支持普通表头和多级表头，防止只保留最后一级列名造成歧义 |
| `value` | 当前数据单元格的文本值 | 作为结构化问答的候选答案 |
| `source_locator` | 来源内容块、页码、坐标及坐标粒度 | 将答案定位回解析器原始对象和原文页面 |
| `status` | 该绑定是证据完整、根据结构推断，还是需要进一步确认 | Wiki 可按可信程度决定是否直接回答、附带提示或拒绝使用 |
| `evidence` | 行键单元格、列标题单元格、值单元格及其坐标索引 | 解释这条绑定是怎样构造出来的，并支持后续审计 |

本轮真实样本中，Markdown 表格的一部分为：

~~~markdown
| 排行 | 品类 | 同比增长 | 销售额占比 |
| --- | --- | --- | --- |
| 1 | 裤子 | 28.2% | 13.6% |
~~~

质量层把其中“排行 1 的同比增长为 28.2%”转换为下面这条真实绑定记录。示例中的字段和值来自实际输出；为便于阅读，只保留与绑定解释直接相关的证据字段，不展示同一 JSON 中的其他 319 条绑定：

~~~json
{

  "table_id": "mineru-0022",
  "block_id": "f192b590-769a-513b-ab30-613194d6dba4",
  "row_key": "1",
  "column_path": [
    "同比增长"
  ],
  "value": "28.2%",
  "source_locator": {
    "source_block_id": "mineru-0022",
    "page_number": 4,
    "bbox": [
      23.0,
      268.0,
      488.0,
      946.0
    ],
    "bbox_granularity": "table",
    "provenance_status": "inferred"
  },
  "status": "inferred",
  "evidence": {
    "row_key": {
      "value": "1",
      "source_cells": [
        {
          "cell_id": "mineru-0022:r1c0",
          "start_row": 1,
          "start_col": 0,
          "row_span": 1,
          "col_span": 1
        }
      ]
    },

      {
        "cell_id": "mineru-0022:r0c2",
~~~

这条记录表达了以下绑定关系：

~~~text
表格 mineru-0022
  -> 表格内容块 f192b590-769a-513b-ab30-613194d6dba4
  -> 行键“1”
  -> 列路径“同比增长”
  -> 值“28.2%”
  -> 原文第 4 页的表格级坐标
~~~

Wiki 查询“排名第一的品类同比增长是多少”时，可以先召回表格内容块，再按行键和列路径找到 `28.2%`，最后携带页码和坐标作为答案来源。该绑定被标记为“根据结构推断”，主要原因是 MinerU 没有明确标记哪一列是行表头，质量层只能把首列“排行”推断为行键。此外，该值没有独立的单元格坐标，来源只能定位到整张表；质量层不会把推断行键和表格级定位伪装成已经精确验证的单元格绑定。

该样本还暴露了一个需要下游注意的边界：原表格横向排了两组相同的“排行、品类、同比增长、销售额占比”列，因此同一张表中可能出现相同的行键和列路径。`binding_id` 和证据中的单元格行列位置可以避免记录本身发生覆盖，但仅靠 `row_key + column_path` 仍可能产生业务歧义。后续若要支持无歧义的字段查询，统一层或质量层还应把表头分组或列区段纳入完整列路径；在此之前，Wiki 必须同时限定表格编号、内容块编号和单元格位置，不能只按行键与列名全局取值。

### 6.3 JSON 对复杂表格的支持范围

当前 JSON 对复杂表格采用“可阅读表示 + 字段绑定 + 关系与质量诊断”三层表达：`optimized.md` 保存便于大模型阅读的表格，`table_bindings` 保存可查询的字段，`relations` 和 `quality_report` 保存跨页关系、结构异常与证据强度。不同复杂表格的支持程度如下：

| 复杂表格类型 | JSON 中的表达方式 | 当前支持程度 | 当前边界 |
|---|---|---|---|
| 普通单层表头表格 | 一个数据单元格对应一条 `table_bindings` 记录 | 已支持 | 行键、列名或来源证据缺失时会降级，不能强行生成可靠绑定 |
| 多级表头、父表头横跨多列 | `column_path` 按层保存完整路径；`column_path_segments` 保存每一级表头单元格及其跨列范围 | 已支持 | 表头区域必须能够从明确标记或连续结构中确定；互相重叠的表头不会强制绑定 |
| 行表头或多个联合行表头 | 优先使用被标记的行表头；多个行表头用完整组合构成 `row_key` | 已支持 | 未标记行表头时只能使用首列推断；行键重复时整行绑定降级为“需要进一步确认” |
| 跨行或跨列合并单元格 | 证据中保留起始行、起始列、跨行数和跨列数；网格检查会展开其占位范围 | 条件支持 | Markdown 无法保留视觉合并效果，覆盖位置会留空；数据合并单元格只生成一条绑定，不把值复制到所有覆盖列 |
| 横向并排、重复表头的表格 | 每条记录仍有独立绑定编号和单元格行列位置 | 部分支持 | 相同的行键和列路径仍可能产生语义歧义，需要增加表头分组或列区段 |
| 明确的空单元格 | 空单元格对象仍占据网格位置，可与“单元格缺失”区分 | 已支持 | 空值不会被自动补写或推算 |
| 网格缺口、单元格重叠或越界 | 质量报告记录网格缺口、占位冲突、越过声明行列范围等问题 | 检测支持 | 网格不可信时不生成可能错误的字段绑定，也不会猜测缺失单元格 |
| 单元格级页码和坐标 | `source_locator` 优先保存单元格坐标；没有时保留表格级坐标并声明粒度 | 已支持 | 不会把表格级坐标伪装成单元格级坐标 |
| 跨页续表 | 在 `relations` 中用“表格续接关系”连接前后两个表格内容块，并保存页码、表头路径、列数和续表提示 | 关系级支持 | 当前不会把两页数据物理合并成一张新表；每页字段绑定仍然独立 |
| 跨页列数、列顺序或列位置漂移 | 在质量报告中记录列数变化、表头顺序变化和列坐标漂移 | 检测支持 | 只诊断和降级，不自动移动列或改写单元格 |
| 纯图片表格、旋转表格或解析器未提供单元格网格的表格 | 只能保留表格内容块、图片或 HTML/Markdown 表示，并报告表格证据不足 | 暂不支持字段级绑定 | 质量层不会仅凭视觉猜造单元格；需要解析层提供 OCR、网格和坐标证据 |

#### 6.3.1 多级合并表头示例

#### 6.3.2 跨页续表如何表达

对于相邻页中的两张表，质量层会比较阅读顺序、页码、列数、完整表头路径、续表文字提示和列坐标。当证据表明后一张表是前一张表的续表时，JSON 在 `relations` 中建立关系，而不是直接拼接正文：

~~~json
{
  "relation_type": "table_continuation",
  "from_id": "前一页表格内容块编号",
  "to_id": "后一页表格内容块编号",
  "status": "verified",
  "evidence": {
    "table_ids": [
      "table-page-1",
      "table-page-2"
    ],
    "page_numbers": [
      1,
      2
    ],
    "header_paths": [
      ["行号", "物料", "数量"],
      ["行号", "物料", "数量"]
    ],
    "column_count": [
      3,
      3
    ],
    "continuation_hint": false,
    "column_geometry_drift": false
  }
}
~~~

只有相邻页、阅读顺序正确、列数一致、表头路径一致，并且位置证据充分时，续表关系才可以标记为“证据完整、已经验证”。如果只有“续表”提示或部分表头相同，关系会降级；如果页码不相邻、列数不同或中间夹有其他表格，则不会强行建立续表关系。

#### 6.3.3 当前 JSON 不是完整表格存档

当前正式 JSON 的 `table_bindings` 是面向 Wiki 查询的字段投影，不是对解析器物理表格网格的完整复制。它会在每条绑定的证据中保留相关行表头、列表头和值单元格的行列位置与合并范围，但没有单独输出包含所有单元格的统一 `tables` 数组。因此：

- 当前结构足以支持普通表格、多级表头表格和有可靠行列键的字段问答；
- 当前结构不能保证从 JSON 无损重建任意复杂表格，特别是没有形成绑定的空单元格、装饰单元格、嵌套表格和跨页整体布局；
- 如果 Wiki 后续需要表格图检索、完整网格重建或跨页物理合并，应在 `canonical_document` 中增加统一表格数组，完整保存行列规模、表头区域、全部单元格、合并范围、页面分片和来源位置；`table_bindings` 继续作为面向查询的派生索引，而不应承担完整存档职责。

因此，当前复杂表格能力可以概括为：能够安全生成有证据的字段绑定、保留绑定相关的复杂结构并诊断异常，但不会把证据不足的复杂表格伪装成已经完全结构化。

| 表格字段绑定 | 320 |


该样本的 320 条字段绑定均为“根据现有结构推断”，而不是“证据完整、已经验证”。主要原因是 MinerU 结果没有明确提供行表头标记，质量层只能使用每行首列推断行键；部分单元格同时缺少独立坐标，只能保留表格级来源位置。质量层保留这些绑定候选供 Wiki 检索，同时明确证据强度，不把推断绑定伪装成完全验证的事实。



## 7. 本轮没有自动修复的内容

质量层的设计重点是“可证明地修复”，不是尽可能多地改写。以下问题本轮只诊断或拦截，没有自动改正文：

### 7.1 空 Markdown

Docling 有 1 个空输出，MarkItDown 有 20 个空输出。质量层没有生成替代正文，避免把空结果误变成假内容；这些结果应由路由层触发重新解析。

### 7.2 OCR、乱码和语义内容

质量层没有根据上下文重写 OCR 文字、修正年份和数字、补齐缺失段落或恢复图片中的文字。没有真实 OCR span、原始页面或人工标注时，任何自动补写都可能制造事实错误。

### 7.3 标题语义和阅读顺序

质量层可以发现标题层级、父节点和阅读顺序证据不足，但不会把普通段落强行改成标题，也不会在双栏文档中凭经验重排正文。统一层需要提供真实 order_index、heading_level、section_path 和页级证据。

### 7.4 跨页续表、列漂移和复杂合并单元格

HTML 表格转换只处理表示层。质量层可以在页码、阅读顺序、表头和位置证据充分时建立跨页续表关系，也可以检测列数、列顺序和列位置漂移，但不会把多页表格自动物理合并，也不会自动移动列。跨行或跨列合并单元格转成普通 Markdown 后可能有表示损失，该损失会保留在质量报告中。

### 7.5 图片资产和内嵌 Base64 数据

全量回放能报告图片引用缺失和内嵌 Base64 数据风险，但没有在只读 Markdown 模式下伪造资源文件。图片外置需要统一层交付真实文件、相对路径、引用内容块和来源信息后再执行。

### 7.6 解析器不支持的格式

质量层不会把 Docling 或 MarkItDown 对旧 DOC、PPT 等格式的失败改成成功。格式转换和模型选择属于路由层/解析层职责。



## 8. 当前能力边界总结

| 能力 | AnyDoc | Docling | MarkItDown | MinerU |
|---|---|---|---|---|
| 普通正文输出 | 可用 | 可用 | 可用 | 可用 |
| 空结果风险 | 低 | 1 个空输出 | 20 个空输出 | 低 |
| 扫描/OCR | 弱 | 取决于配置 | 弱 | 当前最强 |
| 页码和 bbox | 低 | 强 | 低 | 强 |
| 图片资产 | 弱 | 较强 | 存在内嵌 Base64 数据风险 | 较强，但需统一层闭合 |
| 物理表格网格 | 弱 | 有，但本次配置不稳定 | 弱 | 当前最丰富 |
| HTML 表格风险 | 无明显命中 | 无明显命中 | 无明显命中 | 本轮核心修复对象 |
| 适合的路由位置 | 普通正文、旧 Office 兜底 | 版面和来源证据 | 轻量格式转换 | 扫描件、图文和复杂表格 |

这些结论是当前数据集、当前解析配置和当前统一适配器的结果，不等同于四种模型的理论上限。


## 9. 结论

本轮质量审查证明，质量层已经能够对四种解析器结果执行统一的、证据驱动的安全修复：

1. 对格式噪声执行行尾空白和 Markdown 表格分隔线规范化；
2. 对可定位的 MinerU HTML 表格执行确定性的 Markdown 转换；
3. 在修复前后分别诊断，保留未解决问题、已应用修复和拒绝修复；
4. 在具备原生表格证据时生成 table_bindings 和文档关系；
5. 用质量门决定结果能否交给 Wiki；
6. 最终只向 Wiki 交付 optimized.md 和 quality_package.json。

不同模型的修复重点不同：AnyDoc 和 MarkItDown 主要是 Markdown 表格表示修复，Docling 主要是行尾空白清理，MinerU 同时承担行尾空白清理和大规模 HTML 表格转换。质量层没有把模型结果强行改成同一种“看起来完整”的内容，而是保留证据差异并把不确定性写入质量报告。
