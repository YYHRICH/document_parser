## 1. 落地结论

正式工作台以“处理任务”为用户可见单位：用户提交 1 份或多份文件后，进入同一个处理中心；每份文件仍独立解析、独立生成质量结果、独立重试和重新处理。界面只按“1 份文件”或“N 份文件”表达，不把技术实现称为“批次”。

现有 `ParseJob`、编排器、统一输出协议和质量层继续作为文件级处理主链路；新增的 `ProcessingTask` 只负责聚合、展示、恢复和导出，不能反向控制解析器、路由器或质量规则。

```text
上传文件
  → ProcessingTask（处理任务，持久化聚合）
      ├─ TaskFile A → 现有 ParseJob → ParsedDocument → QualityPackage
      ├─ TaskFile B → 现有 ParseJob → ParsedDocument → QualityPackage
      └─ TaskFile N → 现有 ParseJob → ParsedDocument → QualityPackage
  → 处理中心（聚合状态）
  → 文档详情（单文件连续阅读、修订记录、重新处理）
  → 两类受控压缩包
```

本计划补充既有产品化和 P0/P1 契约，不替代它们。尤其不能因为工作台页面上线，就把“待确认”结果视为已经获准交付。

## 2. 目标、边界与不变原则

### 2.1 本次目标

- 建成三个连续页面：上传文件、处理中心、文档详情。
- 同一提交既支持 1 份文件，也支持多份文件；刷新、关闭页面后仍可从任务链接恢复。
- 在处理中心按文件展示“处理中、待确认、可下载、处理失败”，并提供准确的已完成数量和下一步操作。
- 在文档详情中默认展示优化后内容；通过修订记录展示修改内容、原始内容、当前版本、原因和定位位置。
- 保留一个“下载”入口，展开后只显示“原始解析压缩包”和“优化后文档压缩包”两个选项。
- 复用现有的异步任务、幂等、质量包、manifest 校验、retry、reparse 和谱系能力。

### 2.2 明确不做

- 不重写 `ParsedDocument 2.2`、`QualityPackage 1.0`、质量层规则或解析器适配器。
- 不在前端直接调用解析器、质量层、存储目录或云服务。
- 不把样例的 `sessionStorage` 数据结构、假进度或演示确认逻辑搬到正式项目。
- 不把现有 `/api/parses/{id}/download` 直接改名为“原始解析压缩包”；该接口目前混有原件、native、诊断和质量文件。
- 不在没有 `ReviewCase` / `ReviewDecision`、权限和审计的情况下，让“采用当前结果”越过质量交付门禁。
- 不改变路由层、统一归一化层和质量层的独立运行边界。

### 2.3 产品与代码原则

- 界面文案面向使用者，使用“处理、修改、结果、下载”等业务语言；不展示内部路径、异常栈、模型配置字典或实现自述。
- 后端是状态、权限、质量门禁和下载范围的唯一裁判；前端只渲染安全 DTO。
- 进度只展示已确认的阶段、耗时和文件数量。没有可靠分母的步骤不显示伪造百分比。
- 自动修复只展示质量层已经记录的证据，不补造“修改前后”文本；缺少安全片段时明确展示可定位原因。
- 所有跨模块通信经稳定契约或端口进行，禁止工作台代码导入 parser 私有对象、质量层内部目录或文件系统路径。

## 4. 目标领域模型与状态语义

### 4.1 处理任务模型

| 对象 | 关键字段 | 职责与限制 |
| --- | --- | --- |
| `ProcessingTask` | `task_id`、`scope`、创建时间、提交设置快照、`task_file_ids`、聚合版本号 | 表示一次用户提交；不保存解析结果正文，不替代 `ParseJob`。 |
| `TaskFile` | `task_file_id`、`task_id`、显示文件名、大小、类型、`active_parse_id`、历史 parse 链、产品状态、下一步动作 | 表示任务中的一份逻辑文件；重新处理时切换到新的 child `ParseJob`，历史结果仍可追溯。 |
| `TaskAggregate` | 四种状态计数、最近事件、可下载数量、更新时间 | 由所有 `TaskFile` 投影得到，不能成为质量或交付的事实来源。 |
| `DocumentDetailProjection` | 当前文件摘要、优化预览、原始预览、修订记录、问题、可用动作 | 面向页面的脱敏读模型；从 `ParseJob`、`ParsedDocument`、`QualityPackage` 和复核结果生成。 |
| `ArchiveSelection` | 包类型、目标 `TaskFile` 快照、纳入/排除原因、manifest digest | 生成 ZIP 前冻结的选择结果；不直接从活目录拼接文件。 |

`TaskFile.active_parse_id` 只能指向同一 source identity 的当前处理链。重新处理由现有 reparse 创建新的 child job；新结果不能覆盖旧结果，旧的质量结论、下载快照和复核决定均保持其原有身份。

文件名属于受任务范围保护的用户信息。它只能出现在授权后的 task/file DTO 中，不能为了方便展示而重新写入公开的 `/api/jobs/{parse_id}` DTO。

### 4.2 用户状态映射

| 页面状态 | 底层依据 | 用户看到的主要内容 | 可执行动作 |
| --- | --- | --- | --- |
| 处理中 | `queued`、`preflight`、`parsing`、`normalizing`、`quality_checking` | 当前已确认阶段、开始时间、已耗时；任务总数明确时展示“已完成 X / N 份” | 查看详情、取消（仅后端允许时） |
| 待确认 | `manual_review_required` 或 `reparse_required` | 质量结论、未解决原因、修订/问题摘要和推荐下一步 | 查看详情、重新处理；有正式复核权限和 case 时才可作决定 |
| 可下载 | `pass` / `pass_with_warnings` 且所有目标产物通过 manifest 校验 | 已完成时间、修改数量、可下载包范围 | 查看详情、下载、重新处理 |
| 处理失败 | 解析失败、取消，或 `rejected` 的不可用结果 | 安全的失败摘要和下一步建议 | 重试（仅 `retryable`）、重新处理、重新上传 |

`needs_review` 只是技术任务状态，不能单独决定 UI 含义。页面必须同时读取真实 `quality_state`，区分“可由复核人确认”“建议重新处理”和“不可交付”。

### 4.3 “采用当前结果”的正式语义

样例中的“采用当前结果”在正式系统中不能只是把一个文件从“待确认”改成“可下载”。正式映射如下：

- `pass`、`pass_with_warnings`：不需要用户确认，质量门已经允许交付。
- `manual_review_required`：只有存在与当前 `parse_id + quality_run_id + artifact_manifest_digest` 一致的有效 `ReviewDecision(approve_delivery)` 时，才能显示为可下载。
- `reparse_required`：不允许“采用当前结果”；只能请求/创建重新处理。
- `rejected`：不允许“采用当前结果”；只能保留受控证据、重新提交或重新处理。

在 P0 复核领域对象完成前，详情页只显示“查看处理结果”和“重新处理”，不能提供会误导用户的确认按钮。

## 5. 两类压缩包的正式定义

### 5.1 原始解析压缩包

这是“解析器原始整理结果”的用户可读包，不是上传原件，也不是完整诊断包。每份纳入文件采用稳定 `task_file_id/` 子目录，避免同名文件覆盖。

```text
原始解析压缩包.zip
├─ archive_manifest.json
└─ <task_file_id>/
   ├─ document.md
   ├─ parsed_document.json
   ├─ assets/                 # 仅 document.md / parsed_document.json 实际引用的资源
   └─ parse_manifest.json     # 最小解析元数据、哈希、版本和来源标识
```

必须排除：上传原件、`native/`、内部日志、绝对路径、`optimized.md`、质量报告、quality package、诊断快照和任意未登记文件。

### 5.2 优化后文档压缩包

这是交付给业务使用者的优化后结果包，只纳入已经通过质量门，或按 P0 已被有效批准的文件。

```text
优化后文档压缩包.zip
├─ archive_manifest.json
└─ <task_file_id>/
   ├─ optimized.md
   ├─ canonical_document.json
   ├─ package_manifest.json
   ├─ assets/                 # 仅 optimized.md 实际引用的资源
   └─ delivery_manifest.json  # revision/quality/审批快照和文件哈希
```

默认不放入原件、native 输出、全量质量报告、调试信息和内部 revision 文件。若后续需要给受权复核人提供诊断资料，应单独设计“诊断包”，不能混入这两个用户入口。

### 5.3 归档通用规则

- 两个 ZIP 都由 `TaskArchiveService` 从已验证快照构建，复用现有 manifest 校验和原子读取能力；不直接遍历 package 目录。
- 下载响应和根 `archive_manifest.json` 必须同时说明：纳入了哪些文件、未纳入哪些文件、未纳入原因、各文件的 stable ID、内容哈希和生成时间。
- V1 默认只纳入“可下载”文件。处理中、失败、待确认、被拒绝和完整性异常的文件绝不能静默混入。
- 任何已选文件在验证时发现 manifest 不一致、资源缺失或快照变更时，拒绝整个本次 ZIP；不能用未验证的部分结果代替。
- “下载”菜单始终是一个按钮。没有任何可纳入文件时，菜单项禁用并解释原因；可纳入部分文件时显示准确数量，例如“优化后文档压缩包（3 份）”。

## 6. 模块边界与依赖方向

```text
frontend pages / shared UI
        ↓ HTTP DTO only
Task application service ──> TaskRepository / ArchiveService / existing Job read ports
        ↓                                      ↓
   orchestration (existing) ─────────────> storage / manifest snapshots
        ↓
routing / normalization / quality (existing, independently runnable)
```

| 模块 | 可以做什么 | 不应做什么 |
| --- | --- | --- |
| `task_domain` | 定义 Task、TaskFile、状态映射、聚合和 archive selection 的纯模型 | 不依赖 FastAPI、前端、具体 parser、quality 内部实现或本机路径。 |
| `task_application` | 创建任务、附着 child job、投影任务/文件、计算下载范围 | 不重跑质量规则，不直接读取未验证文件。 |
| `TaskRepository` | 持久化 task 与 file-to-parse 关系，支持 scope 和 CAS | 不推断角色、不生成 ZIP、不执行业务质量判断。 |
| `TaskArchiveService` | 按已验证快照构建两类 ZIP | 不绕过 `delivery_eligibility()`、ReviewDecision 或 manifest 校验。 |
| `backend` | Principal/授权、HTTP DTO、幂等、审计、调用 application service | 不把内部存储路径或原始异常暴露给浏览器。 |
| `frontend` | 上传队列、任务展示、详情阅读、用户操作反馈 | 不拼接 ZIP、不计算交付资格、不直接控制 ParseJob。 |

质量层无需感知 `ProcessingTask`。工作台只消费已发布的 `QualityPackage` 和其安全投影；质量层仍可单独对内存中的 `ParsedDocument` 运行。

## 7. API 契约草案

所有正式 task API 必须遵循 P0 的“解析 Principal → tenant scope 定位资源 → 动作授权 → 业务门禁 → 审计 → 响应”顺序。接口路径可在实现时按现有路由风格微调，但资源语义不能改变。

| 接口 | 用途 | 关键要求 |
| --- | --- | --- |
| `POST /api/tasks` | 上传 1/N 份文件并创建一个处理任务 | multipart 重复字段 `files`；请求幂等；服务端逐文件预检；至少一份受理才创建任务。 |
| `GET /api/tasks` | 我的处理任务列表 | 仅在 Principal/tenant 作用域完成后提供；分页、筛选和排序由后端执行。 |
| `GET /api/tasks/{task_id}` | 读取处理中心 | 返回任务摘要、文件安全 DTO、四种状态数量、可下载范围和 polling token。 |
| `GET /api/tasks/{task_id}/events` | 获取任务级增量事件 | 聚合 child job 的已脱敏持久化事件；支持 cursor/ETag，避免浏览器为 N 个文件无限轮询。 |
| `GET /api/tasks/{task_id}/files/{task_file_id}` | 读取文档详情 | 返回当前 parse/revision 摘要、质量结论、允许动作、预览和修订记录引用。 |
| `GET /api/tasks/{task_id}/files/{task_file_id}/preview` | 读取优化后或原始预览 | `view=optimized|original`；使用安全 Markdown 和定位锚点，不返回本机路径。 |
| `POST /api/tasks/{task_id}/files/{task_file_id}/retry` | 对当前文件安全重试 | 内部复用已有 retry 规则；只在 `retryable` 时生效，创建新的 child job。 |
| `POST /api/tasks/{task_id}/files/{task_file_id}/reparse` | 对当前文件重新处理 | 内部复用已有 reparse；更新 logical TaskFile 的 active parse 指针，保留历史。 |
| `GET /api/tasks/{task_id}/downloads/original` | 下载原始解析压缩包 | 根据第 5 节的原始解析选择范围构建 ZIP。 |
| `GET /api/tasks/{task_id}/downloads/optimized` | 下载优化后文档压缩包 | 在下载时重新校验质量门、审批快照、manifest 和授权。 |
| `POST /api/review-cases/{case_id}/decisions` | 复核人决定 | 采用 P0 的独立 ReviewCase/ReviewDecision 契约；不塞进 TaskFile 的随意状态字段。 |

### 7.1 创建任务的受理语义

- 1 份文件和 N 份文件都调用同一个 `POST /api/tasks`；前端不分“单文件模式”和“批量模式”。
- 多文件上传采用“逐文件受理、任务整体可恢复”的策略：合法文件进入队列，不合法文件返回对应拒绝原因；若所有文件均被拒绝，返回 4xx 且不创建空任务。
- 一个幂等键只能对应同一份文件清单顺序、文件内容指纹和受限设置快照；同 key 不同请求返回冲突。
- 每个成功受理的文件都派生独立 child idempotency key，并建立独立 `ParseJob`；单个 child 失败不能回滚已经开始的其他 child。
- 请求只允许表达现有受限 parser/route preference；云端权限、URL、Token、临时路径和执行参数仍由服务端策略决定。

### 7.2 详情与修订投影

`DocumentDetailProjection` 至少提供以下安全字段：

```text
file_id, display_name, state, quality_state, current_parse_id,
current_version_label, parser_summary, created_at, completed_at,
preview anchors[], changes[], issues[], allowed_actions[], download_availability
```

每条 `changes[]` 由 `AppliedRepair` 和相关 `QualityIssue` 投影而来，包含：修改标题、状态、页/块/表定位、说明、原始片段、当前片段、处理原因和证据完整度。`before/after` 必须来自 repair evidence 或经相同 target/hash 验证的原始/优化表示；不能按整篇 Markdown 搜索猜测。过长或敏感片段需要截断、转义并附定位入口。

## 8. 前端正式化设计

### 8.1 页面和路由

| 路由 | 页面 | 核心内容 |
| --- | --- | --- |
| `/` | 上传文件 | 选择/拖放、上传队列、逐文件预检、开始处理。 |
| `/tasks/{task_id}` | 处理中心 | 状态摘要、文件列表、筛选、单一下载菜单、恢复轮询。 |
| `/tasks/{task_id}/files/{task_file_id}` | 文档详情 | 连续阅读、原始/优化切换、修订列表、重新处理、受权复核动作。 |

路由必须由 URL 恢复，不使用内存变量或 sessionStorage 作为任务事实来源。后端静态页面路由需要支持直接打开上述地址和浏览器刷新。

### 8.2 上传文件页

- 文件 input 启用 `multiple`；拖放、选择文件、移除单项和清空队列都保持键盘可达。
- 当前上传队列逐项展示文件名、大小、推断格式和移除操作；格式、内容和大小由服务端逐文件校验，部分受理数量会在进入处理中心时提示。
- 当前页面只提交文件；解析方式和路由偏好仍由服务端现有策略决定，不在页面中承诺固定处理方式。
- 提交按钮使用“开始处理”，选择摘要展示 1/N 份文件和总大小；成功后跳转稳定的处理任务 URL。
- 当前页面不展示文件传输或解析百分比；处理中心仅展示后端返回的实际阶段。真实字节进度可作为后续增强项。

### 8.3 处理中心

- 顶部展示四个状态计数：处理中、待确认、可下载、处理失败；点击状态可筛选列表。
- 当前每行保留一个与状态匹配的主操作：处理中和失败为“查看详情”，待确认为“查看并处理”，可下载为“查看文档”；不显示会绕过复核门禁的确认交付操作。
- 当前文件行展示文件名、格式、大小、处理状态和后端安全投影出的下一步说明；不展示内部 parse 选项或服务器信息。
- 页面只有一个“下载”按钮，点击或键盘展开“原始解析压缩包”和“优化后文档压缩包”；下载范围使用后端返回的可用数量。
- 当前页面刷新后从任务 API 恢复，且仅在存在处理中项目时进行定时状态读取。任务级 cursor/ETag、指数退避、AbortController 和事件增量读取仍为后续优化项。

### 8.4 文档详情

- 默认显示优化后文档，提供明确的“优化后内容 / 原始解析”切换；不将原始 JSON 当作默认结果。
- 桌面端使用固定可视高度的双栏：左侧正文连续滚动，右侧修订列表独立滚动；窄屏改为顺序布局，避免双重嵌套滚动。
- 右侧每条修订显示“修改内容、原始内容、当前版本、原因、位置”；点击后左侧滚动并聚焦对应锚点。
- 修订记录按自动完成、需要处理、未采用/跳过等真实状态筛选。没有安全前后片段时显示原因和定位，不能虚构差异。
- `manual_review_required` 的动作由真实 ReviewCase 决定；`reparse_required` 和 `rejected` 始终不出现“采用当前结果”。

### 8.5 前端实现结构

当前已落地的无框架结构为 `frontend/index.html`（上传页）、`frontend/task-center.html`（处理中心）、`frontend/document-detail.html`（详情页）、`frontend/workbench.js` / `frontend/workbench.css`（上传与处理中心共享逻辑和样式）以及详情页独立脚本和样式。正式 Lucide 资产已位于 `frontend/assets/` 并保留许可证说明。

下列更细粒度的 `pages/`、`shared/`、`styles/` 目录拆分仍是后续代码结构优化目标，不应被视为本轮已完成事项。

保持现有无框架、可静态部署的技术路线，但拆分当前单体 `app.js`：

```text
frontend/
├─ pages/             # upload、task-center、document-detail 页面控制器
├─ shared/
│  ├─ api-client.js   # HTTP、错误映射、幂等和 AbortController
│  ├─ task-contract.js# TaskView/FileView/DetailView 校验与状态映射
│  ├─ polling.js      # cursor/ETag 轮询与恢复
│  ├─ markdown.js     # 安全渲染与锚点定位
│  └─ download-menu.js
├─ assets/
│  ├─ lucide-icons.js
│  └─ NOTICE.md
└─ styles/
   ├─ tokens.css
   ├─ components.css
   └─ pages.css
```

样例中的本地 Lucide 图标可以正式复用，但应移入正式 `frontend/assets/`，保留许可证说明；禁止 CDN 和混用图标库。样例 `task-demo.js` 与 `02-review-workbench.html` 当前字段不一致，正式开发前必须先冻结 `TaskView`、`FileView`、`DetailView` JSON 契约，并为三页共用该契约加测试。

## 11. 风险、默认决策与完成定义

### 11.1 已知风险与处理

| 风险 | 处理方式 |
| --- | --- |
| 当前没有父任务 | 先落盘 Task domain 和 repository，再开发三页 UI；不使用浏览器临时状态替代。 |
| 当前没有身份/RBAC | 生产 task/list/download/review API 必须等 P0 授权接入；开发环境仅显式注入 fake principal。 |
| 当前队列为进程内执行器 | V1 设置严格任务限额；高并发部署前替换为耐久队列，不让页面承诺无法保证的吞吐。 |
| 当前质量报告不保证每项都有可读前后片段 | 使用 evidence/hash 验证投影；缺失时显示原因和锚点，绝不猜测 diff。 |
| 样例数据模型不一致 | 先以正式 JSON schema/fixture 冻结三页共享字段，样例只负责验证交互。 |
| 现有 ZIP 语义混杂 | 新建 archive service，旧接口保持兼容，不在原接口上做危险的含义替换。 |

### 11.2 推荐默认决策

1. 单文件和多文件采用同一个后端 `ProcessingTask`，但界面仅展示文件数量，不强调“批量”。
2. V1 两类 ZIP 只纳入状态为“可下载”的文件；复核资料以后以单独、受权的诊断包提供。
3. “采用当前结果”只在 P0 的真实复核决策完成后开放；不以点击前端按钮替代质量和权限门禁。
4. 先完成任务模型/API，再接处理中心和上传页；最后才实现下载菜单和正式复核动作，避免页面先于事实模型上线。

### 11.3 完成定义

- 用户能提交 1 份或多份文件，在处理中心看到每份文件的真实状态，并能通过稳定链接恢复任务。
- 用户能打开任一文件的详情，阅读优化后内容、查看原始解析和可追溯的修订记录。
- 两个下载选项只交付其明确定义的文件，且始终经过授权、质量/复核、manifest 和快照校验。
- 重新处理不会覆盖历史结果；质量层、统一归一化层、路由层仍可在没有工作台的情况下独立运行。
- 工作台不泄露文件系统路径、原始异常、解析器私有配置或跨任务数据。
- 真实 Docling 与 MinerU 文档可完整走通上传、任务中心、详情、修订展示和允许范围下载的浏览器 E2E。
