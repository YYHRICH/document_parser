# 文档解析工作台产品化实施清单（完全态）

> 状态：规划完成，待按阶段实施  
> 面向对象：文档提交人、质量复核人、租户管理员、平台运营/SRE、下游 LLMwiki 系统  
> 产品定位：不是“在线 PDF 转文字”工具，而是 LLMwiki 的上游文档加工、质量门禁、人工复核与受控交付工作台。

## 0. 先给结论

当前页面已经具备“上传 → 解析 → 查看基础结果 → 下载 → 重解析”的 MVP 骨架，适合内部演示与单文件验收。

完整态产品应升级为一个围绕**可信交付**运转的工作台：用户不仅要拿到文本，更要知道处理位置、任务进度、结果质量、是否可以交付、谁复核过、下游实际拿到了哪个版本。

```text
提交文档
  → 上传预检与处理同意
  → 可恢复的后台任务
  → 解析 / 归一化 / 质量检查
  → 质量分流
       ├─ 通过 / 带提醒：生成交付包
       ├─ 待人工复核：进入复核队列
       ├─ 建议重解析：推荐方式并保留版本对比
       └─ 拒绝：阻止下游交付，仅保留受控诊断证据
  → 已批准 revision 交付给 LLMwiki
```

## 1. 产品边界与不变原则

### 1.1 产品目标

- 将原始文件加工为可追溯、可校验、可判断质量的版本化文档包。
- 让业务人员能完成提交、跟踪、理解质量结论、发起重解析和查看交付状态。
- 让复核人能基于证据完成批准、拒绝或要求重解析，而不是阅读原始 JSON。
- 让下游 LLMwiki 只能消费明确 revision、质量允许且完整性已验证的交付包。
- 让管理员能控制云端策略、权限、保留期、配额、队列和审计。

### 1.2 明确不做

- 前端不直接调用 parser、质量层、云服务或存储目录；只调用受权限保护的后端 API。
- 路由、归一化和质量层仍保持独立运行；工作台只消费它们通过 Gateway/编排器输出的稳定协议。
- 不重新引入 Agent/LLM 作为质量放行或确定性修复的裁判；质量门禁和审批必须可解释、可审计。
- 不把“解析完成”误写成“可以交付”；任务状态、质量状态、审批状态、交付状态必须分开表达。

### 1.3 当前可复用基座

以下能力已经存在，应优先接入页面和产品流程，而非重复建设：

- durable `ParseJob`、阶段状态、attempt、event、错误分类、取消、重解析和 revision 谱系；
- parser capability snapshot、自动路由与 fallback 审计；
- `ParsedDocument`、`QualityPackage`、修复审计、manifest 与产物完整性校验；
- manifest 白名单下载、原子发布、跨进程 CAS 与任务恢复；
- 真实 Docling/MinerU 端到端执行证据和质量层 HTML 表格转 Markdown 能力。

## 2. 角色、权限与核心用户故事

| 角色 | 核心目标 | 可以做什么 | 不可以做什么 |
|---|---|---|---|
| 提交人 | 让文档被安全处理并获得可信结果 | 上传、查看自己任务、取消可取消任务、申请重解析、下载获准产物、删除自己任务 | 查看他人任务、读取未授权原件/诊断包、绕过质量门禁 |
| 复核人 | 对不确定结果作可追溯决定 | 领取待复核任务、查看证据与差异、批准交付、拒绝、要求重解析、填写结论 | 改写原始解析事实、修改质量规则、绕过租户边界 |
| 租户管理员 | 管理本租户的数据与策略 | 管理成员、保留期、云端策略、额度、审核队列、审计查询 | 查看其他租户数据、绕过平台级安全策略 |
| 平台运营 / SRE | 保证平台稳定可靠 | 查看匿名化指标、队列、worker、依赖健康、告警与安全诊断 | 通过普通下载接口读取客户原文 |
| 下游系统账号 | 拉取可入库版本 | 读取已批准 revision 的交付包与 manifest | 读取原件、native 产物、诊断包、待复核或拒绝版本 |

### 2.1 角色与资源权限清单

- [ ] 每个 source、job、attempt、revision、quality run、review decision、delivery、artifact 都保存 `tenant_id`、`owner_id`、创建时间和生命周期状态。
- [ ] 所有读写接口从认证 principal 推导租户与角色；不得仅凭 `parse_id` 授权。
- [ ] 原件、native 产物、优化内容、质量报告、审计证据分别配置访问级别。
- [ ] 下游系统使用最小权限服务账号，只能读取明确的已放行 revision。
- [ ] 授权改变、下载、删除、云端同意、审批、撤销交付均产生审计事件。

**验收：** 猜测或枚举任务 ID 不能泄露跨租户存在性、元数据或文件；任何未授权下载均返回 401/403 或不泄露存在性的 404。

## 4. 状态模型与不可绕过的业务规则

### 4.1 四条独立状态轴

| 状态轴 | 示例 | 用户需要理解的含义 |
|---|---|---|
| 任务状态 | queued、preflight、parsing、normalizing、quality_checking、terminal | 系统现在正在做什么，是否可取消/重试 |
| 质量状态 | pass、pass_with_warnings、manual_review_required、reparse_required、rejected | 内容是否可信、风险是什么 |
| 复核状态 | not_required、pending、assigned、approved、rejected、exception_expired | 是否已经由有权角色作出交付决定 |
| 交付状态 | not_eligible、eligible、delivered、revoked、expired | 下游是否能读取本 revision |

- [ ] UI 使用中文产品语言映射任务阶段，不能展示未解释的内部枚举。
- [ ] 每次状态变化都有时间、操作者/系统、关联 attempt/revision 和安全摘要。
- [ ] 前端超时、刷新、断网不会改变后端任务状态；页面必须支持凭 URL 或任务列表恢复。
- [ ] `needs_review` 不能吞没质量语义；页面必须同时展示真实 `quality_state` 与推荐动作。

### 4.2 质量状态 × 用户体验 × 交付权限

| 质量状态 | 用户看到什么 | 默认可下载 | 允许的下一步 | 下游正式交付 |
|---|---|---|---|---|
| `pass` | 质量通过与结构摘要 | 交付包、诊断包按权限 | 交付、下载、归档 | 允许 |
| `pass_with_warnings` | 风险范围与提醒 | 交付包（附警告）、诊断包按权限 | 交付、可选复核 | 允许，带质量元数据 |
| `manual_review_required` | 待复核原因、证据位置、负责人 | 仅诊断包按权限 | 领取复核、批准、要求重解析 | 默认禁止 |
| `reparse_required` | 推荐解析方式、失败/证据原因 | 仅诊断包按权限 | 用推荐方案创建 child job | 禁止 |
| `rejected` | 明确不可用原因 | 仅管理员受控诊断 | 拒绝、修复源文件、重新提交 | 禁止 |

- [ ] 上述门禁必须由后端下载/交付接口执行，前端隐藏按钮不是安全边界。
- [ ] `optimized.md` 是默认的“整理后内容”预览；`document.markdown` 必须标为“原始解析”。
- [ ] 页面提供“原始解析 / 优化后 / 差异”切换，并能定位每个自动修复和保守跳过项。
- [ ] HTML 表格转 Markdown 等修复按业务问题去重展示；同一表在 document/block 两个表示上的审计不能被用户误解为两次内容修改。

### 4.3 云端、隐私与数据留存规则

- [ ] 默认关闭云端解析；服务端策略可进一步收紧，客户端不能绕过。
- [ ] 自动路由或 fallback 如需从本地转到云端，任务进入“等待云端同意”，不得静默上传。
- [ ] 同意记录绑定 `job_id + revision + 服务商/区域 + 数据范围 + 同意文案版本 + 时间`；更换服务商或重新解析需重新判断。
- [ ] 高敏感文档、无授权用户或禁止云端租户必须硬性拒绝云端路径。
- [ ] 上传前和任务详情中展示：本次实际处理位置、服务商、保留期、删除方式、是否包含原件/native 产物。
- [ ] 原件、native 产物、优化内容、诊断包配置不同保留期；每个 revision 显示到期时间、冻结/legal hold 状态。
- [ ] 删除覆盖 source、产物、索引与临时下载文件；审计只保留合规所需的脱敏元数据。
- [ ] UI/API/日志不得显示绝对服务器路径、Token、Authorization、内部地址或原始堆栈。

## 5. 核心用户旅程与验收条件

### 5.1 新建任务：提交人上传一份文档

**用户故事：** 作为提交人，我希望在上传前知道文件是否受支持、会在哪里处理、可能等待多久、是否会使用云端，以及提交后怎样找到任务。

- [ ] 选择文件后进行前端轻量预检：文件名、扩展名/MIME、大小、空文件、压缩包风险提示。
- [ ] 展示服务端返回的支持格式、大小/文件数/并发配额和可用 parser；不可用 parser 禁用而非仅附加“环境未就绪”。
- [ ] 自动选择为默认，展示“为什么推荐此方案”；手动选择显示适用格式、预计限制、是否本地/云端、可能成本。
- [ ] “LibreOffice 是否可用”等服务器事实只能由服务端能力探测展示，用户不能勾选声明。
- [ ] 允许云端时展示二次确认和简明隐私说明；默认本地优先。
- [ ] 创建 job 后立即返回任务号、可复制链接与当前阶段；写入浏览器历史和“我的任务”。
- [ ] 提交使用 `Idempotency-Key`；双击、网络重放、浏览器重试不创建重复 job。

**验收：** 支持/不支持/超限/需云端同意/配额耗尽五种场景均在真正调用 parser 前给出可行动提示；刷新后可从任务链接恢复。

### 5.2 任务进行中：用户离开、刷新或遇到失败

**用户故事：** 作为提交人，我希望知道任务进展，不必守在页面前；发生问题时能理解下一步，而不是看到“5 分钟超时”。

- [ ] 任务详情展示中文阶段、开始时间、已耗时、排队位置/预计等待、实际 parser、fallback 和 attempts。
- [ ] 使用 SSE/WebSocket 或带退避的 polling 消费持久化事件；前端等待上限只影响本地提示，不改变任务结论。
- [ ] 排队/preflight 状态提供取消；不可立即取消时明确显示“取消请求”或“当前阶段不可中断”。
- [ ] `retryable=true` 显示“一键安全重试”；policy、unsupported、integrity 等不可重试错误显示对应操作。
- [ ] 失败页提供错误类别、支持码 `error_reference`、安全摘要和可复制任务链接。
- [ ] 新建或重解析进行中时，旧结果区折叠或加“上一版本”水印，禁止用户误下载旧结果当作新结果。
- [ ] terminal event 可触发站内、邮件、Webhook 通知；用户可管理通知偏好。

**验收：** 任务运行期间刷新、关页、网络恢复、worker 重启后仍可看到正确状态；5 分钟以上真实解析不会被 UI 标记为失败。

### 5.3 结果查看：用户判断内容是否可用

**用户故事：** 作为提交人，我希望用普通阅读方式理解结果和质量风险，不需要阅读 JSON 才知道该做什么。

- [ ] 默认渲染 `optimized.md`，支持安全 Markdown、表格、标题、链接与代码块展示。
- [ ] 提供“原始解析 / 优化后 / 差异 / 技术详情”四个明确层级；技术详情仅给受权诊断角色。
- [ ] 质量卡展示最终状态、交付资格、问题数量、已修复问题数、未修复风险和下一步 CTA。
- [ ] 问题列表支持严重度、规则类别、页码、block/table、修复状态筛选与定位。
- [ ] 每项问题有简明解释：影响、证据、是否已自动修复、为何不能自动修复、建议动作。
- [ ] 表格提供阅读视图与来源/结构视图；无 span 的 HTML→Markdown 修复可见，含 span 的保守保留理由可见。
- [ ] 不把服务器 package path、原始错误栈或敏感 native 内容暴露给普通用户。

**验收：** 真实 MinerU 表格修复后，默认预览与 `optimized.md` 内容一致；用户无需打开 JSON 即可知道是否可交付和如何处理问题。

### 5.4 人工复核：复核人作出可审计决定

**用户故事：** 作为复核人，我希望有一个待办队列和足够证据来批准、拒绝或要求重解析，并让提交人和下游看到可靠结果。

- [ ] 复核队列按严重度、敏感级别、等待时间、失败类型、业务优先级排序，支持领取/转派/SLA。
- [ ] 复核页展示质量问题、页/块/表来源、原始与优化差异、parser attempts、历史 review decision。
- [ ] 操作至少包括：批准交付、要求重解析、拒绝、带到期时间的例外放行；必须填写原因。
- [ ] 人工审批只改变 `ReviewDecision` / delivery eligibility，不能篡改 ParsedDocument、QualityPackage 或修复审计。
- [ ] 高风险文档支持双人复核或管理员二次批准；例外放行到期自动失效。
- [ ] 已交付后发现严重缺陷时可撤销交付、吊销下载令牌/下游访问并通知相关方。

**验收：** 每种复核动作都有 actor、角色、时间、目标 revision、理由、前后状态和证据引用；客户端改字段无法绕过门禁。

### 5.5 重解析与版本比较：用户选择更可信的版本

**用户故事：** 作为提交人或复核人，我希望重解析不覆盖旧结果，且可以理解不同解析方式带来的质量变化。

- [ ] 每次 reparse 创建新的 child job 和 immutable revision，保留 parent/source identity。
- [ ] 重解析建议依据质量状态、文件类型、能力、失败分类和云端策略排序，而不是简单列出全部 parser。
- [ ] 重解析继承并显示有效策略；用户可在权限范围内修改，所有差异有审计。
- [ ] 比较页只允许同 source identity 的 revision，展示 parser、版本、参数摘要、耗时、blocks/tables/assets、质量状态、问题变化和文本差异。
- [ ] 新 revision 不自动继承旧 revision 的人工批准；必须重新经过质量门禁。

**验收：** 用户可随时回到任一历史 revision；比较页不能把不同 source 误当作同版本，且能清楚显示“为什么推荐新版本”。

### 5.6 下载与下游交付：用户交付正确的包

**用户故事：** 作为提交人，我希望下载适合业务使用的文件；作为下游系统，我只能拿到完整、已批准、可验证的版本。

- [ ] 分离三类包：业务交付包、复核诊断包、完整审计包；每类显示内容、用途、敏感性、大小和权限。
- [ ] 交付包只含下游契约需要的受控产物，例如 optimized Markdown、canonical document、quality summary、manifest/revision 元数据。
- [ ] 原件、native、原始 HTML、调试日志默认不进入业务交付包。
- [ ] 下载前后都校验 manifest；完整性异常时阻断所有下载，不能回退渲染未验证链接。
- [ ] 下游拉取指定 revision，响应带 `revision_id`、quality/review/delivery 状态、manifest digest 和有效期。
- [ ] 所有下载/推送保留 actor、用途、时间、IP/客户端、目标 revision 和结果的审计。

**验收：** `manual_review_required`、`reparse_required`、`rejected` 均无法通过直接 URL、ZIP、API 或下游账号绕过交付限制。

### 5.7 删除、保留与批量处理

- [ ] 用户可查看并申请删除自己有权的任务，页面明确删除范围、延迟、不可恢复性和 legal hold 例外。
- [ ] 管理员可配置 source/native/quality/delivery 各自保留期、冻结和配额。
- [ ] 批次是独立实体，聚合多个 child job；显示成功、失败、待复核、取消、重复和拒绝数量。
- [ ] 支持批量预检、部分失败继续、按错误类型筛选和批量安全重试；每个重试仍生成新的 job/revision。
- [ ] 批次导出只纳入质量与权限规则允许的 revision，待复核/失败项必须显式列出。

## 6. 前端实现清单

### 6.1 交互与状态管理

- [ ] 建立全局 `current user / tenant / permissions / capability snapshot / task state` 数据模型。
- [ ] 任务详情使用 URL 路由或可分享的 `task_id`，刷新后自动恢复，不依赖内存变量。
- [ ] 将 raw job status 映射为中文产品步骤，并根据事件展示真实进度。
- [ ] 新任务、失败、取消、恢复、重试、复核、交付均有明确 loading/success/error/empty 状态。
- [ ] 不再以固定 5 分钟为失败判定；采用事件驱动或指数退避轮询。
- [ ] 上传显示真实传输进度；浏览器无法提供时如实提示“正在上传，暂无法估算百分比”。
- [ ] 下载使用安全链接策略；`target="_blank"` 增加 `rel="noopener noreferrer"`。
- [ ] 新任务运行期间不让旧 revision 冒充当前结果；显示版本标签和切换器。

### 6.2 可访问性与移动端

- [ ] 上传控件必须键盘可达：保留可聚焦 input 或提供真实 button 触发，不能只依赖 `display:none` 的 input 和鼠标点击。
- [ ] 动态状态使用 `role="status" aria-live="polite"`；严重错误使用 `role="alert"`，结果完成后移动焦点到结果标题。
- [ ] 所有按钮、下载链接、复制任务号在触屏环境达到至少 44×44px 点击区域。
- [ ] 小字号文字、footer、标签、muted 文本符合 WCAG AA 对比度；质量状态不能仅依赖颜色。
- [ ] 支持键盘焦点、skip link、可见 focus ring、`prefers-reduced-motion`。
- [ ] 窄屏采用可展开/全屏的内容预览，避免固定高度的嵌套滚动造成操作困难。
- [ ] 表格在移动端提供横向滚动、卡片式摘要或下载选项，不能强行压缩。

### 6.3 前端质量保证

- [ ] 单元测试：状态映射、权限条件、质量 gate CTA、artifact 分类、错误映射、路由恢复。
- [ ] 组件测试：上传、预检、云端同意、进度、取消、重试、复核、下载阻断、版本对比。
- [ ] 浏览器 E2E：刷新恢复、长任务、worker 重启、网络断开/恢复、浏览器重复提交、各质量状态、权限隔离、manifest 异常。
- [ ] 自动化可访问性测试：键盘路径、焦点、aria-live、对比度、移动端 viewport。
- [ ] 所有用户可见错误映射为中文且可行动；内部诊断仅通过受权支持入口查看。

## 7. 后端、领域模型与 API 实施清单

### 7.1 推荐新增/收敛的领域对象

| 对象 | 关键字段 | 目的 |
|---|---|---|
| `Tenant` / `Principal` | tenant、user、role、scopes | 统一访问控制与归属 |
| `DocumentClassification` | 敏感级别、业务标签、云端限制 | 控制处理和保留策略 |
| `CloudConsent` | job/revision、供应商、区域、文案版本、时间 | 证明真实同意，不依赖 checkbox |
| `ReviewDecision` | revision、decision、reviewer、reason、expiry、evidence refs | 审批不篡改质量包 |
| `Delivery` | revision、package type、recipient、manifest digest、expiry、status | 受控交付与撤销 |
| `AuditEvent` | actor、tenant、object、action、time、result、context | 合规追溯 |
| `Batch` | batch、child jobs、policy、aggregate status | 批量处理与部分失败 |
| `RetentionPolicy` | artifact class、expiry、legal hold | 真实数据生命周期 |

- [ ] `ParseJob`、revision、artifact 与以上对象建立明确外键/稳定 ID 关系。
- [ ] 任务事件保留系统状态迁移；人工操作、下载、策略变更另写不可变审计事件。
- [ ] API 响应使用逻辑 artifact 名称和 revision ID，移除服务器绝对目录路径。

### 7.2 API 能力清单

- [ ] `POST /api/jobs`：接收上传、预检、幂等键、可审计的云端同意；返回 task URL 与状态。
- [ ] `GET /api/jobs`：按当前 tenant/role 分页、搜索、筛选和排序；提供“我的任务/待复核/团队任务”。
- [ ] `GET /api/jobs/{id}`、`/events`：返回已脱敏的产品状态、attempt、retryability 和 timeline。
- [ ] `POST/DELETE /api/jobs/{id}/cancel`、`POST /retry`：遵守可取消/可重试规则，行为幂等。
- [ ] `POST /api/parses/{id}/reparse`：创建 child job，带 parent/source/revision 关系与策略审计。
- [ ] `GET /api/revisions/{id}`、`/compare?left=&right=`：提供不可变版本、质量、结构和差异数据。
- [ ] `GET/POST /api/reviews`：复核领取、决定、转派、备注和例外放行；后端执行授权。
- [ ] `POST /api/deliveries`、`GET /api/deliveries/{id}`：只为 eligible revision 生成受限交付包/令牌/推送。
- [ ] `DELETE /api/jobs/{id}`、`/revisions/{id}`：按保留与 legal hold 策略执行删除或申请删除。
- [ ] `/api/admin/*`：角色、策略、配额、审计、队列、指标；与普通用户 API 隔离。

### 7.3 服务端强制规则

- [ ] 服务端是云端、权限、质量交付、下载、保留和配额的唯一裁判；请求参数只能表达偏好，不能提升权限。
- [ ] 下载/ZIP/下游交付始终重新验证 manifest、revision identity、quality/review/delivery eligibility。
- [ ] Job claim/lease/heartbeat 与 CAS 保证重启/多 worker 下不重复调用 parser。
- [ ] `retryable` 只允许对真实 transient 类失败开放；policy、unsupported、integrity 失败不能伪装为可重试。
- [ ] 每个下游交付绑定明确 revision，禁止通过“当前最新”隐式取件。

## 8. 管理、运营与可观测性清单

### 8.1 管理能力

- [ ] 管理 parser catalog：可用状态、支持格式、本地/云端、GPU/许可证要求、容量与成本提示。
- [ ] 管理租户：成员、角色、并发、单文件/日处理量、存储、下载与云端额度。
- [ ] 管理数据：保留期、删除、legal hold、敏感分类、业务交付包模板。
- [ ] 管理复核：队列分配、SLA、双人复核、例外放行、撤销交付。
- [ ] 管理审计：查询上传、下载、云端、审批、删除、策略变更；支持脱敏导出。

### 8.2 运营与 SRE

- [ ] Dashboard：吞吐、排队时长、P50/P95、成功率、fallback 率、needs-review 率、质量 gate 分布、下载失败率、存储用量。
- [ ] 队列视图：queued、running、长时间无事件、死信、重复失败、取消请求、worker 健康度。
- [ ] 解析器视图：按 parser/version/format 观察失败分类、耗时、成本和质量收益。
- [ ] 告警：队列积压、云 parser 异常、manifest 完整性异常、存储逼近配额、质量 gate 异常上升、审计写入失败。
- [ ] 每个告警关联 runbook、owner、阈值、脱敏诊断与处理记录。
- [ ] 健康检查分为 liveness、readiness、worker、storage、parser capability、云端依赖，不只返回进程存活。
- [ ] 备份与恢复演练覆盖 source、job、revision、manifest、review、delivery 和 audit；定义 RPO/RTO。

## 建议的首个实施切片

先完成 P0 中最能消除用户误判的六项：
