## 1. 项目概况与真实边界

### 1.1 为什么需要这个项目

Document Parser 可定位为“面向 Wiki 知识应用的文档解析与质量交付层”。输入是 PDF、Office、图片或文本源文件，也可以是已保存的原生产物；输出是统一文档、可读正文、表格与来源结构、质量问题及可选大表索引。

使用对象主要是向知识系统提供数据的开发和集成人员，以及检查解析效果的内部使用者。典型任务是上传资料，确认内容是否完整、表格是否能定位到源单元格、哪些问题要复核，再交给下游。

【实现分析】直接把工具输出的 Markdown 入库，会混淆四件事：工具运行结束、有非空文字、结构与原文一致、足以支持业务回答。扫描件可能为空，表格可能只剩外壳，图片可能成为巨大 Base64 文本。项目需要明确“保留了什么、缺了什么、允许怎样使用”。

【待确认】原来的人工流程、需求部门、实习岗位、使用人数、交付日期和业务成本。源码不能证明“客户原来人工录入效率低下”。

### 2.1 30 秒版本

“我主要负责一个面向 Wiki 的文档质量处理模块。项目要把多种解析器的输出交给知识系统，但解析成功不代表表格结构和来源都可靠。我围绕统一文档做质量检查、表格字段绑定、白名单修复和修复后复检，把结果整理成带来源和质量状态的交付物。核心是让下游不仅拿到文本，也知道哪些结构可以使用、哪些需要复核。”

### 2.2 90 秒版本

“我主要做的是文档解析后的质量层，为 Wiki 入库提供结构可靠、来源可追踪的数据。上游接了多种解析器，但它们输出能力不同：有的只有 Markdown，有的保留表格和坐标，甚至会出现运行成功但正文为空的情况。

我的工作主线是把这些结果放到统一的质量处理流程中：先检查可用证据，再做规则诊断，只执行有明确依据的修复，最后用修复后的内容重新检查。复杂表格是重点，例如合并单元格不能简单拍平，多级表头要转成列路径，再与行键和值建立绑定；证据不充分或行键重复，就保留来源并标记不确定性。

修复也要保证一致性，不能只改表格对象而让正文还是旧内容。所以质量层会同步正文、表格块和结构，记录做过什么、什么问题已消除、哪些修复被拒绝。最终交付的不只是清洗后的文本，还有结构与质量结论。项目已有正反例测试和数据回放材料，我会用这些具体证据说明效果范围。”

### 2.3 3—5 分钟版本

“这个项目服务于 Wiki 知识应用，输入是 PDF、Office 等业务资料。我主要负责质量层，上游同学处理解析器接入和路由，下游再基于我们的交付做知识消费。这里最关键的问题是：工具成功返回，不代表文档已经能可靠入库。扫描件可能没有正文，复杂表格可能丢掉多级表头，或者文字还在但已经不知道属于哪一行哪一列。

因此质量层的目标不是重新做 OCR，而是把解析结果变成有证据、有结构、有使用边界的数据。我围绕统一的 ParsedDocument 开展处理，质量规则不依赖某个解析器私有对象。这样换解析器时，只要统一层提供相同字段，质量规则就能复用。每条规则先确认所需证据，例如有没有单元格、来源和层级，信息不足时明确记录，不能用假坐标或猜测内容补齐。

表格是最能体现处理深度的部分。一个跨两列的父表头在结构里仍然只有一个真实单元格，覆盖位置指回它。生成字段绑定时，我们按照单元格跨度构建多级列路径，再与行路径和值关联，同时保留源单元格身份。合并行头跨多行时，后面的数据行会继承同一个源行头。这样下游可以知道某个值对应的是哪个对象、哪个业务字段，而不需要再从 Markdown 猜关系。遇到重复行键或者推断表头，状态会相应降级，保留复核依据。

另一个重点是受控修复和一致性。比如 HTML 表格需要转成可读的 Markdown，我们不能只修改表格对象，还要确保表格块和全文使用同一个结果。找不到安全替换位置时就拒绝修复。处理完成后重新执行质量规则，将剩余问题、已解决问题和修复动作分别记录；这样既能追踪改了什么，也不会把执行过修复等同于问题已经解决。

质量门最后汇总问题和能力状态，区分可以交付、带警告交付和拒绝。文档能交付不意味着每一个字段都无条件可信，所以还保留局部绑定的状态。我的重点是让这套质量结论可解释、可验证，并能与上下游接口对接。

验证方面，项目有合并表头、重复行键、缺失证据和修复失败等正反例，也有基于已有解析输出的批量回放记录。最近保存的一批回放覆盖 777 个输出单元，其中包含实际表格修复和拒绝修复案例。这个数字说明处理规模，不等于答案准确率。我在面试里会重点展开自己实际负责的规则、难点和验证，回放组织等具体职责按真实参与情况说明。”

## 4. 用三个任务串起执行过程

### 4.1 正常流程：上传带合并表头的工作簿

**构造示例，非本次运行日志。** 假设上传“设备清单.xlsx”，第一层表头是“技术参数”，第二层是“电压”，数据行的行头是“设备甲”，值为“220 V”。

1. 前端把文件、可选 parser_id、options_json 组成 multipart 请求。HTTP 读取文件字节，拒绝空文件，将 JSON 选项校验为对象，再构造 ParseRequest。这里不是模型决策。
2. 未指定解析器时，应用调用路由。Excel 候选为 AnyDoc、MarkItDown，注册表过滤不可用候选并记录原因；若均不可用则异常终止。
3. AnyDoc 适配器优先尝试结构桥接。桥接脚本先生成 Markdown，再尝试 toDocument，保存 blocks 和结构错误；结构调用失败不一定让整个脚本失败。
4. Python 遍历 origin 单元格并建立 ID；covered 槽位回指 origin；子表有结构证据才递归建模。随后读取工作簿证据，补工作表名、范围、隐藏行和原始值。
5. 统一结果进入 ParsedDocument。内容和结构是解析器证据，可信范围不等于“全部内容正确”；没有 bbox 就声明缺失。
6. 应用产生 parse_id，先写统一解析包和原始文件，再执行质量用例。此时解析文件已经落盘，后续失败不代表整个任务没有任何产物。
7. 质量层建立证据索引并执行修复前规则，再执行白名单修复、复检。表格网格合法时建立列路径与行键；无法确定表头则不生成高可信绑定。
8. 质量门汇总未解决问题和能力观测，给出文档状态。API 存储随后写正文、结构和问题文件；接口返回解析结果，前端再取质量包展示。
9. 本次普通上传不会自动执行生命周期 publish。用户下载解析任务压缩包，也不等于 Wiki 已经入库。

简化绑定示例：

~~~json
{
  "row_path": ["设备甲"],
  "column_path": ["技术参数", "电压"],
  "value": "220 V",
  "value_cell_id": "table-0:r2c1",
  "source_locator": {"container_name": "设备表", "cell_ref": "B3"},
  "status": "inferred"
}
~~~

row_path 表示该值属于谁，column_path 表示该值是什么，value_cell_id 与 cell_ref 分别表示结构身份和原工作簿地址。示例使用 inferred，强调“坐标明确”与“表头语义经过验证”是两件事。真实状态由证据计算，不能写死。

### 4.2 信息不充分：只解析了筛选后可见行，且行键重复

**构造示例。** 某工作表有隐藏行，解析输出只有可见行；两条记录都叫“设备甲”，其中一条的列标题仅可从布局推断。

工作簿证据读取器取得源行数、隐藏行数、可见源行号。若输出行数等于可见行数且小于源行数，标记 visible_rows；等于全量行数标记 all_rows；对不上则 unknown。列数也一致时才把逻辑行列映射到 A1 坐标。因此“输出比源文件少”不能直接判为漏行。

质量层生成行键时先统计重复项。重复键不靠附加序号伪造成业务唯一键，而将绑定标记为 manual_review_required；表头推断则是 inferred。文档可能仍为 pass_with_warnings，不等于这些字段都可以无条件用于回答。

用户可以修改源文件后重新上传，或基于旧 parse_id 手动选择解析器重解析。重解析用例读取保存的 original 文件、创建新请求和新任务；当前没有会话槽位补全，也没有自动询问“你指哪台设备”的聊天流程。

状态变化是“旧任务保留 → 新 parse_id 与新质量结果”，不是在原任务上补一句话。前端重解析当前传 options={}，旧任务的自定义选项不会自动恢复；原文件名也被换成 reparse 加扩展名。这应作为接口边界讲清。

### 4.3 异常流程：PDF 首选解析失败，或 HTML 表无法安全替换

**构造示例。** 自动选择的首个 PDF 解析器抛出异常，编排记录 parser_id、失败原因和 duration_ms，尝试下一候选。成功后保留 fallback_history 和最初建议解析器，不把实际解析器伪装成首选。

但 fallback 触发判断较窄：只要有 Markdown、blocks、tables、OCR 或 native_artifacts，便可能认为已有结果，不继续回退。它不是质量评分驱动重试；含原生产物但无可消费正文也可能进入质量阶段。末候选为空时也未必抛“无可用结果”，因此必须依赖后续质量规则和具体输出检查。

另一种失败发生在质量修复：发现 HTML 表应转换，但其原表格块正文在全文中找不到。修复器保留原内容并写 rejected_repairs；不会只改表格对象、让正文继续显示旧表。复检将问题留在报告中，最终是否拒绝文档由实际严重程度和质量门决定，不能说任何拒绝修复都导致 rejected。

**对应已有记录**：20260908 的 MinerU Markdown 回放保存了 2 条 QL-RPR-003 拒绝原因，均为表格块内容未出现在全文中。它证明历史回放确实遇到这类同步失败，不证明本次重新运行，也不证明发生过本节假设的云端故障。

    MODE -->|是| ADAPTER[解析器适配器]
    ROUTER --> ADAPTER
    ADAPTER --> EXT[第三方本地解析 / MinerU 云 API]
    EXT --> NORM[统一 ParsedDocument + 原生旁路文件]
    NORM --> STORE[写解析包与原始源文件]
    STORE --> Q[质量用例]
    Q --> DIAG[证据检查 → 初诊 → 白名单修复 → 复检]
    DIAG --> CAN[规范块 / 表格绑定 / 关系 / 质量门]
    CAN --> APISTORE[API 存储写正文与 JSON / 可选 SQLite]
    APISTORE --> OUT[响应 / 质量展示 / 下载]
    SCAN[手动触发目录扫描] --> LIFE[SourceLifecycleService]
    LIFE --> UC
    LIFE --> MM[mmwiki 交付：原 ParsedDocument]
    LIFE --> MW[Mobilework 交付：检查质量状态]
    MW --> WIKI[下游 Wiki 自行消费]
~~~

上图区分普通解析与生命周期交付。独立的质量包目录写入器另有“临时目录—校验—替换”流程，当前 API 存储没有调用它，不应画成所有输出都具有整包事务。

| 模块 | 为什么存在 | 交换内容与确定性边界 |
|---|---|---|
| trigger | 适配 HTTP/CLI，不复制算法 | 文件字节、选项 → 请求；参数格式由代码检查 |
| app | 编排一项任务、连接端口 | 路由/解析/存储/质量结果；异常与执行顺序由代码决定 |
| domain/routing | 给出可解释候选 | 文件信号、注册能力 → 决策；不是 LLM 选工具 |
| infra/parsers | 隔离第三方调用方式与原生结构 | 子进程/API/sidecar → 统一模型与资源 |
| domain/quality | 判断结构和证据可用范围 | 问题、候选绑定、修复记录 → 质量包 |
| infra/storage 与 packaging | 文件持久化及格式投影 | 逻辑质量包 → 多文件；不同写入器保证不同 |
| lifecycle / delivery | 管理源文件变化与下游文件适配 | source_id、parse_id、哈希、发布/撤下记录 |

框架不负责“决定表格是否可信”。Pydantic 能验证枚举、字段和部分引用身份，但跨表网格关系、修复安全性、质量门策略由项目代码实现。依赖倒置使编排只依赖端口，具体解析器在组合根注入；这里的领域划分是同一 Python 项目内分层，并非多个微服务。

### 5.1 在线与离线的关系

HTTP 的 async 上传函数在读取文件后直接调用同步解析用例，并非立即返回 job_id 再由队列执行。长时间子进程或云端轮询可能阻塞该执行路径；没有本次证据支持后台分布式任务队列、请求取消传播或并发吞吐承诺。

离线回放读取已保存的 Markdown，重建分析用块/HTML 表，再执行同一质量规则。它绕过了真实原文件到解析器的过程，也没有天然带入原生坐标和图片。离线脚本与在线主链共享质量逻辑，但输入证据不同，不能直接比较两者质量状态作为解析器排名。

## 6. 路由与解析适配：选择工具之后还要验证实际输出

### 6.1 自动路由怎么决定

当前策略以扩展名为主：文本直走 MarkItDown；CSV 候选 MarkItDown、Docling、AnyDoc；Excel 是 AnyDoc、MarkItDown；现代非 Excel Office 是 Docling、AnyDoc、MarkItDown；PDF 固定 MinerU、Docling、OCR、MarkItDown。图片根据 quality_first/local_first 调整顺序。旧 Office 是否有转换工具影响候选。

之后注册表筛掉格式不支持、环境不可用或云端被禁止的候选，保存不可用原因。文件信号可以影响 OCR 参数，但不能说当前已经按照扫描比例、页数和复杂度自动计算最优成本：PDF 的候选优先级仍然固定。

【实现分析】静态候选易解释、可测试，适合初期能力边界明确的接入；代价是不能感知单份文档的最终质量或实时负载。没有每份文档全模型竞赛或自动效果学习。

### 6.2 手动选择与云端边界的实际缺口

ModelRouter 的手动分支有格式、可用性、allow_cloud 校验；但 DocumentParsePipeline 仅在 parser_id 为 None 时调用路由，手动指定直接选择适配器。因此“路由单测证明禁止云端”不能自动推广到 HTTP 手动解析。

进一步追踪 MinerU：先读 sidecar，其次 _should_use_cloud_path；该函数优先看 mineru_force_local，其后看 token 或 api_mode，没有直接读取 allow_cloud。RoutingSettings 的 allow_cloud 默认还是 true。因此 README 中“只有显式允许才云调用”并非完整入口级强保证。**这是静态发现，未进行真实上传复现。**

整改分析是让所有入口统一经过有效策略校验，并让适配器也拒绝与有效策略冲突的云调用；同时定义服务端策略与请求选项的优先级。该方案尚未实施，不能写成完成的安全贡献。

### 6.3 各适配器具体做了什么

| 适配器 | 上游已提供 | 本项目适配 | 当前边界 |
|---|---|---|---|
| AnyDoc | Office 转 Markdown 与结构 Document | Node 桥、origin/covered、嵌套表、Python 统一、工作簿证据 | 结构失败可仍保留文本；不会保证自动转用 MarkItDown |
| MinerU | 解析任务、原生 Markdown/JSON/图片 | 本地/云调用、任务轮询、下载结果、内容与表格映射 | 可用性、token、网络、产物布局影响结果 |
| Docling | 文档转换及原生结构 | 适配运行与原生结果统一 | 历史无 OCR 的实验配置不能代表当前所有配置 |
| MarkItDown | 轻量文件转换 | 统一 Markdown 块与简单表格；旧格式经转换层 | confidence 0.9/0.0 是是否有块的标记，非准确概率 |
| RapidOCR | OCR 文字、框和分数 | 图片/PDF 渲染、按页运行、行级跨度和坐标映射 | PDF 默认最多 20 页，需额外渲染依赖；不能宣称任意长 PDF 全覆盖 |

AnyDoc 桥实际先 toMarkdownBytes，再 toDocument。toDocument 错误会写到 sidecar，并不一定让进程失败；Python 桥执行失败则可能运行 AnyDoc CLI 文本路径。README “结构通道不可用则明确降到 MarkItDown”过于简化：自动编排看到非空文本或原生产物可能停止候选回退。

### 6.4 模型如何参与，为什么这里没有 Prompt 章节模板

主链里的模型职责是识别文字、版面或结构。MinerU 路由参数含 model_version=vlm、OCR/表格/公式开关；这表示调用外部模型能力，不表示本项目训练 VLM。云 API 的提交、上传、轮询、错误处理和结果解析由适配器完成。

质量修复没有自由文本 Prompt，也没有要求 LLM 输出 JSON 后执行修复的路径。模型结果先成为原生载荷，再经过字段映射、契约校验和质量规则，不能直接授权覆写事实。旧日志提出“接入 LLM repair agent”是待办，工作区已删除旧 agno-agent-design 文档，不能把它包装为现成多 Agent 系统。

常见失败分别处理：子进程超时/返回码、云端 HTTP 或业务错误、轮询未完成、结构 JSON 不合法、归一化证据不足。自动候选可能回退，手动路径通常直接呈现该适配器结果或异常；语义错误不保证都能被规则识别。没有本项目 Prompt 技巧、模型微调或生成式判分成果可据此宣称。

## 7. 统一文档：把解析结果转成可检查的证据

### 7.1 输入协议为何不只用 Markdown

ParsedDocument 包含全文、blocks、tables、assets、OCR、provenance、capabilities、warnings 和原生产物说明。全文供阅读和检索；块给出顺序和类型；表格保存单元格关系；资源对应真实字节；来源描述解析器和定位；能力声明说明哪些证据缺失。

只传 Markdown 无法区分“原表本来没有坐标”和“适配器漏了坐标”，也无法证明跨行标题如何覆盖数据。统一模型让质量层以同一种字段理解不同工具，避免每加一个解析器就复制一套质量规则。

简化证据声明：

~~~json
{
  "capabilities": {
    "table_cells": {"state": "partial", "reason": "仅有文本表格结构"},
    "bbox": {"state": "unavailable", "reason": "上游未提供坐标"}
  }
}
~~~

字段名需以具体输出为准；此例表达的是缺失要说明原因。契约校验会检查部分字段合法性，但“存在 reason”不代表 reason 正确。

### 7.2 三种身份不能混用

- source_id 是文件生命周期身份；移动但内容不变时可能沿用。
- parse_id 是一次解析任务的随机身份；重解析创建新任务。
- document_id 是统一文档身份。统一 Bundle 的生成函数使用源哈希、解析器 ID 和版本构造确定性 UUID；不同解析器/版本会不同。不能推广为所有适配器都遵循同一 ID 生成方式，MarkItDown 直接构造 ParsedDocument。
- block_id、table_id、cell_id 是文档内部对象身份；源坐标不是任务身份。

即使统一 Bundle 的文档 ID 稳定，生成函数也未包含全部解析选项，因此不能说“同 ID 必然对应完全相同的解析内容”。质量对象 ID 还可能依赖内容、来源和顺序，文本变化可能改变 ID。

### 7.3 校验与来源闭合

包校验检查对象唯一性、表格是否指向真实 table block、资源与原生产物路径、安全相对路径和可用的资源引用。质量层进一步检查顺序、来源粒度、结构与内容一致性。类型校验、对象引用闭合、文件实际存在、业务事实正确是不同层级。

代价是协议变大、跨团队字段变更要同步。收益是错误可以归因：上游没有提供、统一时丢了字段、质量规则拒绝使用，不必全都称为“模型效果不好”。

## 8. 表格结构是本项目最值得深挖的实现

### 8.1 合并单元格如何保真

AnyDoc 结构网格将真实起点标为 origin，合并覆盖位置标为 covered。本项目只把 origin 写入 cells，covered 记录 origin_cell_id；单元格有行列跨度。这样原来一个横跨两列的“技术参数”仍是一个事实，而不是两个独立表头。

Markdown 展示可以把锚点文本复制到覆盖位置以便阅读，称为 anchor-copy；它是派生显示，不创造新的源单元格。HTML 修复的另一条路径对跨度表示存在损失时也保留说明，不能把所有表格显示方式都当作完全相同的无损转换。

结构规则分析尺寸、跨度越界、重叠与网格引用。网格不合法则不继续建立可靠字段绑定。测试里构造了合并槽位与真实子表，断言子表回指父表和父单元格；这验证映射算法，不代表真实 AnyDoc 所有输入都产生正确结构。

### 8.2 多级表头与字段绑定如何生成

先分析表头行，再按列收集覆盖该列的表头单元格，形成从父到子的 column_path；同一位置冲突、找不到路径时不生成确定绑定。行头优先使用明确标记；没有时可退到首单元格，但可信状态降为 inferred。

合并行头跨越多行时，建立槽位到起始单元格索引，数据行沿 covered 继承同一个来源，去掉重复源 ID。随后统计 row_key 是否重复。重复键降为 manual_review_required，不能简单拼行号假装业务对象唯一。

最终每个数据值保存 row_path、column_path、value、行头/列头/值的 cell IDs 与 source_locator。表头可靠且行头明确才可能 verified；源 block 缺失还会降级。verified 是此规则证据链成立，不是模型对值的真实性作了人工验收。

【实现分析】预先建立行和槽位索引减少反复扫描；但跨度展开和路径构建仍占内存。没有压测支持“任意规模实时完成”。对应测试包括合并表头路径、MinerU 无行头只能 inferred、重复行键降级和合并行头继承。

### 8.3 Excel 筛选、公式和源地址怎么处理

工作簿读取器使用 openpyxl/xlrd 读取源证据，本项目不重算公式。保留 formula 与 raw_value，意味着可追踪公式表达式，不保证得到最新计算值。

工作表匹配先按名称，再按行列规模候选；若只剩一张未匹配工作表，还会使用该表。因此“唯一来源”存在启发式部分，不能说做了内容级严格对齐。行数匹配可见/全量范围且列数一致才生成具体 A1 地址；否则保留未知并记录警告。

visible_rows 表示输出符合保存的可见行范围，并非程序重新执行任意筛选表达式。隐藏行可能来自保存状态，不能简单将其归为业务过滤。测试用人工构造工作簿验证隐藏行、合并计数、B2 定位与公式保留，未验证全部复杂 Excel 格式。

### 8.4 嵌套表与跨页表

真实子表来自 AnyDoc Cell.blocks 中的 table 对象，独立编号并保存 parent_table_id、parent_cell_id 和 nesting_depth。单元格里有“类似表格”的分隔文本，不足以构造子表。

跨页规则输出续表关系候选和列漂移诊断，不会把跨页内容强行合成一张表。表头一致、弱“续行”提示和几何证据强弱不同；不能将“检测关系”说成“完整恢复所有跨页表格”。

## 9. 质量流水线：诊断、修复、复检和准入为何拆开

### 9.1 规则需要先声明证据

EvidenceContext 为块、顺序、表格等建立查询上下文。每条规则声明 required_evidence；条件不满足则跳过该规则，并记录 evidence_availability 警告。跳过不是通过，也不表示输入内容一定错误。

规则返回 issues、capability_observations、relation_candidates、binding_candidates 等。流水线注册了完整性、来源、标题、数字引用、表格和安全检查，具体能力来自实际注册表，不以旧文档的规则数量为准。

这种机制让缺失信息可解释，却也有代价：能力未观测时可能以 unavailable、非阻塞输出；无表格的文档里表格能力不适用，不应拒绝整篇文档。不能把“质量门通过”理解为每一项能力都验证了。

### 9.2 为什么先诊断再修复

当前顺序是：修复前规则 → 安全修复 → 修复后规则 → 能力矩阵与规范结构 → 质量门 → 报告。复检针对同一个修复后对象，避免正文已经变了而表格和报告仍使用旧内容。

resolved_issues 来自前后问题指纹差集：初诊出现、复检消失，才标已解决。applied_repairs 只说明发生动作；rejected_repairs 说明没做；issues 是最终仍有问题。一个修复可能对应多个问题，一次修改也可能没有让任何诊断消失，所以不能将修复数量直接当作解决问题数量。

当前 resolved_by_repair_ids 记录本轮应用的修复 ID 列表，不是逐条问题的严格因果定位。问题因指纹改变而不再出现也需要谨慎解释，不等价于人工判定事实修复正确。

### 9.3 四类自动修复的输入、行为与边界

| 修复 | 使用什么依据 | 实际动作 | 拒绝或局限 |
|---|---|---|---|
| QL-RPR-001 | 现有 Markdown | 清理行尾空白 | 不能据此证明所有 Markdown 语义完全不变，如硬换行语法需另审 |
| QL-RPR-002 | 可识别的表格分隔行 | 格式规范 | 不推测丢失内容 |
| QL-RPR-003 | HTML 表与对应 table block、全文片段 | 转 Markdown，同步表与块 | 找不到原文、结构不可转换则拒绝；跨度展示损失保留说明 |
| QL-RPR-004 | Excel string 类型 raw_value 中明确换行 | 恢复文本，重新派生表格 Markdown 并同步四份表示 | 非字符串/无换行不处理；无法与全文同步则拒绝 |

QL-RPR-004 不是“模型觉得这里该换行”。它先确认源值确实有换行，且与当前文本不同；再检查表为 anchor-copy 且有网格、对应块存在、旧块在全文可定位，最后一起更新。若更新条件不满足，不留下半改状态。当前是工作区源码事实，未找到该规则的直接专项回归记录。

QL-RPR-003 和 004 使用全文子串定位并只替换首处，不是完整文本区间映射；重复的相同表片段仍值得补反例。不要宣称已解决所有歧义定位。

### 9.4 标题树和数字引用

标题规则按确定性顺序用栈建树：新标题弹出同级或更深节点，挂到剩余较浅父节点。原层级不可依赖时，编号如 1.1 只能辅助推断，不能创建无来源的虚拟标题；全平层级等可疑情况降级。它不是通用语义章节理解。

数字引用先找到参考文献区，按明确编号或顺序建立索引，再将正文标记连接到唯一条目。重复标签不当成唯一命中；作者—年份引用不属于已有 MVP 能力。关系能够追踪到块，不能代替学术引用内容真实性核验。

### 9.5 文档状态与对象状态

文档状态为 pass、pass_with_warnings、reparse_required、rejected。绑定/能力可能为 verified、inferred、manual_review_required、unavailable 等；问题有 repaired、unfixed 等状态。uncertain 也会出现在交付复核表达中，不能与所有内部枚举混写。

质量门优先拒绝，再考虑重解析，最后是警告通过和通过。critical 默认 rejected；只有合法推荐存在时才可输出 reparse_required。当前 run_pipeline 调用 Gate 时未传推荐，报告也设置 recommendation=None，因此默认流水线需要重解析的情况会退为 rejected，不会自动选择模型重新跑。

警告不必然阻止交付：本地图片缺失规则当前是 warning，data URI 残留和系统性乱码则是 critical。不同入口的包完整性校验可能先行拦截，不能仅凭单条规则预测所有 HTTP 行为。人工复核状态也不是已建人工工单队列。

质量配置中的 enforce_stable_ids 与 unavailable_blocks_when_applicable_only 在所查质量代码中只找到定义，未见实际消费。字段存在不代表切换开关会改变运行行为。

## 10. 大表外置与物理交付

### 10.1 为什么使用 SQLite

触发条件是 max(真实 cells 数, 行数×列数) > 50,000，恰好 50,000 不触发。这是每张表的结构规模阈值，不是文件大小或整篇文档总单元格数，也没有证据表明它来自最优阈值实验。

普通表内嵌 JSON；大表的结构 JSON 保留表级信息与索引描述，省略 cells/grid 和该表绑定。SQLite 保存 document_tables、table_cells、field_bindings；按表内位置、行键和源 A1 地址建索引，FTS5 可用时加全文检索。

写入按 2,000 条批次 executemany；生成器减少一次组装全部绑定记录的开销，但 _row_data 仍构造行与覆盖槽位索引，canonical 仍持有单元格。准确说法是“减少交付 JSON 和绑定批次开销”，不能说“端到端零拷贝、常量内存”。

### 10.2 什么已校验，什么尚未证明

SQLite 校验检查文件存在、document_id、必要表和 PRAGMA integrity_check。数据库结构完整不代表每个业务绑定正确；代码声明外键也不等于实际开启外键约束。写入临时产物时还关闭 journal/synchronous，速度与故障恢复之间存在取舍。

普通绑定和 SQLite 绑定由不同函数生成，状态细节并不完全相同：普通路径还检查 source_block_id，大表路径主要依赖表头和行键。不能声称两路径已经通过全量语义等价测试。

前端大表显示外置提示，不一次加载完整单元格；API 返回质量模型时也不自动把 SQLite 全部展开成普通表。未看到完整的大表分页查询 API 或下游实测，不应把“生成索引”说成“已完成在线大表问答”。

### 10.3 两条写入路径必须区别

**独立质量包目录写入器**：创建同父目录临时目录，写 SQLite 和三个文件，校验后将旧目录改为备份、将临时目录替换为目标，失败尝试恢复。这样减少发布半包的风险；但多次 rename 并非严格的跨文件系统事务，进程崩溃和并发读者窗口仍需验证。

**当前 HTTP/CLI 应用的 ApiStorage**：先写 SQLite，再逐个写 structure.json、quality_issues.json、optimized.md，没有调用上述目录写入器及其全部引用校验。解析包也先于质量结果写入。故“所有请求都原子交付三文件”不成立。

文件交付不是只读业务：API 还支持覆盖质量包、上传和删除受管源文件，生命周期适配器写下游目录。没有发现全局鉴权或租户隔离；不能把下载路径检查泛化成完整权限体系。

## 11. 上下文与状态：管理的是文件，不是聊天记忆

每次 ParseRequest 保存文件名、类型、字节、解析器与选项；结果保存解析来源、警告和回退轨迹。重解析恢复的是原文件字节，不是会话摘要。没有用户画像、跨轮工具槽位、模型上下文裁剪或长期记忆主链。

生命周期扫描加载 manifest，对比路径及内容哈希：

| 变化 | 当前处理 | 注意事项 |
|---|---|---|
| 同路径同哈希且 active | unchanged，不重新解析 | 不等于新解析器版本自动重跑 |
| 同路径内容改变 | modified，生成新解析任务 | 下游发布失败会将源记为 parse_failed |
| 前次 parse_failed | retry，再走解析与交付 | 状态名也承载交付失败，定位需看 last_error |
| 新路径与消失文件哈希一致 | moved，沿用 source_id，更新交付文件名 | 多个同内容文件可能有匹配歧义 |
| 新文件 | added，生成 source_id 并解析 | 顺序扫描，不是分布式任务 |
| 旧路径消失 | deleted，撤下下游源 | 没有跨两个下游的事务保证 |

当前 HTTP 扫描接口明确指定 microsoft.markitdown、allow_cloud=False 和 local_first，不走默认 Excel→AnyDoc 的自动路径。网页上传普通解析与“受管目录扫描”是不同运行口径。

多模态 publish 在 Mobilework publish 之前，前者接收原 ParsedDocument、后者接收质量包并检查状态。后者失败时，前者可能已写出；删除时异常也可能中断后续 manifest 保存。这是当前状态机的剩余一致性风险，不是已实现全链补偿事务。

## 12. 外部交付与权限边界

Mobilework 已约定监视 raw/sources 下的 Markdown。本项目将允许状态的优化正文写过去，复制资源、改写相对引用、记录解析来源与质量元数据；质量状态必须 pass 或 pass_with_warnings，正文不能空，文档身份必须匹配。这里的“接入”是文件契约适配，未调用下游生成答案的 API。

mmwiki 适配把块类型、顺序、表格、资产与来源映射到其内容包，semantic 字段可为空；没有据此调用多模态模型总结图片的证据。它不接收 QualityPackage，不能保证与 Mobilework 相同质量门。

当前同时存在三文件质量包、API 内部解析包、Mobilework 元数据包、mmwiki 包，以及 schemas/examples 里的 manifest/JSONL 契约。新契约测试能证明示例自洽，不证明主应用已经输出它。不能拿 examples 的字段作为生产响应字段。

对外安全的准确口径是“存在局部路径、哈希、身份及状态检查”。上传选项仍可传 native_output_dir，错误响应会直接包含异常字符串，未见完整请求长度、资源限额和身份鉴权保障。生产接入需要先定义可信调用方和服务端参数白名单。本次未进行路径越权、云上传或破坏性验证。

## 13. 技术难点与真实问题案例

面试优先讲“发现了什么问题、如何将它转成设计”，不需要逐项朗读所有限制。下面区分已有修复和本次发现；个人参与定位、实施与验收的过程仍需本人确认。

### 13.1 工具成功了，文档却不能用

**现象与定位证据**：四模型保真度报告记录 MarkItDown 有 20 个“状态成功但空正文”，Docling 有 1 个。报告中的扫描样本还表现为无正文或表格只有空壳。定位手段是对齐源文件实例、检查输出状态与实际字符/单元格，并选样对照原文；这是已有审计过程，不是本次重新执行。

**根因**：解析运行状态表达任务结束，不表达输出可消费。仅看返回码会把语义失败当成功。

**实际应对**：当前质量注册表已接入空正文、空表结构、乱码、data URI 等规则；关键问题可变成 critical 并进入拒绝状态。自动 fallback 则仍是较窄的“是否有内容/原生产物”判断，没有完整质量反馈重试。

**为什么有效**：把执行成功与数据准入分开，错误不会只停留在工具日志中。历史 777 输出回放里仍有 rejected，说明该次回放没有把所有输入都视作合格。

**验证边界**：规则检测的是已定义失败模式，不是完整语义正确率。乱码规则基于替换字符和固定编码标记，不能识别全部内容错误。

**面试表达**：“我关注的不只是解析接口能否返回，而是结果能否进入知识链路；因此将工具状态与质量准入拆开，用可复现规则定位空成功和结构缺失。”仅在职责确认后使用第一人称。

### 13.2 修好了表格对象，正文却可能还是旧内容

**现象与证据**：MinerU 结果含 HTML 表格，若只修改 tables 而未同步 block 与全文，下游看到的是不一致版本。当前修复器与测试直接围绕三份表示同步，历史回放也记录了无法定位原文而拒绝修复的 2 个表。

**根因**：表格结构、表格块、完整 Markdown 是同一内容的不同表示；单点替换没有解决一致性。

**实际修改**：转换前找到对应 table block 和全文片段，转换后同步更新；定位失败则不覆盖原对象。之后复跑规则，用最终对象生成规范结构与报告。

**验证**：test_document_repair_synchronizes_document_block_and_table 检查同步；缺失 block 反例检查保持原文。20260908 回放记录 1,309 次 HTML 表转换、2,611 条问题消失，但不同计数不能混为修复文档数。

**剩余范围**：相同片段重复出现时，首处替换仍是限制；没有证据证明逐页人工验证所有转换。

**面试表达**：“将表格修复从字符串替换推进到对象级一致性处理，保证正文、块与表结构同步，并以复检决定问题是否真正消除。”

### 13.3 合并行头的第二行丢了业务归属

**现象**：跨行合并的行头只在第一行有真实单元格，后续数据行若只搜索本行 origin，就可能拿数值当行键或丢掉父级归属。

**根因**：把物理起始单元格误当作完整逻辑网格，没有沿 covered 找到源锚点。

**实际修改**：构建槽位到真实单元格映射，继承跨行行头并按 ID 去重；列路径仍保留多级表头。重复业务行键降级，而不是用序号绕过唯一性问题。

**验证**：当前单测包含 merged_row_header_is_inherited_by_covered_data_rows、duplicate_row_key_is_manual_not_verified；fixture 集成断言多级采购表头路径，且 MinerU 缺行头证据时只能 inferred。

**证据边界**：这是由代码改动与回归用例支撑的修复机制；未找到完整工单说明最初由谁发现、如何逐轮排查，不能编造线上事故经过。

**面试表达**：“针对合并单元格导致的字段归属丢失，建立逻辑网格与源单元格的映射，将数据值绑定到可追溯的行列语义。”

### 13.4 隐藏行不等于解析丢行，换行也不能靠猜

**现象**：保存的工作簿可能有隐藏行，输出行数少于源范围；源单元格中的多行文本也可能被压成一行。仅比较数量或盲目补文本都会误修。

**根因**：没有区分源工作表、可见视图和最终显示，也没有携带原始值。

**实际修改**：适配阶段补源行数、隐藏行、可见行号、A1 坐标和 raw_value；质量修复只在源 string 值明确含换行且能同步四份表示时恢复。

**验证**：工作簿构造测试验证可见视图、公式和 A1 定位；换行修复已读到实现，但未找到专项测试或完整实测记录。因此前半段可讲已具备测试，后半段只能讲已实现、待完善验证。

**面试表达**：“将 Excel 的视图语义和原始单元格证据引入质量链路，避免把筛选结果误判为漏数据，并限制修复只使用源文件中存在的信息。”

### 13.5 大表不宜在 JSON 中无限展开

**问题与机制证据**：当前表格数量一大，cells、grid、bindings 同时序列化会增加交付体积与对象开销。代码新增按单表规模外置 SQLite，并以批次写入、索引检索解决交付表示问题。

**实际修改**：领域策略决定阈值，基础设施生成数据库，结构 JSON 保留引用，前端提示使用外置索引。

**为什么有效**：下游不必为了查看文档结构先解析全部单元格 JSON，可按行键或源坐标查表。成本是额外文件、两条绑定实现和兼容性验证。

**验证边界**：目前是源码设计与界面分支证据，未找到专项大表压测或前后体积/耗时对照；不包装成“性能提升数倍”。这是当前改造案例，非已证实的性能事故修复。

### 14.3 设计取舍怎样包装得有技术含量

### 15.4 怎么解释价值而不依赖虚构指标

可以说“统一多解析器输入，使质量规则和下游消费不再绑定某个私有格式”“将复杂表格输出为带源单元格的字段绑定”“形成诊断、修复、复检和问题记录”“完成既有输出的批量回放与问题分层”。这些都是具体交付价值。

暂不说“问答准确率提升 30%”“性能提升 5 倍”“支撑数万用户生产运行”。需要量化时，先确认数据集、基线、指标、环境、前后对照和本人贡献，再决定是否写进简历。

## 16. 高频面试问答：以质量层为主线

### 16.1 这个项目里你主要负责什么？

**结论：我主要负责文档解析后的质量处理，把解析结果转换为可检查、可追溯的知识输入。** 项目上游负责路由和解析，下游负责 Wiki 消费；质量层基于统一文档完成诊断、表格字段绑定、确定性修复、复检及准入判断。具体子模块独立完成、协作完成的划分还需按实际经历细化。

**追问：与简单清洗脚本区别在哪？** 这里不仅改格式，还检查证据是否足够、对象关系是否可靠、修复是否同步，并输出对象状态与文档状态；不能安全处理时保留问题。

### 16.2 为什么质量层不直接调用 MinerU 的对象？

**结论：质量规则要面向统一证据，才能跨解析器复用。** 适配器负责原生字段映射，质量层只接收 ParsedDocument；同一张采购表的行列绑定不需要分别写 MinerU 和 Docling 版本。代价是上游必须保留规则所需信息，统一模型不能凭空补证据。

### 16.3 为什么不能让 LLM 直接修复全部文档？

**结论：知识输入中的数字、来源和表格归属需要受控修改。** 当前采用确定性白名单：HTML 表有可定位源片段才转换；源换行有 raw_value 才恢复。LLM 可作为未来建议工具，但当前没有生成式修复主链，也不能凭常识补缺失值。

**追问：规则不是能力太弱吗？** 对未知错误覆盖确实有限，所以系统将无法确定的内容显式标记，交给重解析或复核，而不是用流畅文本掩盖缺证。

### 16.4 修复之后如何证明没有把结果改乱？

**结论：使用同一个修复后对象重新执行规则，并同步各份表示。** 表、块与全文一起更新，随后生成规范结构；初诊与复检问题分开。测试检查同步与拒绝条件。它能证明已定义不变量，不替代完整语义验收。

### 16.5 applied_repairs 与 resolved_issues 有什么区别？

**结论：前者证明做了动作，后者证明原问题在复检中消失。** 清理行尾空白可能有动作却不改变问题数，HTML 表转换可能同时消除表示和结构问题。统计时不能一比一等同；当前问题与修复的精确因果归属也并非完整。

### 16.6 多级表头具体怎样还原？

**结论：根据真实单元格跨度，为每列构建从父到子的表头路径。** 覆盖某列的“技术参数”和“电压”组成两级路径，再与行键和值连接。冲突或缺路径时不输出可靠绑定；编号和布局推断必须降级。

### 16.7 合并行头怎样继承？

**结论：数据行沿逻辑 covered 槽位回到同一个 origin 源单元格。** 通过行/槽位索引取得跨行行头，按 ID 去重，再生成 row_path。不会把覆盖位置复制成新的事实；已有对应单测断言源 ID 继承。

### 16.8 为什么行键重复不加个序号解决？

**结论：序号只能让程序 ID 唯一，不能证明业务对象唯一。** 两条“设备甲”可能来自不同部门，重复时保留坐标和 manual_review_required，不能假装已消除歧义。下游可按源位置复核。

### 16.9 verified 等于答案正确吗？

**结论：verified 表示当前规则所需的证据链成立，不是业务正确概率。** 表头和来源可验证不意味着 OCR 数字一定无误；用户回答质量还需下游检索和人工验收。缺少 evidence_ref 的 verified 能力还会被汇总器降为 inferred。

### 16.10 没有表格的文档会因为表格能力缺失被拒绝吗？

**结论：不应把不适用能力当作缺陷。** 无表格时相关能力标 unavailable 并附不适用说明，内部 blocking=false。规则因缺证跳过仍可产生警告；不适用与“应有但没解析到”需要结合上游证据判断。

### 16.11 文档通过了，为什么里面还有人工复核项？

**结论：文档准入与局部绑定可信度是两层状态。** pass_with_warnings 可保留可用正文和不确定绑定，消费方仍需按对象状态过滤。当前人工复核标记不代表存在自动派单平台。

### 16.12 如何处理乱码和空成功？

**结论：对已知失败模式做确定性检测，并将关键问题送入质量门。** 检查空正文/空表、替换字符、编码标记、控制字符和残留 data URI。规则可复现但并非通用语义纠错；不直接猜原文。

### 16.13 HTML 表修复失败怎么办？

**结论：保留原内容，记录拒绝原因，再由复检和质量门决定是否交付。** 例如 table block 在全文找不到，就不能只改单份表示。历史回放有两条这类拒绝记录；不是所有拒绝修复都会拒绝整篇文档。

### 16.14 标题和参考文献怎么建立关系？

**结论：基于顺序、层级和明确编号建立带证据的关系。** 标题栈构建 parent_child，层级可疑时降级；数字引用只连接唯一参考条目。作者年份、任意语义引用和虚拟标题生成不在当前能力内。

### 16.15 表格少了很多行，是解析器错了吗？

**结论：先判断输出视图，再判断缺失。** 源工作表存在隐藏行时，可见行输出要标 visible_rows，保留源行数和 A1 映射。该证据由适配层提供，质量层检查和使用，个人贡献不要越过协作边界。

### 16.16 质量门为什么不用一个总分？

**结论：关键错误不能被其他高分抵消。** rejected、reparse、warning 等按明确优先级处理，critical 不应通过平均分被放行。适用范围是已定义的规则和证据，不是全能质量评分模型。

**追问：reparse_required 现在会自动执行吗？** 默认质量流水线尚未生成合法推荐，因此不能宣称自动重解析闭环；现有人工重解析能力属于应用链路。

### 16.17 测试怎么设计才有意义？

**结论：围绕不能被破坏的不变量设计正反例。** 正例验证多级表头路径，反例验证缺行头不能 verified、重复键必须降级、找不到正文不得覆盖、critical 不得被 info 策略降级。已有 fixture 和合成测试，本次未重跑。

### 16.18 你怎么证明质量处理有价值？

**结论：用可追溯交付和明确范围的回放结果证明。** 最近记录回放 777 个保存输出，0 程序异常；MinerU 有 1,309 次 HTML 表转换与 2 次拒绝修复。可说明质量链路对已保存数据有可观察处理结果，不能替代答案准确率或效率提升。

### 16.19 大表外置与你的质量层有什么关系？

**结论：质量层决定结构怎样可靠表达，存储层决定怎样承载规模。** 普通绑定内嵌，大表提供外置语义和状态；SQLite 写入是协作实现，其个人归属另核。当前尚不能保证两条绑定路径全量等价或端到端恒定内存。

### 16.20 如果继续迭代，优先做什么？

**结论：先补质量结论与实际交付的一致性，再扩展规则。** 优先统一不同入口的质量包写入/校验、增加源换行和大小表语义一致性反例、明确警告绑定的下游消费政策，再考虑可执行重解析推荐。它们是后续建议，不是已完成贡献。
